# 자기소개서·포트폴리오 초안 생성 정책

> 이슈 #14, #21. 작성일 2026-11-05, 개정 2026-11-06(#21). 구현: `core/writer_input.py`(입력 구성), `agents/application_writer.py`(생성과 검증), `prompts/write_cover_letter.md`, `prompts/write_portfolio.md`.
> 관련: 자격요건 평가 `eligibility.md`(상태 3종, 16장 개인정보), 선택한 공고 `docs/data-contract.md` 4장, 프로젝트 안내 2-4(경력·학력·자격증 창작 금지).

## 1. 원칙

1. **쓸 수 있는 사실은 코드가 정한다.** 자격요건 결과에서 요건을 `쓸 수 있는 사실(usable_facts)` / `확인 필요(to_confirm)` / `주장 금지(do_not_claim)`로 나누는 일은 코드(`build_writer_input`)가 한다. LLM은 이 분류를 바꾸지 못하고, 그 안에서 문장만 쓴다.
2. **프로필에 없는 사실은 쓰지 않는다.** 경력, 학력, 자격증, 도구, 수치, 성과를 만들어 쓰지 않는다 (프로젝트 안내 2-4).
3. **미충족과 확인 필요 요건은 "할 수 있다"고 쓰지 않는다.**
4. **경고는 지우지 않는다.** 선택한 공고의 경고 문구(data-contract 4장)는 코드가 입력에서 복사해 결과에 붙인다. LLM이 쓰지도 바꾸지도 못한다.
5. 이 정책은 문체를 다듬지 않는다. 문체 첨삭(humanizer)은 범위 밖이다.

## 2. 사실 분류 (코드)

입력은 선택한 공고(`SelectedJob`, 프로필 원문 인용을 담은 것)와 가상 프로필이다. 인용이 없으면 입력을 만들지 않는다(`WriterInputError`).

| 그룹 | 조건 | 담는 것 | 초안에서 |
|---|---|---|---|
| `usable_facts` (`F1`, `F2`…) | 요건 상태 `met` | 요건 문장, 근거 인용(경험 id 또는 칸과 원문), 숫자 요건은 코드가 만든 비교식, 경험이 근거면 그 경험의 지정 칸(`evidence_detail`, 아래) | 근거로 쓸 수 있다. 문단·불릿마다 어떤 사실을 썼는지 `fact_ids`로 밝힌다 |
| `to_confirm` (`C1`…) | 요건 상태 `needs_check`, 또는 `met`인데 근거 인용이 없는 skill·qualitative 요건 | 요건 문장, 사유 코드(후자는 `no_evidence`), 사용자에게 물을 질문 | 충족 사실처럼 쓰지 않는다. 확인 필요 목록으로 따로 돌려준다 |
| `do_not_claim` (`X1`…) | 요건 상태 `not_met` | 요건 문장 | 근거로 쓰지 않는다. 충족한다고 주장하지 않는다 |

- `any_of` 요건은 항목별로 나눈다. 통과한 항목은 `usable_facts`, 확인 필요 항목은 `to_confirm`, 미충족 항목은 `do_not_claim`이다. 요건 전체가 `met`이어도 미충족 항목을 충족했다고 쓰지 않는다.
- `type=preference`(상태 없음)는 어느 그룹에도 넣지 않는다.
- **`needs_check`인데 근거 경험이 일부 있는 요건** (`scope_unclear`, `level_unclear`): 관련 경험을 **프로필에 적힌 그대로 서술하는 것**은 `usable_facts`의 다른 사실로만 가능하다. 그 요건을 충족한다는 주장은 하지 않는다. (결정 D3)
- **사실의 근거 경험 (`evidence_detail`).** 인용문 한두 줄만으로는 쓸 재료가 없어서, 사실이 가리킨 경험의 내용을 함께 붙인다. (결정 D8)
  - `evidence_detail`은 **경험별 목록**이다: `[{experience_id, role, actions, tools, result}]`. 근거 인용(`profile_evidence`)이 가리킨 `experience_id`마다 한 항목이고, 여러 경험이 인용되면 인용된 경험 **모두**를 붙인다.
  - 허용 칸은 **`role`, `actions`, `tools`, `result` 네 개로 한정한다.** `title`, `period`, `type`, `category`는 붙이지 않는다(기간·분류값의 숫자가 근거로 새지 않게 한다). 구현은 경험 전체를 복사하지 않고 칸을 지정해 복사한다.
  - 근거가 경험이 아니라 칸(`skills`, `education[0]` 등)이면 `evidence_detail`은 붙이지 않는다. 인용문만 쓴다.
  - 인용되지 않은 경험은 어떤 경로로도 사실에 붙이지 않는다.
  - `evidence_detail`은 프로필 원문이므로 `WriterInput`과 같이 저장하지 않고, 캐시·로그·오류 메시지에 넣지 않는다.
- **업무 연결 후보 (`task_links`).** (결정 D14) 선택한 공고의 주요 업무 항목(`main_tasks`)마다 "이 경험을 이 업무와 연결해 설명할 수 있다"는 후보를 따로 둔다. **사실(`usable_facts`)이 아니다.**
  - 항목: `task_id`(`T1`…, 업무 항목 순서), `text`(업무 문장), `evidence`(프로필 인용, 경험 id + 원문), `evidence_detail`(인용된 경험의 `role`, `actions`, `tools`, `result`만, 위와 같은 규칙).
  - 만드는 방법: AI가 업무마다 프로필 경험과 인용을 고르고(`agents/task_linker.py`), 코드가 인용이 프로필 원문에 있는지 다시 대조한다. 어긋나는 후보는 버린다. 다시 묻지 않는다. 후보가 없는 업무는 없는 대로 둔다.
  - **코드가 보장하는 것:** 인용한 경험과 인용문이 프로필에 있다. 그 경험의 지정 4칸이 토큰 근거로만 쓰인다. **보장하지 않는 것:** 그 경험이 정말 그 업무와 관련 있는가(AI 판단, 사람이 읽고 확인한다).
  - **연결 후보는 판정이 아니다.** 점수, 자격요건 충족, 역량 보유의 근거로 쓰지 않고, `usable_facts`·`to_confirm`·`do_not_claim`을 바꾸지 못한다. 초안은 "이 업무를 할 수 있다"가 아니라 "이 경험을 이 업무와 연결해 설명한다" 수준으로만 쓴다.
  - **`not_met`·`to_confirm`과의 관계.** (결정 D16) 연결 후보는 프로필에 실제로 적힌 경험의 서술만 허용한다. 같은 경험이 `not_met` 요건과 관련돼도 그 요건의 충족·보유·수준을 주장할 수 없다. 허용: "관련된 경험으로 문서 정제 작업을 보조했다". 금지: "요구 경력을 갖추었다", "해당 업무를 수행할 수 있다", `X` 요건을 충족한다는 표현. `X`·`C` id를 `fact_ids`에 쓰면 계속 `forbidden_fact_id`다.
  - `evidence_detail`과 같이 프로필 원문이므로 `WriterInput`과 함께 저장하지 않고 캐시·로그·오류 메시지에 넣지 않는다. 예외는 5장.
- 프로필 근거는 `check_profile_evidence`(eligibility.md 13장)로 다시 대조한다. 프로필에 없는 경험 id나 인용이 있으면 입력을 만들지 않는다.
- 선택한 공고가 참고용(`reference_only`), 필수 요건 미충족(`eligibility_not_met`), 추출 불완전(`extraction_incomplete`)이어도 막지 않는다. 선택은 사용자의 결정이고, 경고가 따라간다. (결정 D4)

## 3. 코드가 검증하는 것과 못 하는 것

**검증한다.** 초안이 모델에서 돌아오면 `validate_draft`가 아래를 확인하고, 하나라도 어기면 초안 전체를 버리고 단계 실패로 처리한다.

| 코드 | 어긴 경우 |
|---|---|
| `bad_section` | 이 종류(`kind`)에 없는 섹션 이름(자소서의 `quality` 포함), 같은 섹션이 둘 |
| `missing_evidence` | 문단이나 불릿에 `fact_ids`도 `task_ids`도 하나도 없음 (이전 이름 `missing_fact_id`) |
| `unknown_fact_id` | 입력에 없는 사실 id |
| `unknown_task_id` | 입력에 없는 업무 연결 후보 id |
| `forbidden_fact_id` | `to_confirm`(`C…`)이나 `do_not_claim`(`X…`) id를 사실로 씀 |
| `task_only_claim` | `task_ids`만 있고 `fact_ids`가 없는 문단·불릿이 자격요건 충족·역량 보유·요건 수준을 주장하는 명시적 표현을 씀 (아래 "연결 후보만 근거인 문단") |
| `unsupported_token` | 제목, 문단, 불릿의 숫자나 영문 고유명(도구명, 자격증명 등)이 그 단위의 근거에 없음. 근거의 범위는 아래 "토큰 근거" |

**토큰 근거.** (결정 D9) 숫자·영문 토큰 검증은 **제목(`heading`), 문단 `text`, 불릿 `text` 모두**에 적용한다.

- 문단과 불릿의 근거는 **그 단위가 단 `fact_ids`와 `task_ids`의 합집합**이다(연결 후보의 근거는 그 후보의 인용문과 `evidence_detail` 지정 4칸이다). 한 문단에 사실을 둘 달면 두 사실의 근거가 합쳐진다(두 사실을 잇는 문장을 쓸 수 있어야 해서 의도한 수준이다). 단위 밖의 사실은 합치지 않는다.
- **제목의 근거**는 그 섹션의 문단과 불릿이 단 `fact_ids`와 `task_ids`의 합집합이다. 제목은 사실 id를 따로 달지 않는다.
- 사실 하나의 근거는 `text`, `evidence.quote`, `computed`, 그리고 `evidence_detail`의 `role`, `actions`, `tools`, `result` 값이다. `experience_id`, `field`, `fact_id` 같은 식별자·메타데이터는 근거가 아니다.
- 프로필 전체, 공고 요건 문장, 인용되지 않은 경험은 근거가 아니다. 연결 후보의 업무 문장(`text`)도 근거가 아니다. 그 안의 회사·팀 이름은 아래 예외의 섹션에서만 쓸 수 있다.
- 예외: 지원동기(`motivation`)와 공고 연결(`job_connection`) 섹션의 제목·문단·불릿에서만 회사명, 직무명, 업무 항목의 토큰을 더 쓸 수 있다.

**코드가 보장하는 것과 보장하지 않는 것.** (결정 D10) 코드 검증은 **토큰의 존재 여부**만 확인한다.

- 보장: 숫자 토큰(`200`)과 영문 토큰(`B2B`, `Figma`)이 위 근거에 있다.
- 보장하지 않음: (a) 숫자와 함께 쓴 `약`, `이상`, `이내` 같은 범위어가 원문과 같은 의미인지("약 200건" → "200건 이상"), (b) 역할·성과·인과관계가 보존되는지("분석 보조" → "분석 주도"), (c) 경험 필드 자체에 이미 있는 과장의 진위.
- 근거 범위를 경험으로 넓혔으므로 (a)~(c)가 지나갈 틈도 넓어졌다. 그래서 `verification` 문구에 "경험 필드 내부의 범위·역할·성과 의미는 검증하지 않았다"를 넣는다.

**근거 규칙.** (결정 D15) 문단·불릿마다 `fact_ids`와 `task_ids` **중 하나 이상**이 있어야 한다. 둘 다 있어도 된다. 연결 후보에만 근거한 문단(학회장 경험처럼 어떤 `usable_fact`에도 없는 경험)을 쓸 수 있게 하려는 것이다. `fact_ids`를 필수로 두면 무관한 사실을 임의로 붙이게 되어 근거 추적이 스키마 통과용이 되기 때문이다.

**연결 후보만 근거인 문단.** (결정 D15) `task_ids`만 있고 `fact_ids`가 없는 문단·불릿은 모든 섹션에서 허용한다. 단 자격요건 충족·역량 보유·요건 수준을 주장하는 **명시적 표현**이 있으면 거부한다(`task_only_claim`). 표현 목록: 충족, 갖추, 수행할 수 있, 해낼 수 있, 능숙, 숙달, 전문가. "설명할 수 있습니다"처럼 연결해 설명하는 표현은 막지 않는다. 이 목록 검사는 **표면 검사일 뿐**이다. 바꿔 쓴 표현("충분히 해낼 수 있는 사람입니다" 등)은 못 잡는다. 그래서 프롬프트도 "업무 관련 경험을 서술할 수는 있지만 해당 업무를 수행할 수 있다고 단정하지 않는다"를 명시하고, 통과한 초안은 사람이 4-1의 체크리스트로 읽는다.

모델 응답이 JSON이 아니거나 스키마를 어기면 `LLMStageError`다. 원시 응답은 사용자에게 보이지 않고, 다시 묻지 않는다.

**검증하지 못한다.** 아래는 코드로 확인할 수 없고, 프롬프트와 사람의 검토에 맡긴다.

- 근거 없이 쓴 과장, 그럴듯한 성과 서술, 한국어로만 쓴 새로운 사실.
- `fact_ids`를 붙여 놓고 실제로는 다른 내용을 쓴 문장 (붙은 id가 입력에 있는지만 본다). 한국어 문장의 과장, 새 성과, 프로필에 없는 태도 표현은 코드가 못 잡는다. 그래서 초안과 저장 파일에 `verification`("의미는 검증하지 않았다, 경험 필드 내부의 범위·역할·성과 의미도 검증하지 않았다, 안전 검증을 마친 결과가 아니다")을 항상 붙이고, 실제 AI 통과를 안전 검증 완료로 부르지 않는다.
- `to_confirm`, `do_not_claim`의 요건을 id 없이 문장으로 주장하는 경우. 연결 후보가 실제로 그 업무와 관련 있는지.
- 문체와 설득력.

그래서 초안은 **제출용이 아니라 사용자가 검토할 초안**이다. 화면에도 "초안, 사실 확인 필요"라고 표시한다.

## 4. 출력 형식

초안(`ApplicationDraft`)은 `kind`(`cover_letter` / `portfolio`), 섹션 목록, 확인 필요 목록(코드가 `to_confirm`에서 복사), 경고 문구(코드가 복사), 실행 메타(모드, 모델, 프롬프트 버전, 토큰)를 가진다. 확인 필요 목록과 경고 문구는 모델이 쓰지 않는다.

| `kind` | 섹션 이름 (`section`) |
|---|---|
| `cover_letter` | `motivation`(지원동기와 입사 후 포부), `job_experience`(직무 관련 경험과 역량, 품질·검수 사례도 여기에 쓴다), `collaboration`(커뮤니케이션·주도적 업무 경험) |
| `portfolio` | `project_summary`(프로젝트·경험 제목과 한 줄 요약), `role_actions`(목표, 본인의 역할과 행동), `tools_results`(사용한 도구·방식, 결과), `job_connection`(지원 공고와 연결되는 이유), `highlight_experiences`(포트폴리오에서 강조하면 좋은 경험) |

**섹션의 모양.** (결정 D11) 섹션은 `section`, `heading`(소제목 한 줄), `paragraphs[]`(`text`, `fact_ids`), `bullets[]`(`text`, `fact_ids`, 선택)다. 자소서와 포트폴리오가 같은 모양이다.

- 문단은 1개 이상, 문단과 불릿마다 `fact_ids`·`task_ids`(둘 다 선택, **합쳐서 1개 이상**)를 단다. 제목에는 id가 없고 3장의 토큰 근거 규칙으로 검증한다.
- 화면과 확인용 md는 근거를 구분해 보인다: `(자격요건 근거 F1, 업무 연결 후보 T2)`. 연결 후보가 없으면 `(자격요건 근거 F1)`. 연결 후보를 사실처럼 `사실`이라고 표시하지 않는다. md 상단에는 "업무 연결 후보는 판정이 아니다"를 적는다.
- **문단 수(2~4개)와 문단당 문장 수(3~4문장)는 프롬프트의 권장이다. 스키마 조건이 아니다.** 사실이 적을 때 문단 수를 강제하면 모델이 근거 없는 문단을 채우게 된다.
- 문단은 "경험 → 배운 점 → 입사 후 연결" 순서로 쓰도록 프롬프트가 안내한다(권장).
- `highlight_experiences`는 불릿 목록(강조할 경험)과 작성 요령 문단을 담는다. 불릿도 경험을 직접 주장하므로 문단과 같은 검증을 받는다.

### 4-1. 품질 체크리스트 (사람이 읽는 기준, 이슈 #23)

코드 검증이 못 보는 초안의 품질을 사람이 같은 기준으로 판정한다. **의미 검증이 아니고 코드는 점수로 환산하지 않는다.** 개선 전·후를 같은 사람이 같은 표로 본다. 기준을 바꾸면 기준선도 다시 채워 둘 다 기록한다. (결정 D17)

| 항목 | 판정 | 기록 |
|---|---|---|
| 주요 업무 커버리지 | 업무 항목마다 초안에 **그 업무와 직접 연결되는 문장**이 있으면 1, 없으면 0. 같은 업무를 여러 번 언급해도 1. `task_ids`가 붙었다고 자동으로 1이 아니고, 사람이 문장의 의미를 보고 판정 | `k/업무 수` |
| 운영 행동 활용 | 운영·문서화 경험(예: 학회 스터디 운영, 자료 아카이빙)이 **근거 있는 행동과 함께** 알맞은 섹션에 쓰였는가. 직위(학회장)만으로 조율·주도·성과를 주장하면 ① 역할 부풀림으로 센다. 쓰이지 않았다면 실패가 아니라 "프롬프트 개선 효과 없음"으로 기록 | 쓰임 / 일부 / 안 쓰임 + 섹션 |
| 입사 후 연결 | 일반적 문장인가, 공고 업무와 이어지는 구체 문장인가 | 일반 / 구체 |
| 코드가 못 거른 표현 | **서로 다른 표현 1건**(같은 표현이 반복돼도 1건). 범주 5개: ① 역할 부풀림 ② 근거 없는 성찰 ③ 범위어 변경 ④ 새 성과·능력 ⑤ 일반적 포부. 개선 전 표현에 식별자(`B-CL-01`, `B-PF-01`…)를 붙여 목록을 고정한다 | 범주별 건수 |

표현 원문과 판정은 커밋하지 않는 폴더에 두고, **커밋하는 것은 숫자와 식별자뿐**이다(8장 8-3).

**자소서에서 `quality`를 뺀 이유.** (결정 D12) `quality`(꼼꼼함·품질 관리)는 검수가 핵심 업무인 공고의 항목이었다. 공고와 무관하게 고정 섹션으로 두면 근거가 약하고, 샘플 3번에서는 `job_experience`와 같은 사실을 인용해 겹쳤다. 품질·검수 사례는 `job_experience`에 쓴다. 공고가 4번째 섹션을 고르게 하는 방안은 후속이다. 이전 형식의 응답(`quality`, `text` 단독 칸)은 `bad_section` 또는 스키마 위반이다.

- 포트폴리오는 PPT나 디자인 파일이 아니라 **구성과 방향성을 보이는 프로젝트 소개 초안**이다.
- 자소서와 포트폴리오는 같은 입력(`WriterInput`)과 같은 생성 경로를 쓰고 `kind`와 프롬프트만 다르다. (결정 D1)
- 모든 섹션을 반드시 채울 필요는 없다. 쓸 수 있는 사실이 없는 섹션은 빼고, 사실이 하나도 없으면 단계 실패다.

## 5. 개인정보와 저장

- **외부 LLM에는 가상 프로필과 샘플 공고만 보낸다.** 외부 클라이언트로 부르려면 호출하는 쪽이 `allow_external_profile=True`를 명시해야 하고, 프로필이 가상이 아니면 외부 클라이언트로는 부르지 않는다(`PermissionError`). 실제 프로필 경로는 구현하지 않는다 (eligibility.md 16장).
- 보내는 프로필 입력은 `profile_payload`(이름·연락처·주소·링크 제외)와 같은 칸이다.
- **실제 호출 방법.** `python -m tools.run_demo --select <샘플 job_id> --draft <kind> --ai --accept-free-tier-terms`. 초안 작성 호출 1회(재시도 포함 최대 4회)만 실제 Gemini로 가고, 자격요건과 게이트는 mock이다. 동의, 설정, 하루 호출 예산을 점검한 뒤에만 보내고, 화면 첫 줄에 `writer: ai`와 모델 ID를 표시한다. 샘플 공고 6건 밖의 공고는 선택할 수 없다.
- **`WriterInput`은 디스크에 저장하지 않는다.** 프로필 내용이 들어 있어서 같은 프로세스 안에서만 넘긴다. 프로필이 든 LLM 요청은 `contains_profile=True`로 표시해 디스크 캐시에 남기지 않는다.
- **업무 연결 후보 호출.** (결정 D18) `--task-links {none,fixture,ai}`(기본 `none` = 연결 후보 없이 초안을 쓴다). `ai`는 `--ai`일 때만 가능하고, 연결 후보를 만드는 호출 1회를 초안 호출 앞에 더한다(동의, 설정, 하루 예산 점검에 반영). 외부 클라이언트는 `allow_external_profile=True`와 가상 프로필일 때만 쓴다. 연결 후보는 `contains_profile=True`로 디스크 캐시에 남기지 않고, **어떤 실행 결과로도 저장하지 않는다.** 사람이 읽고 확정하려면 `--links-only`로 연결 후보만 화면에 보인다(초안 호출은 하지 않고 호출은 연결 후보 1회뿐).
- **연결 후보 고정본(예외).** 프롬프트 버전을 바꿔 가며 초안을 비교하려면 연결 후보가 같아야 한다. 실행마다 AI가 새로 만들면 비교가 안 되므로, 가상 프로필(김하늘)과 샘플 공고에서 만든 연결 후보를 **사람이 읽어 확정한 것만** `tests/fixtures/task_links_sample3.json`에 합성 fixture로 둔다(`--task-links fixture`가 읽는다). 이는 이미 커밋돼 있는 mock 근거 fixture(`eligibility_evidence_mock.json`)와 같은 성격의 합성 데이터라서 허용하는 예외다. 실제 지원자 프로필에서 만든 연결 후보는 어떤 경우에도 파일로 두지 않는다.
- **초안은 기본으로 저장하지 않는다.** 가상 프로필이고 `--save-draft`를 줄 때만 `data/results/drafts/<run_id>-<job_id>-<kind>.json`에 쓴다. 이 폴더는 커밋하지 않는다. 초안에는 프로필에서 나온 문장이 들어 있으므로 개인정보로 다루고, 자동 삭제는 없다. (결정 D5)
- **실제 AI 초안은 확인용 md를 항상 쓴다.** (결정 D13) 실제 AI로 만든 초안(`writer: ai`)은 호출 비용을 쓴 결과를 사람이 전체로 읽어야 해서, `--save-draft` 없이도 같은 폴더에 `<run_id>-<job_id>-<kind>.md`를 쓴다. 가상 프로필일 때만 쓰고(가상이 아니면 쓰지 않는다), 커밋하지 않으며, 같은 이름이 있으면 덮어쓰지 않는다. 내용은 화면에 내는 초안과 같다(소제목, 문단, 불릿, 근거 사실 id, 확인 필요 목록, 경고, `verification`). json은 여전히 `--save-draft`일 때만 쓴다. mock 초안은 `--save-draft`를 줄 때만 json과 md를 함께 쓴다. 검증을 통과하지 못해 버려진 초안은 어떤 파일도 남기지 않는다(3·6장).
- 사용량 기록에는 호출 수, 토큰, 모델 ID만 남기고 프롬프트와 응답 내용은 남기지 않는다. 정책 기록에도 숫자만 적는다.
- API 키는 `.env`에만 둔다. 결제 계정은 연결하지 않는다.

## 8. 실제 AI 실행 기록 (2026-11-05, 이슈 #14)

숫자와 코드만 적는다. 공고 원문, 프로필, 초안 본문은 적지 않는다.

- **조건.** 모델 `gemini-3.1-flash-lite`, 생성 설정 `a3ea338a`, 샘플 3번 공고, 가상 프로필(김하늘). 자격요건과 게이트는 mock이고 초안 작성 호출만 실제다. 프롬프트 `write_cover_letter`, `write_portfolio` version 1. RPM 15 / RPD 500, 결제 계정 미연결(사용자 확인). 프로필이 든 요청이라 디스크 캐시에 남기지 않았다.

| 초안 | 실행 ID | 호출(실패) | 토큰 입력 / 출력 | 코드 검증 |
|---|---|---|---|---|
| 자기소개서 | `4187a398` | 1 (0) | 2,360 / 490 | 통과 (섹션 3개, 사실 id 모두 입력에 있음) |
| 포트폴리오 1회차 | `b99862b3` | 1 (0) | 2,422 / 474 | **거부됨.** 초안이 저장·출력되지 않았다. 사유 코드는 이 실행에서 확인하지 못했다(오류 출력이 화면 필터에 가려졌다) |

- 합계 호출 3회(통신 실패 0), 토큰 입력 7,204 / 출력 1,502. 이날 이 모델의 누적은 129/500이다(이 이슈 시작 전 126).
- 검증 결과: 스키마 위반 0, 프로필에 없는 사실 id와 금지·확인 필요 id 사용은 통과한 두 초안에서 0, 숫자·영문 토큰 위반은 통과한 두 초안에서 0. 포트폴리오 1회차의 거부는 위 코드 중 하나다.
- **코드가 못 거른 것(사람이 읽고 확인한 것).** 통과한 초안에도 프로필에 없는 표현이 일부 있었다. 예를 들어 근거가 "약 200건"인 곳에 "200건 이상", 근거가 "인도 개발진"인 곳에 "다국적 팀원들", 근거에 없는 "주도적으로 문제 해결을 고민했다"는 서술이다. 3장이 밝힌 한계(한국어 문장으로 쓴 과장은 코드가 못 거른다)가 실제로 나타난 것이다. 그래서 화면에 "초안, 사실 확인 필요"를 표시한다.
