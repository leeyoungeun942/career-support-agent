# 자기소개서·포트폴리오 초안 생성 정책

> 이슈 #14. 작성일 2026-11-05. 구현: `core/writer_input.py`(입력 구성), `agents/application_writer.py`(생성과 검증), `prompts/write_cover_letter.md`, `prompts/write_portfolio.md`.
> 관련: 자격요건 평가 `eligibility.md`(상태 3종, 16장 개인정보), 선택한 공고 `docs/data-contract.md` 4장, 프로젝트 안내 2-4(경력·학력·자격증 창작 금지).

## 1. 원칙

1. **쓸 수 있는 사실은 코드가 정한다.** 자격요건 결과에서 요건을 `쓸 수 있는 사실(usable_facts)` / `확인 필요(to_confirm)` / `주장 금지(do_not_claim)`로 나누는 일은 코드(`build_writer_input`)가 한다. LLM은 이 분류를 바꾸지 못하고, 그 안에서 문장만 쓴다.
2. **프로필에 없는 사실은 쓰지 않는다.** 경력, 학력, 자격증, 도구, 수치, 성과를 만들어 쓰지 않는다 (프로젝트 안내 2-4).
3. **미충족과 확인 필요 요건은 "할 수 있다"고 쓰지 않는다.**
4. **경고는 지우지 않는다.** 선택한 공고의 경고 문구(data-contract 4장)는 코드가 입력에서 복사해 결과에 붙인다. LLM이 쓰지도 바꾸지도 못한다.
5. 이 정책은 문체를 다듬지 않는다. 문체 첨삭(humanizer)은 범위 밖이다.

## 2. 사실 분류 (코드)

입력은 선택한 공고(`SelectedJob`, 프로필 원문 인용을 담은 것)와 가상 프로필이다. 인용이 없으면 입력을 만들지 않는다(`WriterInputError`).

| 그룹 | 조건 | 담는 것 | 초안에서 |
|---|---|---|---|
| `usable_facts` (`F1`, `F2`…) | 요건 상태 `met` | 요건 문장, 근거 인용(경험 id 또는 칸과 원문), 숫자 요건은 코드가 만든 비교식 | 근거로 쓸 수 있다. 문장마다 어떤 사실을 썼는지 `fact_ids`로 밝힌다 |
| `to_confirm` (`C1`…) | 요건 상태 `needs_check`, 또는 `met`인데 근거 인용이 없는 skill·qualitative 요건 | 요건 문장, 사유 코드(후자는 `no_evidence`), 사용자에게 물을 질문 | 충족 사실처럼 쓰지 않는다. 확인 필요 목록으로 따로 돌려준다 |
| `do_not_claim` (`X1`…) | 요건 상태 `not_met` | 요건 문장 | 근거로 쓰지 않는다. 충족한다고 주장하지 않는다 |

- `any_of` 요건은 항목별로 나눈다. 통과한 항목은 `usable_facts`, 확인 필요 항목은 `to_confirm`, 미충족 항목은 `do_not_claim`이다. 요건 전체가 `met`이어도 미충족 항목을 충족했다고 쓰지 않는다.
- `type=preference`(상태 없음)는 어느 그룹에도 넣지 않는다.
- **`needs_check`인데 근거 경험이 일부 있는 요건** (`scope_unclear`, `level_unclear`): 관련 경험을 **프로필에 적힌 그대로 서술하는 것**은 `usable_facts`의 다른 사실로만 가능하다. 그 요건을 충족한다는 주장은 하지 않는다. (결정 D3)
- 프로필 근거는 `check_profile_evidence`(eligibility.md 13장)로 다시 대조한다. 프로필에 없는 경험 id나 인용이 있으면 입력을 만들지 않는다.
- 선택한 공고가 참고용(`reference_only`), 필수 요건 미충족(`eligibility_not_met`), 추출 불완전(`extraction_incomplete`)이어도 막지 않는다. 선택은 사용자의 결정이고, 경고가 따라간다. (결정 D4)

## 3. 코드가 검증하는 것과 못 하는 것

**검증한다.** 초안이 모델에서 돌아오면 `validate_draft`가 아래를 확인하고, 하나라도 어기면 초안 전체를 버리고 단계 실패로 처리한다.

| 코드 | 어긴 경우 |
|---|---|
| `bad_section` | 이 종류(`kind`)에 없는 섹션 이름, 같은 섹션이 둘 |
| `missing_fact_id` | 섹션에 `fact_ids`가 하나도 없음 |
| `unknown_fact_id` | 입력에 없는 사실 id |
| `forbidden_fact_id` | `to_confirm`(`C…`)이나 `do_not_claim`(`X…`) id를 사실로 씀 |
| `unsupported_token` | 본문의 숫자나 영문 고유명(도구명, 자격증명 등)이 그 섹션이 인용한 사실(문장, 근거 인용문, 비교식)에 없음. 프로필 전체와 공고 요건은 근거가 아니다. 지원동기(`motivation`)와 공고 연결(`job_connection`) 섹션에서만 회사명, 직무명, 업무 항목의 토큰을 더 쓸 수 있다 |

모델 응답이 JSON이 아니거나 스키마를 어기면 `LLMStageError`다. 원시 응답은 사용자에게 보이지 않고, 다시 묻지 않는다.

**검증하지 못한다.** 아래는 코드로 확인할 수 없고, 프롬프트와 사람의 검토에 맡긴다.

- 근거 없이 쓴 과장, 그럴듯한 성과 서술, 한국어로만 쓴 새로운 사실.
- `fact_ids`를 붙여 놓고 실제로는 다른 내용을 쓴 문장 (붙은 id가 입력에 있는지만 본다). 한국어 문장의 과장, 새 성과, 프로필에 없는 태도 표현은 코드가 못 잡는다. 그래서 초안과 저장 파일에 `verification`("의미는 검증하지 않았다, 안전 검증을 마친 결과가 아니다")을 항상 붙이고, 실제 AI 통과를 안전 검증 완료로 부르지 않는다.
- `to_confirm`, `do_not_claim`의 요건을 id 없이 문장으로 주장하는 경우.
- 문체와 설득력.

그래서 초안은 **제출용이 아니라 사용자가 검토할 초안**이다. 화면에도 "초안, 사실 확인 필요"라고 표시한다.

## 4. 출력 형식

초안(`ApplicationDraft`)은 `kind`(`cover_letter` / `portfolio`), 섹션 목록(`section`, `text`, `fact_ids`), 확인 필요 목록(코드가 `to_confirm`에서 복사), 경고 문구(코드가 복사), 실행 메타(모드, 모델, 프롬프트 버전, 토큰)를 가진다. 확인 필요 목록과 경고 문구는 모델이 쓰지 않는다.

| `kind` | 섹션 이름 (`section`) |
|---|---|
| `cover_letter` | `motivation`(지원동기와 입사 후 포부), `job_experience`(직무 관련 경험과 역량), `quality`(꼼꼼함·품질 관리 경험), `collaboration`(커뮤니케이션·주도적 업무 경험) |
| `portfolio` | `project_summary`(프로젝트·경험 제목과 한 줄 요약), `role_actions`(목표, 본인의 역할과 행동), `tools_results`(사용한 도구·방식, 결과), `job_connection`(지원 공고와 연결되는 이유), `highlight_experiences`(포트폴리오에서 강조하면 좋은 경험) |

- 포트폴리오는 PPT나 디자인 파일이 아니라 **구성과 방향성을 보이는 프로젝트 소개 초안**이다.
- 자소서와 포트폴리오는 같은 입력(`WriterInput`)과 같은 생성 경로를 쓰고 `kind`와 프롬프트만 다르다. (결정 D1)
- 모든 섹션을 반드시 채울 필요는 없다. 쓸 수 있는 사실이 없는 섹션은 빼고, 사실이 하나도 없으면 단계 실패다.

## 5. 개인정보와 저장

- **외부 LLM에는 가상 프로필과 샘플 공고만 보낸다.** 외부 클라이언트로 부르려면 호출하는 쪽이 `allow_external_profile=True`를 명시해야 하고, 프로필이 가상이 아니면 외부 클라이언트로는 부르지 않는다(`PermissionError`). 실제 프로필 경로는 구현하지 않는다 (eligibility.md 16장).
- 보내는 프로필 입력은 `profile_payload`(이름·연락처·주소·링크 제외)와 같은 칸이다.
- **실제 호출 방법.** `python -m tools.run_demo --select <샘플 job_id> --draft <kind> --ai --accept-free-tier-terms`. 초안 작성 호출 1회(재시도 포함 최대 4회)만 실제 Gemini로 가고, 자격요건과 게이트는 mock이다. 동의, 설정, 하루 호출 예산을 점검한 뒤에만 보내고, 화면 첫 줄에 `writer: ai`와 모델 ID를 표시한다. 샘플 공고 6건 밖의 공고는 선택할 수 없다.
- **`WriterInput`은 디스크에 저장하지 않는다.** 프로필 내용이 들어 있어서 같은 프로세스 안에서만 넘긴다. 프로필이 든 LLM 요청은 `contains_profile=True`로 표시해 디스크 캐시에 남기지 않는다.
- **초안은 기본으로 저장하지 않는다.** 가상 프로필이고 `--save-draft`를 줄 때만 `data/results/drafts/<run_id>-<job_id>-<kind>.json`에 쓴다. 이 폴더는 커밋하지 않는다. 초안에는 프로필에서 나온 문장이 들어 있으므로 개인정보로 다루고, 자동 삭제는 없다. (결정 D5)
- 사용량 기록에는 호출 수, 토큰, 모델 ID만 남기고 프롬프트와 응답 내용은 남기지 않는다. 정책 기록에도 숫자만 적는다.
- API 키는 `.env`에만 둔다. 결제 계정은 연결하지 않는다.

## 6. 실패 처리

| 상황 | 처리 |
|---|---|
| 외부 클라이언트인데 허용이 없음, 또는 가상이 아닌 프로필 | `PermissionError`. 아무것도 보내지 않는다 |
| 프로필 인용이 없거나 프로필과 맞지 않음 | `WriterInputError`. 호출하지 않는다 |
| 통신 실패, 재시도 소진, 스키마 위반 | `LLMStageError`. 다시 묻지 않는다 |
| 위 3장의 검증 실패 | `DraftError(코드)`. 초안을 저장하지 않고 원시 출력도 보이지 않는다 |
| 한도 소진 | `LLMQuotaExceeded`. 재시도하지 않고 멈춘다 |

실패한 섹션을 임의의 문장으로 채우지 않는다.

## 8. 실제 AI 실행 기록 (2026-11-05, 이슈 #14)

숫자와 코드만 적는다. 공고 원문, 프로필, 초안 본문은 적지 않는다.

- **조건.** 모델 `gemini-3.1-flash-lite`, 생성 설정 `a3ea338a`, 샘플 3번 공고, 가상 프로필(김하늘). 자격요건과 게이트는 mock이고 초안 작성 호출만 실제다. 프롬프트 `write_cover_letter`, `write_portfolio` version 1. RPM 15 / RPD 500, 결제 계정 미연결(사용자 확인). 프로필이 든 요청이라 디스크 캐시에 남기지 않았다.

| 초안 | 실행 ID | 호출(실패) | 토큰 입력 / 출력 | 코드 검증 |
|---|---|---|---|---|
| 자기소개서 | `4187a398` | 1 (0) | 2,360 / 490 | 통과 (섹션 3개, 사실 id 모두 입력에 있음) |
| 포트폴리오 1회차 | `b99862b3` | 1 (0) | 2,422 / 474 | **거부됨.** 초안이 저장·출력되지 않았다. 사유 코드는 이 실행에서 확인하지 못했다(오류 출력이 화면 필터에 가려졌다) |
| 포트폴리오 2회차 | `28e7c06b` | 1 (0) | 2,422 / 538 | 통과 (섹션 5개) |

- 합계 호출 3회(통신 실패 0), 토큰 입력 7,204 / 출력 1,502. 이날 이 모델의 누적은 129/500이다(이 이슈 시작 전 126).
- 검증 결과: 스키마 위반 0, 프로필에 없는 사실 id와 금지·확인 필요 id 사용은 통과한 두 초안에서 0, 숫자·영문 토큰 위반은 통과한 두 초안에서 0. 포트폴리오 1회차의 거부는 위 코드 중 하나다.
- **코드가 못 거른 것(사람이 읽고 확인한 것).** 통과한 초안에도 프로필에 없는 표현이 일부 있었다. 예를 들어 근거가 "약 200건"인 곳에 "200건 이상", 근거가 "인도 개발진"인 곳에 "다국적 팀원들", 근거에 없는 "주도적으로 문제 해결을 고민했다"는 서술이다. 3장이 밝힌 한계(한국어 문장으로 쓴 과장은 코드가 못 거른다)가 실제로 나타난 것이다. 그래서 화면에 "초안, 사실 확인 필요"를 표시한다.
- 확인 필요 목록(`C1`)과 경고 문구는 모델이 쓰지 않았고 코드가 붙였다. 샘플 3번은 경고가 없다.
- 이 실행의 숫자·영문 토큰 검증은 개정 전 규칙(프로필·공고 전체가 근거)으로 했다. 인용한 사실로 좁힌 현재 규칙으로는 다시 돌리지 않았다.
- 샘플 3번에는 `not_met` 요건이 없어 "미충족 요건 주장을 막는다"는 실제 AI 결과로 확인하지 못했다. 단위 테스트(샘플 1번)로만 확인했다. 실제 AI가 프로필 밖 사실을 쓴 경우를 코드가 막는 것도 실제 결과로는 못 봤다(통과한 초안의 표현은 코드가 못 거른 것이다).
- 이 실행은 초안 품질을 평가한 것이 아니다. 생성이 이어지는지와 안전 검증이 동작하는지만 본 것이다.

### 8-1. 개정 뒤 샘플 1번 실행 (2026-11-06, PR #20 리뷰 반영 뒤)

샘플 1번은 `not_met` 요건이 있는 공고다. 자기소개서를 3번 시도했고(실행 8694e032, e4d1d4c4, 09ad416c) 호출은 각 1회, 통신 실패 0, 토큰 입력 2,553 / 출력 263·458·411이다. 이날 이 모델의 누적은 132/500이다.

- 3번 모두 코드 검증이 거부했다: `unsupported_token`, `job_experience` 섹션의 영문 이름 `B2B`가 그 섹션이 인용한 사실에 없었다. 초안은 나오지 않았고 저장도 없다. 실제 AI 결과를 코드가 막은 첫 사례다.
- 초안이 나오지 않았으므로 "미충족 요건을 근거로 한 주장을 막는다"는 이 실행으로도 확인하지 못했다. 단위 테스트로만 확인했다.

## 9. 개정 이력
