## 0. 이 문서가 정하는 것

직무 게이트는 **분류 데이터**와 **판정 규칙**으로 이루어진다. 이 문서는 데이터를 만드는 기준과, 그 데이터로 공고를 판정하는 규칙을 정한다.

| 데이터 | 답하는 질문 | 보관 위치 (MVP) | 이 문서 |
|---|---|---|---|
| 직무군 정의 | 이 직무군은 무엇을 책임지고 무엇을 만들어 내는가? | [03-1_직무군정의.md](job-family-definition.md) + 코드 설정값 | 3-2 (형식) |
| **사람인 소분류 매핑표** | 사람인의 이 소분류는 우리 분류에서 무엇인가? | **매핑 CSV 1개** | 3-3 |
| 문맥 판별 규칙 | 뜻이 여러 개인 소분류는 어떤 단어와 나오면 어느 직무군 후보인가? | 매핑표의 `context_rule` 열에 규칙 ID, 규칙 내용은 이 문서 3-4 표 + 코드 설정값 | 3-4 |
| 인접 직무군 쌍 | 이 두 직무군은 인접으로 볼 수 있는가? | 이 문서 4-2 표 + 코드 설정값 | 4장 |
| 판정 규칙 | 공고 1건을 데이터로 판정하는 절차와 기준값 | 이 문서 | 5장 |

**CSV를 1개만 두는 이유:** 네 데이터는 논리적으로 다르지만, 따로 파일로 관리할 만큼 크거나 자주 바뀌는 것은 사람인 소분류 매핑(664행)뿐이다. 직무군 정의는 10개 안팎이고, 문맥 판별 규칙과 인접 쌍도 지금은 몇 개뿐이다. 목표는 파일 수를 줄이는 것이 아니라 **같은 정보를 두 곳에 적지 않는 것**이다. 그래서 판정 원칙은 이 문서에, 직무군 정의는 [03-1 문서](job-family-definition.md)에 두고, 코드가 반복해서 읽는 구조화된 값만 CSV나 코드 설정값으로 둔다.

**나중에 파일로 분리하는 조건:** 아래 중 하나에 해당하면 그 데이터를 별도 CSV로 옮긴다.

| 데이터 | 분리 조건 | 분리할 파일 |
|---|---|---|
| 문맥 판별 규칙 | 규칙이 20개를 넘거나, 팀원이 코드 없이 직접 고쳐야 할 때 | `context_rules.csv` |
| 인접 직무군 쌍 | 희망 직무가 서비스기획 외로 늘어 쌍이 10개를 넘거나, 여러 직무군 조합을 반복 검증할 때 | `adjacent_pairs.csv` |
| 직무군 정의 | 직무군이 20개를 넘거나, 대표 키워드를 자주 고칠 때 | `job_families.csv` |

## 1. 정의

### 1-1. 직무 게이트

**직무게이트는 채용공고가 하나씩 지나가는 게이트입니다.** 정확히는 공고 혼자가 아니라 "이 공고"와 "사용자가 고른 희망 직무"를 한 쌍으로 받아서, 공고의 핵심 업무가 그 직무와 같은지 봅니다.

```
사용자: 희망 직무 = 서비스기획 (직접 선택)
            │
공고 1 ──▶ [직무 게이트] ──▶ 일치      → 상위 그룹 (primary)
공고 2 ──▶ [직무 게이트] ──▶ 불일치    → 직무 불일치 그룹 (job_mismatch)
공고 3 ──▶ [직무 게이트] ──▶ 검토 필요 → 상위 그룹 + "직무 확인 필요" 표시
```

- **자격요건 평가는 모든 공고가 받는다.** 게이트 결과는 정렬 그룹만 정한다. 불일치·범위 외 그룹의 자격요건 결과는 지원 추천이 아니라 **"참고용 평가"**다 ([자격요건 평가 문서](eligibility.md) 14장).

- 희망 직무는 사용자가 직무군 목록에서 직접 고른다. 그래서 지원자 쪽 직무는 따로 분류하지 않는다.
- 게이트는 공고를 버리지 않는다. 판정 결과에 따라 그룹을 나누고 순서를 정한다.

### 1-2. 게이트가 판단하지 않는 것

> **직무 게이트는 "이 공고의 핵심 업무가 지원자의 희망 직무와 같은가"만 판단한다.**
> 경력·학력·기술 숙련도·고용형태 같은 지원 자격은 자격요건 평가([자격요건 평가 문서](eligibility.md))가 맡는다.

| 질문 | 담당 | 1번 팔레트 공고 예시 |
|---|---|---|
| 이 공고는 지원자가 희망하는 직무인가? | **직무 게이트** (이 문서) | 일치. 에이전트 워크플로우, UX, 예외 처리 설계 중심 |
| 지원자가 이 공고의 자격요건을 충족하는가? | **자격요건 평가** (자격요건 평가 문서) | 서비스 기획 경력 0.5년 < 3년 → 미충족 확인 |
| 종합 | 적합성 평가 결과 | 직무는 맞지만 지원 자격은 부족함 |

인턴 6개월이 "서비스 기획 경력"으로 인정되는지는 게이트에서 정하지 않는다. 자격요건 평가 문서 1장(관련 경력 인정 기준)을 따른다.

### 1-3. 용어

용어는 종류별로 나눈다. 같은 표에 있는 용어끼리만 같은 층위다.

**가. 외부 분류와 공고 표기**

| 용어 | 뜻 | 예 |
|---|---|---|
| 사람인 대분류 | 사람인 직무 코드표의 대분류 (21개) | 기획·전략 |
| 사람인 소분류 | 사람인 직무 코드표의 소분류 (2,178개). 판정 대상이 아니라 후보 탐색 단서로만 쓴다 | 서비스기획, 웹기획, OKR |
| 직무명 | 공고에 실제로 쓰인 직무 이름 | AI Product Manager, AI 에이전트 개발자 |

**나. 우리 분류**

| 용어 | 뜻 | 예 |
|---|---|---|
| 직무군 | 공고의 핵심 업무를 기준으로 정의한 내부 판정 단위. 사람인 대분류와 소분류 사이에 놓인다 | 서비스기획 |
| 직무군 ID | 코드에서 직무군을 가리키는 고유 식별자. 직무군 이름이 바뀌어도 유지한다 | `JF_SERVICE_PLANNING` |
| 직무군 정의 | 직무군이 책임지는 업무와 핵심 결과물을 설명하는 기준. [03-1 문서](job-family-definition.md)에 적는다 | "사용자가 쓰는 서비스의 기능과 화면을 설계한다" |
| 직무군 대표 키워드 | 그 직무군의 업무를 가리키는 단어. 직무군 정의에 속한다 | 화면, 기능, 와이어프레임, 요구사항 |

**다. 판정에 쓰는 단서와 규칙**

| 용어 | 뜻 | 예 |
|---|---|---|
| 후보 탐색 단서 | 업무 항목에서 **후보** 직무군을 찾는 데 쓰는 단어. 사람인 소분류 이름(또는 매핑표 `match_terms`의 대체 표기) + 직무군 대표 키워드. 이것만으로 직무군을 확정하지 않는다 | "웹기획", "프로젝트매니저", "와이어프레임" |
| 문맥 판별 대상 | 이름만으로 직무군을 정할 수 없는 사람인 소분류. 매핑표의 분류 상태 값이다 | 기획, 스토리보드, 사업기획 |
| 문맥 판별 규칙 | 문맥 판별 대상이 어떤 단어와 함께 나오면 어느 직무군 후보인지 정한 규칙. 3-4 표에 적는다 | 스토리보드 + 화면·기능 → 서비스기획 후보 / 스토리보드 + 영상·촬영 → 범위 외 후보 |

**라. 분류 상태 (매핑표의 사람인 소분류 1개에 붙는 값, `mapping_status` 열)**

| 상태 | CSV 값 | 뜻 | 예 | 후속 처리 |
|---|---|---|---|---|
| 매핑 | `mapped` | 직무군 하나에 대응한다 | 웹기획 → 서비스기획 | `job_family_id`를 적는다 |
| 문맥 판별 대상 | `context` | 이름만으로 의미를 정할 수 없어 문맥 규칙이 필요하다. "아직 판단하지 못함"이라는 뜻이 아니다 (그런 행은 `review_status=draft`로 남긴다) | 기획, 스토리보드 | `context_rule`의 규칙 적용, 안 되면 AI 판별 |
| 공통 업무 | `common` | 실제 업무이지만 이 소분류만으로 특정 직무군을 판정할 수 없다. `item_type=직무`여도 이 상태가 될 수 있다 | 시장조사, 자료조사 | 공통 단서로 쓰고, 걸린 하위 업무는 AI 판별로 `공통` 여부를 확인 (5-2) |
| 범위 외 | `out_of_scope` | 직무이지만 지원 범위에 직무군이 없다 | 마케팅기획, 교육기획 | 범위 외 판정의 근거 |
| 비직무 항목 | `non_job` | 직무가 아닌 다른 개념이다 | CEO, OKR, RFP | `item_type`에 무엇인지(직급 / 방법론 / 산출물 / 주제 / 근무형태) 적는다. 판정에 쓰지 않는다 |

**마. 판정 결과 관련**

| 용어 | 뜻 |
|---|---|
| 업무 항목 라벨 | 공고의 업무 항목 1개에 붙이는 값: 직무군 ID / `공통` / `범위외` / `혼합` (5-2) |
| 핵심 직무군 | 업무 항목 라벨로 추정한 공고의 중심 직무군. 판정 결과가 검토 필요여도 보존한다 |
| 판정 결과 | 일치 / 인접 / 불일치 / 검토 필요 / 범위 외 (1-5). 핵심 직무군과 별도 필드다 |
| 인접 직무군 쌍 | 핵심 직무는 다르지만 구체적인 업무가 겹쳐 "인접"으로 볼 수 있는 직무군 두 개 (4장) |

### 1-4. 분류 구조

```
사람인 소분류 (예: 스토리보드)
   │  매핑표에서 분류 상태 확인
   ▼
후보 탐색 단서 (소분류 이름 · 직무군 대표 키워드)
   │  문맥 판별 대상이면 context_rule의 규칙 적용
   ▼
문맥 판별 규칙 (화면·기능·와이어프레임 vs 영상·광고·촬영·콘티)
   │
   ▼
후보 직무군 (서비스기획 또는 다른 직무군)
   │  업무 항목의 결과물이 직무군 정의(3-2)와 맞는지 확인
   ▼
업무 항목 라벨 → 핵심 직무군 → 판정 결과
```

- 단서와 규칙이 내는 것은 **후보**다. "스토리보드"와 "화면"이 함께 나왔다고 무조건 서비스기획으로 확정하지 않는다. 최종 근거는 그 업무 항목이 **어떤 결과물을 만드는지**다 (2-1).
- 사람인 대분류는 위 흐름에 들어가지 않는다. 충돌 기록과 범위 외 확인에만 쓴다 (2-2, 5-1).

### 1-5. 판정 결과 5종

| 결과 | 의미 | 후속 처리 |
|---|---|---|
| **일치** | 핵심 업무가 희망 직무와 같다 | 상위 그룹 (`primary`) |
| **인접** | 핵심 직무는 다르지만 인접 직무군 쌍에 있고, 희망 직무군 업무도 확인된다 (4장) | 상위 그룹 + "직무 범위 차이" 표시 |
| **불일치** | 핵심 업무가 희망 직무와 다르다는 근거가 명확하다 | 직무 불일치 그룹 (`job_mismatch`). 자격요건 결과는 참고용 평가 |
| **검토 필요** | 자동 판정을 믿기 어렵다 (사유 코드 참고) | **자동 제외하지 않음.** 상위 그룹 + "직무 확인 필요" 표시, 사용자 확인 요청 |
| **범위 외** | 지원 범위에 직무군이 없는 직무라는 근거가 있다 (5-1의 범위 외 확정 조건) | 불일치와 라벨을 구분해 맨 아래 그룹(`out_of_scope`)에 표시. 자격요건 결과는 참고용 평가 |

- **검토 필요는 불일치가 아니다.** 업무 정보가 없다는 사실은 직무가 다르다는 증거가 아니다. 적합한 공고를 잘못 제외하는 것(거짓 불일치)이 더 큰 손해이므로, 확신이 없으면 제외하지 않는다.
- **범위 외와 불일치는 다르다.** 범위 외는 "판단하지 않기로 한 영역"이고, 불일치는 "희망 직무와 다르다는 판단"이다.
- **검토 필요는 최종 결과다.** 다만 검토 필요가 되어도 추정한 핵심 직무군과 사유는 지우지 않는다. 사용자가 확인하면 그 값을 출발점으로 쓴다.

**검토 필요 사유 코드** (판정 결과를 검토 필요로 만든다. 코드리뷰 P1-5의 사유 코드 방식과 같다)

| 사유 코드 | 조건 (5-1) |
|---|---|
| `정보 부족` | 정리한 업무 항목이 최소 개수보다 적고, 범위 외 확정 조건도 만족하지 않는다 |
| `핵심 업무 없음` | `공통`을 빼고 나면 남는 업무 항목이 0개다 |
| `혼합 직무` | 어느 라벨도 과반을 차지하지 못한다 |
| `직무명-업무 충돌` | 직무명이 가리키는 직무군과 핵심 직무군이 다르고, 업무 판정이 명확성 기준(5-3)에 못 미친다 |

**경고 코드** (판정 결과는 바꾸지 않고 근거에만 남긴다)

| 경고 코드 | 조건 |
|---|---|
| `직무명 차이` | 직무명이 가리키는 직무군과 핵심 직무군이 다르지만, 업무 판정이 명확하다 |
| `대분류 차이` | 사람인 대분류가 가리키는 영역과 핵심 직무군이 다르다 |
| `미확정 분류 사용` | 판정에 확정되지 않은 매핑 행이 관여했다 (3-3) |

## 2. 기준

### 2-1. 같은 직무의 기준

> **기준: 주요 업무의 중심 책임과 결과물이 같으면 같은 직무다.**

- 직무명은 회사마다 다르다. "AI 에이전트 기획", "프로덕트 매니저", "서비스 기획자"가 사실상 같은 일일 수 있다. 그래서 **직무명이 아니라 담당 업무로 분류**한다.
- 판단할 때 쓰는 질문: **"이 사람이 일을 마치고 나면 손에 남는 결과물이 무엇인가?"**
- 업무가 하나라도 겹친다고 같은 직무가 되지는 않는다. 문서 작성, 데이터 분석, API 명세 작성, 커뮤니케이션 같은 **공통 업무는 단독 판정 근거로 쓰지 않는다.**

일치 여부는 두 단계로 보지만, 게이트는 1차만 판정한다.

| 단계 | 질문 | 예시 | 처리 |
|---|---|---|---|
| 1차 | 핵심 **직무군**이 같은가? | 서비스기획 / 개발 / 영업 / 경영기획 | **게이트에서 판정** |
| 2차 | 책임과 결과물의 **범위**가 같은가? | UX 중심 / AI 워크플로우 설계 중심 / 콘텐츠·데이터 구조화 중심 | 적합성 평가에서 설명 |

2차를 잘게 나누면 이름만 다른 같은 직무를 불일치로 분류할 수 있다. 1번과 3번 공고는 둘 다 서비스기획(1차 일치)이고, 범위 차이(1번 UX·운영 흐름, 3번 콘텐츠 구조화·구현 요건)는 적합성 평가에서 설명한다. 개선안의 "직무 연결 비율 50% 미만 → 직무 연결 약함" 표시가 이 역할을 일부 맡는다.

### 2-2. 사람인 분류와 직무명을 쓰는 방식

우리 분류의 목적은 판정이고, 사람인 분류의 목적은 검색(노출)이다. 직무명은 회사가 붙인 이름이다. **세 가지 모두 업무 판정을 뒤집지 못한다.**

- **사람인 대분류**는 범위 외 확인과 충돌 기록에 쓴다. 너무 넓고(서비스기획과 경영기획이 모두 "기획·전략"), 공고 등록자가 고른 값이라 실제 업무와 다를 수 있다. 대분류가 다르다는 사실만으로 불일치·검토 필요·범위 외를 확정하지 않는다.
- **사람인 소분류**에는 직무명, 직급(CEO), 방법론(OKR), 기술명(PostgreSQL), 근무 형태(2교대)가 섞여 있고, 여러 대분류에 중복된 이름이 150개 있다. 그래서 판정 기준이 아니라 **후보 탐색 단서**로만 쓴다.
- **직무명**은 업무 판정이 명확하면 경고(`직무명 차이`)로만 남긴다. 업무 판정이 명확하지 않을 때만 검토 필요 사유가 된다 (5-3).

### 2-3. 지원 범위

21개 대분류 전부에 직무군을 만들지 않는다.

- **1차 지원 범위 (사람인 대분류 기준, 5개):** 기획·전략, IT개발·데이터, 디자인, 영업·판매·무역, 상품기획·MD
  - 선택 이유 1: 샘플 프로필의 희망 직무(서비스기획)와 샘플 공고 6건의 직무가 모두 이 안에 있다 (기획·전략, IT개발·데이터, 영업·판매·무역).
  - 선택 이유 2: "기획"은 뜻이 넓은 말이라 어느 대분류(문맥)에 있느냐에 따라 가리키는 직무가 달라진다. 서비스기획과 헷갈리기 쉬운 이름이 디자인(UI/UX디자인)과 상품기획·MD(기획MD, 브랜드기획)에 있다. 이 두 대분류를 범위에 넣어 서비스기획과 아닌 것을 가르는 기준점을 분명히 한다.
  - 분류할 소분류 수: 기획·전략 72, IT개발·데이터 260, 디자인 148, 영업·판매·무역 113, 상품기획·MD 71 (합계 664)
  - **상품기획·MD 매핑 보류 (2026-10-27):** 다음 단계(설정값 이전, 샘플 공고 테스트)로 먼저 넘어가려고 상품기획·MD 71행의 매핑을 보류한다. 지금 매핑표는 나머지 4개 대분류 593행이다. 보류해도 지원 범위에서 빼지는 않는다. 그래서 상품기획·MD 공고가 5-1의 1단계에서 범위 외로 끝나지 않는다. 03-1의 `JF_MD` 직무군도 그대로 `지원`이다. 문맥 판별 규칙(`CTX_PLANNING`, `CTX_PRODUCT_PLANNING`, `CTX_SALES_MD`)과 영업 경계 기준이 이 ID를 쓰고, MD 업무 항목은 `JF_MD` 대표 키워드로 후보를 찾는다. 빠지는 것은 기획MD, 온라인MD 같은 소분류 이름 단서뿐이다. 검증용 공고에 MD 공고를 넣을 때(6-1) 다시 작성한다.
- **대분류 범위와 직무군 범위는 다르다.** 위 5개 대분류는 매핑표에 넣어 분류하는 범위(매핑 대상)이고, 실제로 판정하는 범위는 [03-1 문서](job-family-definition.md)에서 `지원` 상태인 직무군이다. 그래서 지원 대분류 안의 소분류라도 대응하는 지원 직무군이 없으면 `out_of_scope`가 된다 (예: 디자인 대분류의 인쇄·편집 디자인).
- `out_of_scope`는 소분류 이름만 보고 붙이지 않는다. 그 소분류의 핵심 책임과 결과물이 03-1의 어느 지원 직무군 정의와도 맞지 않는다는 근거가 있을 때만 붙인다.
- 범위 밖 공고를 어떻게 판정하는지는 5-1의 1번(범위 외 확인)이 정한다.

## 3. 분류 데이터 작성 규칙

### 3-1. 공통 규칙

| 규칙 | 내용 |
|---|---|
| 작성 순서 | **직무군 정의(3-2) → 매핑표(3-3) → 문맥 판별 규칙(3-4) → 인접 직무군 쌍(4-2).** 정의가 먼저 있어야 매핑의 기준이 생긴다. 최소한 서비스기획과 그 경계 직무군(경영기획, 프로젝트관리, 개발, 디자인, 상품기획·MD)의 정의를 먼저 확정한다 |
| 확정 여부 | 매핑표의 `review_status` 열로 관리한다. 에이전트가 채운 행은 `draft`, 작성자가 검토한 행은 `approved`. **판정은 `approved` 행만 읽는다** |
| 미확정 행 | `draft` 행은 판정에 쓰지 않는다. 그 소분류가 나온 업무 항목은 AI 판별로 넘기고 `미확정 분류 사용` 경고를 남긴다 |
| 문서 표와 코드 설정값 | [03-1 문서](job-family-definition.md)와 이 문서 3-4, 4-2의 표가 원본이다. 코드는 같은 값을 설정값으로 읽는다. 값을 바꿀 때는 이 문서 표를 먼저 고치고 코드에 옮긴다. 옮긴 뒤 문서와 코드가 같은지 검증한다 |
| 근거 | 매핑표의 `source`, `mapping_reason` 두 열에 적는다 (3-5) |
| 버전 | 행마다 버전을 적지 않는다. 판정 기록(5-4)에 매핑표 파일 수정일, 이 문서 개정일, 설정값 버전을 남긴다 |

### 3-2. 직무군 정의 형식

- 값은 [03-1_직무군정의.md](job-family-definition.md)에 둔다. 여기에는 항목 형식과 작성 원칙만 둔다. 직무군 수가 적고 사람이 직접 관리하므로 CSV를 따로 두지 않는다 (0장 분리 조건).
- 정의·핵심 결과물·대표 키워드는 NCS 세분류의 능력단위를 근거로 쓴다. NCS에 맞는 세분류가 없을 때만 2-1 기준 문장으로 채운다 (근거 순서는 03-1 문서 0-2).
- 코드는 `직무군 ID`, `대표 키워드`, `정의`, `핵심 결과물`을 읽는다. 앞의 둘은 후보 탐색(5-2), 뒤의 둘은 AI 판별 프롬프트에 쓴다.

| 항목 | 내용 |
|---|---|
| 직무군 ID | 고유 식별자. 바꾸지 않는다 |
| 직무군명 | 화면에 보이는 이름 |
| 정의 | 한 문장 |
| 핵심 결과물 | 일을 마치면 손에 남는 것 |
| 대표 키워드 | `;`로 구분. **그 직무군에만 나오는 단어만** 넣는다. 두 직무군 이상에 나오는 단어는 공통 업무나 문맥 판별 규칙(3-4)으로 보낸다 |
| 경계 기준 | 헷갈리기 쉬운 다른 직무군마다 "결과물이 X면 Y" 한 줄 |
| 지원 상태 | `지원` / `범위외` |
| 근거 | NCS 세분류·능력단위 분류번호, 또는 정책문서 2-1 (3-5) |

**공통 업무 기준:** 아래 둘 중 하나면 공통이다.

1. 지원 직무군 2개 이상의 정의에 같은 업무가 나온다.
2. 그 업무의 결과물이 특정 직무군의 핵심 결과물이 아니다 (예: 회의록, 일반 보고서).

공통 업무 예시는 직무군마다 따로 적지 않고 한 목록으로 둔다: 문서 작성, 데이터 분석, 커뮤니케이션·협업, API 요건 전달, 시장·자료 조사, 서비스 운영.

**운영 업무의 분류 (2026-10-28 추가)** — `공통`과 `범위외`는 핵심 직무군 계산(5-1의 4단계)에서 다르게 센다. `공통`은 분모에서 빠지고, `범위외`는 분모에 남아 직무군의 비율을 낮추며 과반이 되면 공고 전체가 범위 외가 된다. 그래서 "운영"이라는 말이 나오면 무엇을 운영하는지로 가른다.

| 운영 대상 | 라벨 | 이유 | 예 |
|---|---|---|---|
| 자사 서비스·제품을 돌리는 일 (고객 대응, 운영 이슈 처리, 이용 데이터 모니터링, 운영 루틴) | `공통` | 결과물이 지원 직무군 어디의 핵심 결과물도 아니다 (공통 기준 2). 사람인 코드표에도 "서비스운영" 소분류가 없어 범위외 근거가 없다 (2-3) | 핀브릿지 "서비스 운영 및 관리", 치즈에이드 "서비스 운영 이슈 대응" |
| 별개 직무의 운영 (마케팅 캠페인, 커뮤니티, 교육, 정부과제, 이벤트, 매장·사업 운영) | `범위외` | 그 분야 자체가 지원 범위 밖의 직무다 | 펜타베이스 "커뮤니티 운영 및 관리", 지니파이 "교육 현장 운영" |
| 지원 직무군의 산출물을 관리하는 운영 (프로젝트 일정·진척 관리, 출시 일정 관리) | 해당 직무군 | 일정·인력·원가 관리는 `JF_PROJECT_MGMT`의 핵심 결과물이다 | 치즈에이드 "개발 일정 및 이슈 관리, 납품 일정 준수" |

- GM(게임운영)(사람인 97)처럼 매핑표에서 `out_of_scope`로 확정된 운영 직무는 위 표와 관계없이 `범위외`다.
- 판단이 어려우면 `공통`으로 둔다. 근거 없이 `범위외`를 붙이면 서비스기획 공고가 범위 외나 검토 필요로 밀려난다 (1-5: 확신이 없으면 제외하지 않는다).

**공통 단서** (5-2의 3단계에서 쓴다. 공백을 지우고 비교한다)

| 공통 업무 | 단서 (`;` 구분) |
|---|---|
| 문서 작성 | 문서 작성; 문서화; 보고서 작성; 회의록 |
| 데이터 분석 | 데이터 분석; 지표 정의; 모니터링; A/B 테스트; 데이터 취합 |
| 커뮤니케이션·협업 | 커뮤니케이션; 협업; 조율; 협의; 소통; 미팅 |
| API 요건 전달 | 연동 요건; API 명세; 요건 전달 |
| 시장·자료 조사 | 시장 동향; 트렌드; 벤치마킹 |
| 직무 횡단 일반어 | 납품; 견적; 발주; 원가관리; 일정관리 |
| 지원 업무 | 영업 지원 |

- 공통 단서는 `공통`을 확정하는 키워드가 아니라 **AI 판별로 보내는 표시**다. 단서가 걸려도 같은 하위 업무에 직무군 단서가 있거나 결과물이 직무군의 핵심 결과물이면 그 직무군이다 (예: 5번 "시장조사 … 거래처를 발굴" → 영업).
- 매핑표 `common` 행의 `job_name`·`match_terms`(시장조사, 자료조사, 리서치, 트렌드분석 등)도 공통 단서로 쓴다. 같은 단어를 이 표에 다시 적지 않는다.
- "API 연동", "개발"처럼 개발자가 직접 하는 업무에도 나오는 넓은 단어는 단서로 쓰지 않는다 (4번 공고의 "API 연동"이 개발 업무).
- `CTX_CLIENT`의 `공통` 후보 줄(고객사·협업 등)은 "클라이언트"라는 이름의 뜻을 가르는 용도로만 둔다.
- **직무 횡단 일반어 (2026-10-28):** "납품"(영업, 프로젝트 납품), "견적"(영업, 시공), "발주"(상품기획·MD, 매장 개설), "원가관리"(프로젝트관리, 상품 원가)는 둘 이상의 직무와 직무 밖에서도 쓰여 "그 직무군에만 나오는 단어만 대표 키워드로" 원칙에 어긋났다. 대표 키워드(03-1)에서 빼고 공통 단서로 옮겼다. 규칙 확정에 쓰이지 않고 AI 판별로 간다. 3-4 규칙 줄의 키워드는 문맥이 소분류로 이미 좁혀진 상태에서 후보를 가르는 용도라 그대로 둔다.
- **직무 횡단 일반어에 "일정관리" 추가, "영업 지원" 단서 추가 (2026-11-02, 원티드 확인셋 오류에서 나온 수정):** "일정관리"는 기획자·개발자·마케터 모두 쓰는 말인데 프로젝트관리 대표 키워드여서 "R&D 과제 총괄 기획, 운영 및 일정 관리"가 프로젝트관리로 확정됐다. "영업 지원"은 상품기획·마케팅 공고의 "제품 교육 및 영업 지원"처럼 영업이 아닌 직무가 영업을 돕는 업무를 말한다. 영업 대표 키워드 "영업"이 걸려도 규칙 확정을 하지 않고 AI 판별로 보낸다. 영업 지원이 영업 직무인지는 AI가 업무 전체를 보고 정한다. 확인셋을 보고 고쳤으므로 확인셋은 이 수정의 시험에 다시 쓰지 않는다 (6-4).
- 초기값이다. 샘플 6건에 맞춰 만든 표가 아니므로 검증용 공고(6장)로 확인하고 고친다.

**데이터분석 분류 기준:** 독립 직무로서의 데이터분석과 다른 직무 안의 데이터분석 업무를 나눠서 처리한다.

| 상황 | 처리 | 예 |
|---|---|---|
| 독립 데이터분석 직무 (매핑표의 소분류) | 분석 자체가 핵심 책임이고 결과물이 분석 보고서·분석 모델이다. 범위 외 여부는 03-1에 데이터분석 직무군이 `지원` 상태로 있는지로 정한다 (2-3). **2026-10-26에 03-1에 `JF_DATA_ANALYSIS`를 추가했으므로 `mapped`다.** 서비스기획 등 다른 직무를 희망하는 사용자에게는 불일치로 나온다 (4-2) | 사람인 `데이터분석`(1658), 데이터분석가(82), 데이터 사이언티스트(2248) |
| 서비스기획 업무 안의 데이터분석 | 결과물이 기능 요구사항·화면 정의면 서비스기획, 분석 보고서·인사이트면 데이터분석. 지표 정의·A/B 테스트처럼 서비스기획과 데이터분석 정의에 모두 걸리면 `공통` (공통 기준 1) | 사용자 행동 분석 결과를 근거로 기능 요구사항·화면 정의 작성 → 서비스기획 / 성능 지표 정의·모니터링, A/B 테스트 설계·해석 → `공통` |
| 경영기획 업무 안의 데이터분석 | 결과물이 경영기획의 핵심 결과물이면 경영기획, 아니면 `공통` | 경영 실적을 분석해 전사 KPI와 경영계획 수립 |
| 개발 업무 안의 데이터분석 | 결과물이 개발의 핵심 결과물이면 개발, 아니면 `공통` | 시스템 로그를 분석해 오류 원인을 찾고 코드 수정 |

업무 항목 안의 "데이터 분석"은 직무명이 아니라 그 항목의 책임과 결과물로 라벨링한다 (5-2).

**공통 판단 일반 예시 (2026-11-05, 이슈 #15):** 위 표의 예와 7장의 샘플 공고 문장은 모두 샘플 6건에서 나온 것이라 AI 프롬프트에 쓰지 않는다. 프롬프트 실험(6-5)에는 아래처럼 샘플과 무관하게 만든 예시만 쓴다. 같은 종류의 업무가 결과물에 따라 직무군 또는 `공통`이 되는 대비 쌍이다.

| # | 업무 문장 | 라벨 | 이유 (결과물 기준) |
|---|---|---|---|
| 1 | 예약 취소율을 매주 확인하고 지표 대시보드를 점검한다 | `공통` | 서비스기획도 데이터분석도 하는 일이고, 결과물이 어느 한 직무군의 핵심 결과물이 아니다 (공통 기준 1) |
| 2 | 취소 사유를 분석해 취소 화면의 안내 흐름과 요구사항 문서를 새로 정의한다 | 서비스기획 | 분석은 수단이고 결과물이 기능 요구사항·화면 정의다 |
| 3 | 고객 구매 이력을 분석해 이탈 예측 모델과 분석 보고서를 만든다 | 데이터분석 | 분석 자체가 결과물이다 |
| 4 | 결제 서버와 주고받는 API 필드 명세를 정리해 개발팀에 전달한다 | `공통` | 요건 전달이 목적이고 구현은 이 업무의 몫이 아니다. 구현까지 맡으면 개발이다 |
| 5 | 결제 모듈의 API를 직접 구현하고 테스트 코드를 작성한다 | 개발 | 동작하는 코드가 결과물이다 |
| 6 | 병원·약국 파트너 담당자와 주 1회 일정을 맞추고 회의록을 공유한다 | `공통` | 조율·문서화는 어느 직무군의 핵심 결과물도 아니다 |
| 7 | 사내 결재 시스템 개편의 일정과 인력 배분을 관리한다 | 프로젝트관리 | 일정·인력 관리가 결과물이다 (운영 업무 표) |

- 분석·문서·조율·요건 전달 업무는 직무군의 정의에 같은 단어가 있다는 이유만으로 그 직무군이 되지 않는다. 그 일 자체가 직무군의 결과물일 때만 직무군이고, 수단이거나 둘 이상이 똑같이 하는 일이면 `공통`이다.

### 3-3. 사람인 소분류 매핑표 (`job_family_map.csv`)

- 별도 매핑 CSV 1개(제작 예정). 직무 게이트의 유일한 CSV다.
- **이 파일은 직무를 최종 판정하는 표가 아니다.** 공고의 업무 항목에서 후보 직무군을 찾고, 그 근거를 추적하게 하는 매핑 데이터다. 최종 판정은 업무 항목의 책임과 결과물로 한다 (2-1, 5-2).
- 한 줄 = 사람인 소분류 하나. 지원 대분류 5개의 소분류 **664개를 모두** 넣는다. `non_job`, `out_of_scope` 행도 빼지 않는다. 행이 없으면 "분류하지 않음"과 "일부러 뺌"을 구분할 수 없기 때문이다. 단, 상품기획·MD 71행은 보류 중이다 (2-3, 2026-10-27). 대분류 단위로 보류한 것이라 행 하나하나를 빼는 것과 다르다.
- **키는 (`job_mid_cd`, `job_cd`) 두 열이다.** 지금 코드표에서는 `job_cd`만으로도 겹치지 않지만, 같은 이름이 여러 대분류에 있으므로 이름이 아니라 두 코드를 함께 키로 쓴다.
- 인코딩: **BOM이 있는 UTF-8**. BOM이 없으면 한국어 Windows 엑셀이 CP949로 읽어 한글이 깨진다.
- 정렬: 대분류는 작성 순서대로 **16(기획·전략) → 2(IT개발·데이터) → 15(디자인) → 8(영업·판매·무역) → 12(상품기획·MD)**. 대분류 안에서는 `job_cd`를 숫자로 오름차순 정렬한다. 새 대분류는 파일 끝에 붙인다.
- 직무군 정의, 문맥 판별 규칙 내용, 인접 관계는 이 파일에 넣지 않는다. 필요한 곳에서 ID로만 가리킨다.

**열 정의 (12개)**

| # | 열 | 필수 | 내용 | 예 |
|---|---|---|---|---|
| 1 | `job_mid_cd` | 필수 | 사람인 대분류 코드 (원본 그대로) | 16 |

`item_type`과 `mapping_status`는 다른 질문에 답한다.

- `item_type`: 이 소분류는 **무엇의 종류**인가?
- `mapping_status`: 직무 게이트에서 이 소분류를 **어떻게 처리**하는가?

그래서 `item_type=직무`이면서 `mapping_status=common`인 행도 있다. 실제 직무 이름이지만 그 소분류만으로는 특정 직무군을 판정할 수 없는 경우다 (예: 시장조사).

**`match_terms` 작성 기준**

`match_terms`는 소분류 이름의 **대체 표기**를 찾기 위한 보조 열이다. 직무군을 확정하는 키워드 목록이 아니다.

1. 공고에서 실제로 쓰일 만한 다른 표기가 있는 행에만 쓴다.
2. `job_name`은 원본 그대로 둔다. `match_terms`는 `job_name`을 대신하지 않고 더해진다.
3. 여러 표기는 `;`로 구분한다.
4. 직무군을 헷갈리게 할 수 있는 모호한 약어는 넣지 않는다 (예: "PM").
5. 직무군 대표 키워드([03-1 문서](job-family-definition.md))와 섞지 않는다. 대표 키워드는 직무군 정의에 속하고, `match_terms`는 소분류 이름의 다른 표현이다.

| 소분류 | `match_terms` | 판단 |
|---|---|---|
| PM(프로젝트매니저) | 프로젝트매니저;프로젝트 매니저 | 뜻이 분명한 표기 변형만 넣는다 |
| 웹기획 | (빈칸) | 원본 이름으로 충분히 찾을 수 있다 |
| 스토리보드 | (빈칸) | 대체 표기보다 문맥 판별 규칙이 중요하다 |
| OKR | (빈칸) | 비직무 항목이라 직무 후보 탐색용 표기가 필요 없다 |

비어 있으면 `job_name`을 탐색 단서로 쓴다. 단서가 검출됐다는 이유만으로 직무군을 확정하지 않는다. 후보가 여러 개이거나 문맥이 모호하면 3-4 문맥 판별과 5-2의 AI 판별로 넘긴다.

**같은 이름의 소분류 (대분류 간 중복 이름 150개, 2-2)**

이름이 같다는 이유만으로 같은 매핑을 자동으로 적용하지 않는다. 각 행의 실제 의미를 판단한 뒤 처리한다.

| 경우 | 처리 |
|---|---|
| 의미가 같다 | 같은 직무군으로 매핑한다. 문맥 판별이 필요하면 같은 `context_rule` ID를 쓴다 |
| 의미가 다르다 | 행마다 따로 판단한다. 한 행은 서비스기획, 다른 행은 UI/UX 디자인으로 매핑할 수 있다 |
| 이름만으로 의미를 구분할 수 없다 | `context`로 두고 3-4에 문맥 판별 규칙을 정의한다. 규칙으로 구분되지 않으면 AI 판별로 넘긴다 |

- 반대로 대분류가 달라도 책임과 결과물이 같으면 같은 직무군으로 매핑할 수 있다.
- 공고 본문에서 이름이 같은 행 여러 개가 함께 검출되고 매핑이 서로 다르면, 그 이름은 후보를 여러 개 낸 것으로 보고 5-2의 4단계(AI 판별)로 넘긴다.

**자동 검증 규칙** (CSV를 만들거나 고칠 때마다 스크립트로 검사한다)

| `mapping_status` | `job_family_id` | `context_rule` | 추가 조건 |
|---|---|---|---|
| `mapped` | 필수 | 빈칸 | 03-1에 있는 직무군 ID |
| `context` | 빈칸 | 필수 | 3-4에 있는 규칙 ID |
| `common` | 빈칸 | 빈칸 | |
| `out_of_scope` | 빈칸 | 빈칸 | |
| `non_job` | 빈칸 | 빈칸 | `item_type`이 `직무`가 아님 |

- (`job_mid_cd`, `job_cd`) 조합이 중복되지 않는다.
- 행이 위 정렬 기준대로 놓여 있다.
- 모든 행의 `job_mid_name`, `job_name`이 사람인 원본 코드표(saramin_job_codes.csv)와 같다. 지원 대분류 5개의 원본 소분류가 빠짐없이 들어 있다.
- `item_type`이 `직무`가 아니면 `mapping_status`는 `non_job`이다.
- 각 열은 허용값만 쓴다 (`item_type`, `mapping_status`, `review_status`).
- `match_terms`는 빈칸을 허용한다. 값이 있으면 `;`로 나눈 각 표기가 비어 있지 않고 중복되지 않는다.

**적용 방법 (5-2의 2단계에서 쓴다)**

1. 업무 항목에 문맥 판별 대상 소분류가 나오면, 같은 항목 안에서 그 규칙 ID의 각 후보 줄에 있는 판별 키워드를 찾는다.
2. 한 후보의 키워드만 나오면 그 후보 직무군이 후보다.
3. 어느 후보의 키워드도 없거나, 두 후보 이상의 키워드가 함께 나오면 AI 판별로 넘긴다.
4. 규칙이 낸 값은 **후보**다. 그 항목의 결과물이 후보 직무군의 정의·핵심 결과물과 맞을 때 라벨로 확정한다. 맞는지 코드로 판단할 수 없으면 AI 판별로 확인한다.

## 4. 인접 직무군 쌍

### 4-1. 인접 판정 조건

- 인접 직무군 쌍은 4-2 표로 미리 정한다.
- **직무명이 인접 쌍에 있다고 자동으로 인접 판정을 주지 않는다.** "AI Product Manager" 공고라도 업무가 일정·리소스 관리나 제품 전략 중심이면 서비스기획과 거리가 있고, 사용자 기능·서비스 흐름 설계 중심이면 서비스기획에 가깝다. 업무 항목을 보고 판정한다.
- **인접 조건:** 아래 두 가지를 모두 만족해야 한다.
  1. 공고의 핵심 직무군과 희망 직무군이 4-2 표에 `사용` 상태로 있다.
  2. 공고 업무 항목 중 **희망 직무군으로 라벨링된 항목이 1개 이상** 있다. `공통` 라벨 항목은 세지 않는다.
- 1은 맞는데 2가 없으면 **불일치**로 둔다.
- 인접 쌍은 방향을 두지 않는다. A↔B가 있으면 B↔A도 같다.
- **겹치는 업무는 구체적이어야 한다.** 4-2 표의 겹치는 업무에는 공통 업무(문서 작성, 커뮤니케이션 등)를 적지 않는다. 공통 업무가 겹친다는 이유만으로 인접 쌍을 만들지 않는다.

### 4-2. 인접 직무군 쌍 (이 문서에서 관리)

- 쌍이 몇 개 안 되고 거의 고정이므로 CSV를 따로 두지 않는다. 아래 표가 원본이고, 코드는 `사용` 쌍의 직무군 ID 두 개와 겹치는 업무만 설정값으로 읽는다. 겹치는 업무는 AI 판별의 참고 정보다.
- 쌍이 10개를 넘거나 여러 직무군 조합을 반복 검증하게 되면 `adjacent_pairs.csv`로 옮긴다 (0장).
- 상태: `사용` / `보류` / `제외`. 판정은 `사용`만 쓴다. `보류`·`제외`는 왜 쌍으로 보지 않았는지 남기려고 적는다.

| 서비스기획 | 디자인(UI/UX) | 와이어프레임, 사용자 흐름, 프로토타이핑 | 사용 | 2-3에서 디자인을 범위에 넣은 이유와 이어짐 |
| 서비스기획 | 데이터분석 | 지표 정의, A/B 테스트 | 보류 | 데이터 분석은 공통 업무라 겹치는 업무로 쓰기 어려움. 03-1에 `JF_DATA_ANALYSIS`를 추가한 뒤에도 보류를 유지한다 (2026-10-26). 그래서 서비스기획 희망 사용자에게 데이터분석 공고는 불일치다 |
| 서비스기획 | 사업개발 | 신규 서비스 기획 | 보류 | "사업기획"처럼 헷갈리는 경우는 문맥 판별 규칙으로 처리 |
| 서비스기획 | 상품기획·MD | 기획MD, 온라인MD | 보류 | 결과물이 상품 구성·판매 전략이라 겹침이 약함 |
| 서비스기획 | 개발 | (공통 업무만 겹침: API 요건 전달) | 제외 | 2번 공고가 대표적인 불일치 사례 |
| 서비스기획 | 경영기획 | (공통 업무만 겹침: 문서 작성, 시장 조사) | 제외 | 6번 공고가 대표적인 불일치 사례 |

**개발 기준 쌍 (2026-10-26 추가)**

| 직무군 A | 직무군 B | 겹치는 업무 | 상태 | 판단근거 |
|---|---|---|---|---|
| 개발 | QA | 테스트 코드 작성, 테스트 자동화, 결함 재현·수정 확인 | 사용 | 03-1 2-9: 결과물이 테스트 코드면 개발, 테스트 케이스·결함 보고서면 QA. NCS가 테스트 수행을 개발 세분류에 둔 점. QA 공고에 "테스트 코드" 항목이 있으면 개발 항목으로 라벨링되어 인접 조건(4-1)을 만족한다 |

- 이 쌍은 희망 직무가 개발 또는 QA일 때만 쓰인다. 희망 직무가 서비스기획이면 QA 공고는 불일치다.

희망 직무가 서비스기획이 아닐 때 쓸 나머지 쌍(경영기획↔사업개발, 개발↔데이터분석, 영업↔상품기획·MD)은 해당 희망 직무를 지원할 때 추가한다. 개발↔데이터분석은 데이터엔지니어와 데이터 사이언티스트의 경계에서 겹치는 업무가 구체적인지 확인한 뒤 정한다.

## 5. 판정 절차

### 5-1. 전체 순서

키워드 매칭 개수는 업무의 중요도를 뜻하지 않는다. 분류표에 등록된 키워드 수에 따라 결과가 흔들리고, 5번 공고의 "에이전트"(원단 대리점)처럼 같은 단어가 다른 뜻으로 쓰인다. 그래서 **키워드는 후보를 찾는 단서로만 쓰고, 판정은 업무 항목 단위로 한다.**

**입력:** 직무명, 주요 업무 항목, 사람인 대분류(있으면). 자격요건의 기술 요구(Python 등)는 판정에 쓰지 않는다.

| 순서 | 단계 | 결과 |
|---|---|---|
| 0 | **업무 항목 정리** (5-2의 1단계) | 정리된 업무 항목 목록 |
| 1 | **범위 외 확인:** 아래 네 조건을 **모두** 만족하면 범위 외로 끝낸다 ① 사람인 대분류가 지원 범위 밖이거나 대분류 정보가 없다 ② 직무명에 지원 직무군의 후보 탐색 단서가 없다 ③ 모든 업무 항목에 지원 직무군의 후보 탐색 단서가 없다 ④ **범위외 근거가 있다:** 사람인 대분류가 지원 범위 밖으로 확인됐거나, 업무 항목의 절반 이상에 범위외 근거가 있다 | **범위 외** 또는 다음 단계 |
| 2 | **정보 충분성:** 정리된 업무 항목이 최소 개수(5-3) 미만이면 끝낸다 | **검토 필요** (`정보 부족`) 또는 다음 단계 |
| 3 | **업무 항목 라벨링** (5-2의 2단계) | 항목별 라벨 |
| 4 | **핵심 직무군 결정:** ① `공통`을 뺀 항목 수를 분모로 한다 ② 분모가 0이면 **검토 필요** (`핵심 업무 없음`) ③ 한 라벨이 과반이면 그 라벨이 핵심 직무군이다. 과반 라벨이 `범위외`면 **범위 외** ④ 과반이 없으면 **검토 필요** (`혼합 직무`) | 핵심 직무군 또는 판정 종료 |
| 5 | **직무명·대분류 대조** (5-3): 업무 판정이 명확하면 차이를 경고로만 남기고, 명확하지 않으면 **검토 필요** (`직무명-업무 충돌`) | 경고 또는 판정 종료 |
| 6 | **희망 직무와 비교:** 핵심 직무군 = 희망 직무군 → **일치** / 4-1 인접 조건 충족 → **인접** / 그 외 → **불일치** | 최종 판정 결과 |

- 1단계를 2단계보다 먼저 하는 이유: 범위 밖이 명확한 공고(예: 업무 한 줄짜리 간호사 공고)를 검토 필요로 올리지 않기 위해서다. 단, 범위 외는 **네 조건을 모두** 만족할 때만 확정한다. 대분류만 범위 밖이고 업무나 직무명에 지원 직무군 단서가 하나라도 있으면 다음 단계로 넘어간다.
- **지원 직무군 단서가 없다는 사실만으로는 범위 외로 확정하지 않는다 (④, 2026-10-28).** 범위 외는 근거가 있을 때만 붙인다는 2-3의 원칙이다. 원티드 개발셋에서 대분류가 없는 공고 중 개발·영업·상품기획·MD 공고 6건이 키워드가 없다는 이유만으로 범위 외가 되었다. 근거도 단서도 없는 공고는 3단계로 가서 항목 라벨이 정한다. 범위 밖 항목이 과반이면 4단계에서 범위 외가 된다.
- **범위외 근거:** 항목 원문에 매핑표 `out_of_scope` 행(`approved`)의 소분류 이름(`job_name`, `match_terms`) 또는 3-4 문맥 판별 규칙의 `범위외` 후보 판별 키워드가 하나라도 있으면 그 항목에 범위외 근거가 있다. 일치는 5-2 1단계와 같이 단어 시작 경계를 지킨다.
- **후보 탐색 단서의 범위 (②③, 2026-11-03).** 직무군이 정해진 단서(대표 키워드, `mapped` 행)뿐 아니라, 지원 직무군을 후보로 가진 문맥 판별 대상 소분류(`context` 행)와 미확정 행이 나온 것도 단서로 센다. 문맥 판별이 아직 후보를 정하지 못했을 뿐 지원 직무군일 수 있기 때문이다. 이런 공고는 범위 외로 확정하지 않고 다음 단계로 간다. 예: 직무명 "사업기획"(`CTX_BIZ_PLANNING`)에 업무 "마케팅기획"이면 1단계에서 끝내지 않는다. 후보가 `범위외`·`공통`뿐인 문맥 규칙의 소분류는 단서가 아니다.
- 판정이 어느 단계에서 끝나도, 그때까지 만든 업무 항목 라벨과 핵심 직무군(있으면)은 결과에 남긴다 (5-4).

### 5-2. 업무 항목 정리와 라벨링

**1단계: 업무 항목 정리**

| 규칙 | 내용 | 예 |
|---|---|---|
| 기본 단위 | 원문 업무 항목 1개 = 1개. 굵은 소제목 아래 "/"로 이어진 업무는 소제목 1개 = 1개 | 1번 공고: 소제목 4개 = 4개 |
| 회사 소개·포지션 설명 제외 | 회사·사업 소개 문장과 포지션 설명 문장은 업무 항목에서 뺀다. 입력에서는 `exclude`를 붙인 항목으로 받고, 항목으로 세지 않으며, AI에는 참고 문맥으로만 준다 (아래 표) | 5번 첫 줄 "MFI는 이태리 원단을 수입 및 유통 판매합니다" |
| **하위 업무 분리** | 한 항목에 **서로 다른 직무군의 책임**이 병렬로 적혀 있으면 하위 업무로 나눈다 | "서비스 요구사항을 정의하고, Python으로 에이전트를 구현한다" → ① 요구사항 정의 ② 에이전트 구현 |
| 분리하지 않는 경우 | 같은 직무군 안의 여러 업무는 나누지 않는다 | 1번 "에이전트 기획 & 설계" 아래 5개 업무는 모두 서비스기획이라 1개 |
| 분리할 수 없는 경우 | 한 책임 안에 두 직무군 성격이 섞여 나눌 수 없으면 라벨을 `혼합`으로 둔다 | "프롬프트를 설계하고 직접 튜닝 코드까지 작성" 같은 문장 |

- 하위 업무 분리는 게이트 라벨링 안에서만 쓴다. 개선안의 "직무 연결 비율" 분모는 원문 업무 항목 수를 유지한다.

**목록형 공고의 항목 정리 (원티드 등, 2026-10-28 추가)**

주요 업무가 구역 제목·번호 소제목·글머리표(`•`, `-`, `■` 등)로 계층을 이루는 공고에 쓴다. 기본 단위 규칙(소제목 1개 = 1개)을 계층 구조로 넓힌 것이다. 구현 시 업무 항목 정리 로직에 반영한다.

| 규칙 | 내용 | 예 |
|---|---|---|
| 소제목 + 목록 = 항목 1개 | 아래에 글머리표 줄만 있는 소제목은 그 목록과 합쳐 항목 1개다. 목록 한 줄은 하위 업무 1개다 | "1. 기존 서비스 고도화 기획" + `•` 3줄 = 항목 1개, 하위 업무 3개 |
| 소제목 없는 목록 | 소제목 아래에 있지 않은 글머리표 줄은 한 줄이 항목 1개다 | `•`만 있는 공고 |
| 구역 제목 | 아래에 다시 소제목이 있는 제목은 항목이 아니다. 그 소제목들이 항목이 된다 | "[메인 업무]" 아래 "1. …", "2. …" |
| 안내 제목 | "주요 업무", "역할", "하게 되나요", "함께 합니다"처럼 내용이 아니라 안내인 제목은 항목이 아니다. 그 아래 목록 한 줄이 항목 1개다. 전체 업무를 감싸는 제목 하나뿐이면 같게 본다 | "■ 다음 도전들을 우리와 함께 합니다." + `•` 7줄 = 항목 7개 |
| 소개 문장 제외 | 첫 글머리표·소제목 앞의 문장, "소개합니다", "이렇게 일합니다", "찾습니다" 같은 소개 구역은 뺀다 | "이 직무는 … 역할입니다." |
| 업무가 아닌 구역 제외 | 기대역량, 전형 절차, "얻을 수 있는 것", "기대하는 결과", "하지 않아요", "Tech Stack" 제목 이후는 뺀다 (자격요건·채용 안내·기술 목록). 제목은 한 줄 전체가 그 말일 때만 센다. "개발팀 기술 스택 선정"처럼 업무 문장 속에 나오면 제외하지 않는다 | "[기대역량]", "● 전형 절차", "[Tech Stack]" |
| 링크 제외 | URL이 있는 줄과, 그 링크를 소개하는 바로 앞의 짧은 줄은 뺀다 | "당사 운영 채널/서비스" + 링크 5줄 |
| 문장만 있는 공고 | 글머리표 없이 문장만 있으면 한 줄이 항목 1개다 | 한국해양기상기술 4줄 = 4개 |

**2단계: 업무 항목 라벨링**

항목마다 아래 중 하나를 붙인다.

| 라벨 | 조건 |
|---|---|
| 직무군 ID | 항목의 결과물이 그 직무군의 정의·핵심 결과물과 맞는다 |
| `공통` | 항목이 공통 업무다 (3-2 공통 업무 기준) |
| `범위외` | 항목이 지원 범위에 없는 직무의 업무다 |
| `혼합` | 1단계에서 분리할 수 없었던 항목 |

**판단 단위:** 라벨과 집계는 항목 단위다. 키워드 탐색과 공통 확인은 한 단계 아래인 **하위 업무** 단위로 한다. 하위 업무는 항목 안에서 `/`로 이어진 업무 또는 문장 하나다. 한 문장은 하위 업무 1개다 (5번 "시장조사 및 분석하여 … 거래처를 발굴"은 1개).

- **문장을 나누는 위치 (2026-11-03).** 한글 음절이나 닫는 괄호(`)`, `]`) 바로 뒤의 마침표와 공백에서 나눈다. 숫자 뒤의 마침표("1. 기획"), 영문 약어("Ph.D."), 공백 없는 마침표("Node.js", "v1.5")에서는 나누지 않는다. 예: "PRD 작성. GUI 디자인." → 하위 업무 2개. 이전에는 `다요함음`으로 끝난 문장만 나눠서 명사로 끝난 문장이 합쳐졌다.

라벨을 고르는 순서 (하위 업무마다):

1. **후보 탐색:** 코드로 매핑표(`approved` 행)의 소분류 이름(`job_name`과 `match_terms`)과 직무군 대표 키워드([03-1 문서](job-family-definition.md))를 찾아 후보를 낸다. 하위 업무와 키워드 모두 공백을 지우고 비교한다 ("경영 계획"과 "경영계획"을 같게 본다). 단, **일치는 원문 단어의 시작에서 시작해야 한다** (공백이나 문장부호 바로 뒤, 또는 문장 처음). 공백을 지우면 두 단어에 걸쳐 우연히 생기는 일치를 막기 위해서다 ("운영 업무" → "운영업무"의 "영업", 2026-10-28). 단어 끝은 조사·어미가 붙으므로 따지지 않는다.
2. **문맥 판별:** 문맥 판별 대상 소분류가 나오면 `context_rule`의 규칙을 적용한다 (3-4 적용 방법).
3. **공통 단서 확인 (후보 탐색 뒤):** 하위 업무에 공통 단서(3-2 표, 매핑표 `common` 행)가 하나라도 있으면 후보 수와 관계없이 4로 보낸다. **공통 단서만으로 `공통`을 확정하지 않는다.** 공통 단서가 없고 후보가 하나이며 같은 하위 업무에 다른 직무군의 대표 키워드가 없으면 그 후보로 라벨을 붙인다.
4. **AI 판별:** 후보가 없거나, 둘 이상이거나, 미확정 행이 관여하거나, 공통 단서가 있으면 **정해진 라벨 목록 안에서만 고르게 하는 AI 호출**을 한다. 결과 캐시로 같은 입력에 같은 결과를 보장한다. 호출·응답·실패·기록의 계약은 아래 "AI 판별의 계약"이다. 라벨 목록은 후보 직무군 ID / `공통` / `범위외` / `혼합`이다. **판단 순서는 공통 기준(3-2)이 먼저다 (2026-11-05).** 하위 업무가 지원 직무군 둘 이상의 정의에 같은 업무로 나오거나 결과물이 특정 직무군의 핵심 결과물이 아니면 `공통`이다. 한 직무군의 정의에 나온다는 이유만으로 그 직무군으로 정하지 않는다. 공통이 아닐 때에만 "이 하위 업무의 결과물이 직무군의 핵심 결과물인가"로 직무군을 고른다. 직무군 이름이 "서비스 기획에 반영"처럼 대상으로만 나오면 그 직무군의 업무가 아니다.
5. **항목 라벨 정하기:** 아래 규칙으로 하위 업무 라벨을 항목 라벨로 올린다.

| AI에 주는 것 | AI에 주지 않는 것 |
|---|---|
| 해당 하위 업무와 그 항목 전체 / 같은 "주요 업무"의 나머지 항목 원문 / 포지션 설명·회사 소개 문장(`exclude` 항목, 항목으로 세지 않고 참고 문맥으로만 줌) / 후보 직무군의 정의·핵심 결과물 / 공통 업무 기준(3-2) | 채용공고명·모집부문(직무명), 사람인 대분류, 자격요건·우대사항, 다른 항목의 라벨 |

- 직무명과 대분류를 주지 않는 이유: AI가 직무명에 맞춰 항목을 읽으면 `직무명 차이` 경고(7-6)와 5-1의 5단계 대조가 의미를 잃는다 (2-2).
- 다른 항목의 라벨을 주지 않는 이유: 핵심 직무군을 라벨로 정하는데 라벨을 핵심 직무군으로 정하면 순환한다. 다른 항목은 원문 텍스트만 준다.
- 자격요건·우대사항은 5-1의 입력이 아니다.
- **포지션 설명·회사 소개는 `exclude` 항목으로 받는다 (2026-11-05).** 5-1의 입력(직무명, 주요 업무 항목, 사람인 대분류)에 칸을 늘리지 않고, 업무 항목이 아닌 설명 문장은 항목에 `exclude`를 붙여 둔다. 코드는 이 항목들을 업무 항목에서 빼서(항목 수, 라벨, 집계에 쓰지 않는다) AI 요청의 `context_items`로만 준다. 모집부문(`position`)은 직무명과 같은 취급이라 포지션 설명이 아니며 줄 수 없다. 샘플 6건에서 이런 문장은 5번의 회사 소개 한 줄뿐이고 포지션 설명이 든 샘플은 없다. 이 줄은 정책의 표와 구현이 어긋나 있던 것(PR 리뷰 P1)을 맞춘 것이다.

**AI 판별의 계약 (2026-11-05, 이슈 #12).** 위 4단계의 AI 호출을 실제 모델로 하는 방법이다. 규칙으로 정하는 것과 AI가 정하는 것을 섞지 않는다.

- **호출 단위.** 하위 업무 1개당 호출 1회다. 항목 단위 호출은 "공통이 아닌 하위 업무가 정확히 절반"일 때만 생긴다. 공고당 1회로 묶는 것은 이번에 정하지 않고, 개별 호출과 결과를 비교한 뒤 따로 정한다.
- **요청.** 입력은 위 표의 "AI에 주는 것"뿐이다. 후보 직무군의 정의·핵심 결과물은 코드의 직무군 정의에서 실행할 때 채우고 프롬프트에 복사해 두지 않는다(정의가 두 곳이 되지 않게). **공고 문장은 외부에서 온 입력이다.** 판단 규칙, 허용 라벨, 직무군 정의(코드가 채운, 믿을 수 있는 글)는 **시스템 지시**로, 공고 문장은 **별도 메시지**에 구분자로 감싸 비신뢰 데이터로 보내고, 그 안의 지시문은 따르지 않게 한다. 공고 안의 구분자 표시는 무력화한다. **이것은 주입의 영향을 줄이는 완화이지 방어가 아니다.** 모델이 공고 안의 지시문을 실제로 따르지 않는지는 오프라인 테스트로 확인할 수 없다. 최종 방어선은 코드다: 라벨은 허용 목록 안에서만 받고 판정은 코드가 한다. 다만 허용 목록 안의 다른 라벨로 유도하는 것은 막지 못한다. 지원자 정보는 어떤 경우에도 넣지 않는다 ([자격요건 평가 문서](eligibility.md) 16장). 외부로 나가는 것은 공고 정보뿐이다.
- **응답.** `{"label": 문자열, "reason": 문자열}`이다. `label`은 라벨 목록(후보 직무군 ID / `공통` / `범위외` / `혼합`) 안에서만 고르고, 목록에 있는지는 **코드가 검증한다.** 목록에 없는 라벨, `reason`이 없거나 공백뿐인 응답, 형식이 틀린 응답은 성공 응답이 아니다. **다시 묻지 않고** 그 호출의 실패로 처리한다. `reason`은 판정에 쓰지 않는다. 응답을 받을 때 제어문자를 지우고, 개행·연속 공백을 한 칸으로 합치고, 200자와 600바이트(UTF-8) 중 먼저 닿는 쪽까지만 둔다(캐시에 들어가기 전에 한다). 요청에 든 공고 문장이 30자 이상 그대로 들어 있으면 기록에 남기기 전에 고정 문구(`공고 문장을 그대로 옮겨 기록하지 않음`)로 바꾼다. 저장되는 곳은 5-4의 AI 판별 기록(하위 업무의 `ai_reason`과 `ai_log`)과 결과 캐시뿐이다. 사용량 기록과 화면에는 없고, 파이프라인 저장 결과는 게이트 `detail`을 비우므로 거기에도 남지 않는다.
- **AI가 정하지 않는 것.** AI는 하위 업무의 라벨만 고른다. 항목 라벨, 핵심 직무군, 최종 판정, 사유 코드, 경고 코드, 순위 그룹은 코드가 정한다. 점수 계산과 자격요건 판정은 AI에 맡기지 않는다.
- **호출 실패.** 실패한 하위 업무를 임의의 라벨(`공통`, `혼합` 등)로 채우지 않는다. 그 공고의 게이트 판정은 만들지 않고 호출 실패로 남긴다. 평가 도구는 이를 `AI 실패`로 따로 세어 원인 범주 이름만 보고하고, 판정 지표는 **전체 공고를 분모로 한 값과 호출이 끝난 공고만 분모로 한 값을 둘 다** 적는다. 일시 오류(서버 오류, 네트워크, 분당 제한)만 제한된 횟수로 재시도하고, 일일 한도나 quota 소진은 재시도 없이 남은 공고를 시작하지 않고 멈춘다. 일시 제한인지 구별할 수 없으면 소진으로 본다. 자동으로 다른 모델로 바꿔 다시 부르지 않는다.
- **캐시와 호출 기록.** 요청에 프로필이 없으므로 결과를 디스크에 캐시한다. 키는 모델 ID, 프롬프트 버전, 시스템 지시와 프롬프트, 생성 설정의 해시다. 캐시에는 공고 원문이나 프롬프트가 아니라 모델 응답의 `label`과 정리된 `reason`이 저장된다. 사용량 기록에는 **호출 식별자** `{공고 id}:item:{항목 번호}:subtask:{하위 업무 번호}`(항목 단위 호출은 `{공고 id}:item:{항목 번호}`, 번호는 0부터), 단계 이름, 모델, 프롬프트 버전, 캐시 여부, 성공 또는 실패 범주, 토큰 수만 남기고 **공고 원문, 프롬프트, `reason`은 쓰지 않는다.**
- **호출 예산 (2026-11-05 개정).** 실행 전에 같은 입력을 mock으로 돌려 **mock 예상 논리 호출 수**를 세지만, **이것은 상한이 아니다.** 하위 업무 호출은 규칙이 정하므로 AI 라벨과 무관하지만, 항목 단위 호출은 AI가 고른 라벨에 따라 생기기 때문이다("공통이 아닌 하위 업무가 정확히 절반"). 그래서 규칙이 정한 구조에서 **최대 논리 호출 수**를 따로 계산한다: 하위 업무 호출 수에, 항목마다 "하위 업무 수 n이 짝수이고 규칙이 확정한 하위 업무 수 r이 n/2 이하이며 n/2가 r과 r + AI가 부른 하위 업무 수 사이에 있는" 항목 수를 더한다(그런 항목은 AI 답에 따라 항목 단위 호출이 생길 수 있다). 실제로는 재시도가 있어 한 논리 호출이 최대 (1 + 재시도 상한) 번 시도되고 실패한 시도도 한도에 센다. 그래서 **최대 시도 수 = 최대 논리 호출 수 × (1 + 재시도 상한)** 이 오늘 남은 한도(이미 쓴 호출 포함)를 넘으면 시작하기 전에 멈춘다. 네 숫자(mock 예상 논리 호출, 최대 논리 호출, 최대 시도, 오늘 이미 쓴 호출)를 모두 보고하고, 실행이 끝나면 실제 논리 호출과 실제 시도를 더해 적는다. 샘플 6건은 mock 예상 20회, 최대 논리 21회(1번 공고 항목 4), 재시도 상한 3회일 때 최대 시도 84회다. 첫 실제 실행에서 논리 호출이 21회였으므로 mock 예상(20회)은 실제를 덮지 못했다.
- **모델.** 정확한 모델 ID를 지정한다(`latest`·preview 별칭, 폐지된 모델 금지). 기본은 `gemini-3.1-flash-lite`다. 같은 키와 일일 한도를 자격요건 평가와 나눠 쓴다.

**항목 라벨 규칙 (하위 업무 → 항목)**

| 상황 | 항목 라벨 |

### 5-3. 기준값 (초기값)

검증(6장) 결과를 보고 조정한다.

| 항목 | 초기값 | 이유 |
|---|---|---|
| 정보 부족 기준 | 정리된 업무 항목 **2개** 미만 | 실제 공고는 업무가 2~3줄인 경우가 많다. 3으로 하면 4번·5번 공고가 검토 필요가 된다 |

| 대분류 정보가 없는 공고 | 대분류 대조를 건너뛴다. 1단계 범위 외 확인에서 조건 ①은 "범위 밖"과 같게 보되, 조건 ④는 업무 항목의 범위외 근거로만 판단한다 | 샘플 공고는 텍스트만 있고 사람인 대분류가 없다 |

- 정보 부족 기준은 3개 이상으로 올리면 정답이 `일치`인 서비스기획 공고가 검토 필요가 된다 (아래 6-4). 1개와 2개는 개발셋에서 구별되지 않아, 처음 정한 이유(실제 공고는 업무가 2~3줄인 경우가 많다)대로 2를 유지한다.
- 명확성 기준은 0.50부터 1.00까지 어떤 값에서도 결과가 같다. 직무명이 다른 직무군을 가리키면서 5-3이 적용되는 개발셋 공고가 없기 때문이다.
- **개발셋은 이 기준값들을 거의 시험하지 못한다.** 항목이 1개인 공고, 직무명과 업무가 충돌하는 공고, 과반 경계(동수)인 공고가 없고, 정답에 인접·검토 필요가 0건이다. 그래서 위 값은 여전히 초기값이다. 6-1의 빠진 유형(직무명과 업무가 다른 공고, 인접 직무, 정보 부족)을 모은 뒤 다시 조정한다.
- 기준값의 경계 동작은 `tests/test_job_gate_sample.py`의 `test_threshold_boundaries`가 고정한다. 값을 바꾸면 그 테스트도 같이 고친다.

#### 핵심 근거를 만드는 규칙 (코드)

`핵심 근거`(`detail.evidence`)는 코드가 아래 규칙으로 만든다. LLM이 쓰지 않는다. 인용은 **하위 업무 원문 전체**다. 단서 문구가 아니다. 단서는 정규화한 글자(대소문자·공백)로 찾아서 원문 위치를 모르고, 하위 업무 원문은 항상 항목 `heading` 또는 `text`의 부분 문자열이라 인용 검사(data-contract 1-5)를 반드시 통과한다.

| 판정이 끝난 곳 | `supporting` | `conflicting` |
|---|---|---|
| `일치`, `인접`, `불일치` | 라벨이 핵심 직무군인 항목마다 1개 | 라벨이 핵심 직무군이 아닌 직무군(`JF_*`)인 항목마다 1개 |
| `범위 외` (4단계) | 라벨이 `범위외`인 항목마다 1개 | 없음 |
| `범위 외` (1단계), `검토 필요` | 없음 | 없음 |

- **한 항목에서 인용은 1개다.** 그 항목의 라벨(`supporting`이면 핵심 직무군 또는 `범위외`, `conflicting`이면 그 항목의 직무군)이 후보로 잡힌 첫 하위 업무를 인용하고, 없으면(AI가 정한 경우 등) 그 항목의 첫 하위 업무를 인용한다. 항목 순서는 `index` 오름차순이다.
- `공통`·`혼합` 라벨 항목은 인용하지 않는다. 공통을 뺀 비율(`core_ratio`)이 그 판단을 담는다.
- `decided_by`는 인용한 하위 업무의 라벨을 규칙이 정했으면 `rule`, AI가 정했으면 `ai`다.
- **`missing`은 검토 필요일 때 사유 코드마다 고정 문구 하나를 쓴다.** 그 밖의 판정은 비어 있다.

| 사유 | `missing` 문구 |
|---|---|
| 정보 부족 | `업무 항목 {n}개 < 최소 {min_items}개` |
| 핵심 업무 없음 | `공통을 뺀 업무 항목 0개` |
| 혼합 직무 | `가장 많은 라벨 {top_n}/{total}이 과반이 아님` (가장 많은 라벨이 `혼합`이면 `가장 많은 라벨이 혼합`) |
| 직무명-업무 충돌 | `직무명은 {직무명 직무군}, 업무 핵심은 {핵심 직무군}({count}/{total}), 명확성 기준 {clear_ratio} 미만` |

## 6. 검증

### 6-1. 검증 데이터

- 샘플 6건은 구분이 쉬운 공고가 많아 분류 성능을 평가하기에 부족하다. 인접·검토 필요·범위 외 사례도 없다.
- 지원 범위 대분류의 공고 **20~30건의 제목과 담당 업무**를 추가로 모은다. 다음 유형을 골고루 넣는다.
  - 같은 직무, 다른 직무
  - 인접 직무: PM 공고, UX 디자이너 공고 (4-2 표의 `사용` 쌍)
  - 혼합 직무: 기획+데이터 분석, 기획+개발. 한 항목 안에 두 직무가 섞인 공고 (5-2 하위 업무 분리)
  - 정보 부족: 업무 설명이 짧은 공고
  - 범위 밖 대분류 공고: 업무가 짧은 것과 지원 직무군 단서가 있는 것 (5-1의 1단계)
  - 직무명과 업무가 다른 공고 (5-3 명확성 기준)
  - 문맥 판별 대상이 나오는 공고: 스토리보드, 사업기획 등
- 동일 공고 중복을 먼저 정리한다.

### 6-2. 기준 판정(정답) 만들기

- 문서 작성자가 공고마다 직무 판정과 근거를 먼저 적는다. 그다음 에이전트 판정과 비교한다. 엇갈린 공고를 보며 정의·공통 업무·키워드·문맥 판별 규칙을 고친다.
- **직무 판정 정답과 자격요건 정답을 따로 기록한다.** 그래야 오류가 게이트에서 났는지 후속 평가에서 났는지 구분할 수 있다.
- 정답을 정하기 어려운 공고는 임의로 정하지 않고 보류 목록에 남긴다.

### 6-3. 검증 지표

| 지표 | 확인하는 것 |
|---|---|

### 6-5. 실제 AI 실행 기록 (2026-11-05, 이슈 #12)

실제 모델을 쓴 실행의 기록 방법이다. 6-4의 mock 기록과 섞지 않고, 실행마다 따로 적는다.

- **범위(최소 시연 기준).** 샘플 6건(7-1)만 실제 AI로 돈다. 논리 호출은 mock 기준 20회(공고별 9, 3, 2, 1, 2, 3)다. 개발셋(mock 기준 197회)과 확인셋(181회)의 실제 AI 평가는 후속이다. 그때는 확인셋을 한 번만 재고, 그 결과를 보고 규칙·기준값·정답·프롬프트를 고치지 않는다(6-4와 같은 원칙).
- **실행의 구분.** 필수 실행 1회와, 필수 실행이 끝난 뒤에만 하는 선택 재현성 확인 1회를 따로 기록한다. 합산하지 않고, 선택 실행을 필수 실행의 결과로 바꾸지 않는다. 시도 수 상한은 필수 84, 선택 84, 합쳐 168이다(처음에는 mock 예상 20회 기준 80으로 정했으나 최대 논리 호출이 21회라 84로 고쳤다).
- **샘플 6건 비교.** `정답지(fixture) == 기대표(7-1) == 실제 AI 실행 결과`인지 본다. 비교 항목은 항목별 라벨, 핵심 직무군, 최종 판정, 사유 코드와 경고 코드(7-1: 6건 모두 경고 없음), 논리 호출 수·시도 수·토큰이다. 1번 공고의 게이트는 `일치`이고 자격요건은 별도로 `미충족`이어서 두 판단이 섞이지 않는지도 본다.
- **기록할 것(숫자와 코드만).** 날짜, 셋, 모드(`ai`), 모델 ID, 프롬프트 버전, 생성 설정, 캐시 모드, 논리 호출 수·최대 시도 수·실제 시도 수·토큰, AI 실패 수, 판정·항목 라벨·핵심 직무군 일치(전체 분모와 완료한 공고만 분모), AI 호출 비중, 규칙 확정 라벨 오답 수. 공고 원문, 프롬프트, 모델이 쓴 `reason`은 적지 않는다.
- **기대표와 다를 때.** 정답지, 기대표, 정책을 실제 AI의 결과에 맞춰 고치지 않는다. 불일치마다 원인 범주를 하나 적는다.

| 범주 | 뜻 |
|---|---|
| AI 판단 오류 | AI가 호출된 하위 업무에서 기대와 다른 라벨을 골랐다 |
| 규칙 확정 오류 | 규칙이 확정한(`source=rule`) 라벨이 기대와 다르다 |
| 후보 탐색 누락 | 기대 라벨이 AI의 라벨 목록 밖에 있다 (규칙이 후보를 좁힌 것) |
| 호출 실패 | AI 호출이 실패해 라벨이 없다 (`AI 실패`) |
| 정답 불확실 | 7-1이 애매하다고 적은 곳이다 (예: 3번 "결과 검증"은 서비스기획 또는 공통으로 볼 수 있고 판정은 같다). 사람이 판단해 기록한다 |

앞의 네 범주는 평가 도구가 자동으로 나누고, 정답 불확실은 사람이 정한다.

**프롬프트 실험 (2026-11-05, 이슈 #15).** 항목 라벨이 기대표와 다른 원인을 가르려고 프롬프트 변형을 돌릴 때의 규칙이다.

  - **실행 `08275e1a`: 평가에 쓰지 않는다.** 서버 오류(`503` 13회, `504` 3회) 때문에 시도 27회 중 16회가 실패했고, 재시도 3회를 모두 쓰고도 3개 공고(1번, 2번, 3번)가 `AI 호출 실패`로 끝났다. 논리 호출 14회, 토큰 입력 19,770 / 출력 657. 호출이 끝난 3개 공고(4번, 5번, 6번)의 항목 라벨은 9/10이었다. 코드의 문제가 아니라 일시적인 서버 상태였고(같은 날 앞선 실행은 서버 오류 없이 끝났다), 서버가 회복된 4~6번 공고에서는 호출이 성공했다.
  - **실행 `9697949b`: 완료.** 논리 호출 21회, 시도 27회(서버 오류 6회, 재시도로 모두 성공, 최종 실패 0), 토큰 입력 37,100 / 출력 1,238, 이날 이 모델의 누적 호출 103/500. 게이트 판정 6/6, 핵심 직무군 6/6, 사유·경고 6/6(없음), **업무 항목 라벨 20/25**, 공고 전체 일치 2/6. 규칙 확정 오류 0, 후보 탐색 누락 0, 호출 실패 0, `AI 판단 오류` 5.
  - **v1과 비교.** 틀린 항목은 **같은 5곳**(1번 항목 3·4, 2번 항목 6, 3번 항목 5, 6번 항목 2)이다. 개선되지 않았다. 틀린 라벨의 종류만 두 곳에서 바뀌었다(3번 항목 5: 프로젝트관리에서 서비스기획으로, 6번 항목 2: 경영기획에서 데이터분석으로). 두 실행의 숫자 차이를 프롬프트의 효과로 읽지 않는다. 같은 모델의 실행 간 변동과 구분할 수 없다.
  - **관찰(원인 판단 전).** (1) 새로 넣은 "먼저 공통인지 확인" 단계를 모델은 21번 호출 중 3번만 이유에 적었고, 그것도 3-2의 공통 업무 예시에 그대로 있는 업무(API 요건 전달, 커뮤니케이션·협업)에서였다. 둘 이상의 직무군이 함께 하는 일인지 따져 보라는 기준(3-2 공통 기준 1)은 실제로는 적용되지 않았다. (2) 3-2의 공통 업무 예시에 "데이터 분석"이 있는데 직무군 `JF_DATA_ANALYSIS`도 있다. 독립 직무로서의 데이터분석과 다른 직무 안의 데이터분석 업무를 나누는 기준(3-2 "데이터분석 분류 기준")이 프롬프트에 없어서 지표 정의·분석 성격의 업무가 데이터분석으로 갈린 것으로 보인다. 확정은 못 한다. (3) 한 번의 프롬프트 개정이 효과가 없었고, 추가 수정의 근거는 샘플 6건뿐이라 샘플에 맞춘 프롬프트가 될 위험이 있다. 이 구분을 프롬프트에 옮기는 것과 규칙 쪽(공통 단서) 조정은 개발셋 평가와 함께 후속 이슈에서 다룬다.
  - 필수 완료 조건의 "샘플 6건의 항목 라벨 일치"는 두 프롬프트 모두에서 충족되지 않았다. 이 실행으로 정답지, 기대표, 규칙을 고치지 않았다.
- **프롬프트 version 3 (2026-11-05, PR 리뷰 반영).** 위 실행 기록은 모두 version 1과 2 기준이다. version 3은 **라벨 결과를 맞추려는 수정이 아니다.** 정책 5-2와 구현이 어긋나 있던 두 곳을 맞춘 것이다: (1) 포지션 설명·회사 소개 문장을 참고 문맥으로 줌, (2) 판단 규칙과 공고 문장을 시스템 지시와 사용자 메시지로 나눠 보냄. 판단 순서의 내용은 바꾸지 않았다. 정답지, 기대표, 규칙도 그대로다. **version 3은 아직 실제 모델로 실행하지 않았다.** 실행하면 위 기록과 따로 적고 합산하지 않는다. 샘플 6건의 항목 라벨 20/25는 version 2 기준의 의도된 기록이며 코드 결함으로 보지 않는다. 원인 분석과 일반화 검증은 후속 이슈에서 한다.

## 7. 예시

### 7-1. 샘플 공고 6건의 기대 판정 (테스트 케이스)

사용자프로필_샘플채용공고.md 기준. 프로필은 김하늘, 서비스기획 신입 희망, 기획팀 인턴 6개월이다. 샘플 공고에는 사람인 대분류 정보가 없다.

| 번호 | 공고 | 업무 항목 라벨 | 핵심 직무군 | 직무 게이트 (기대) | 자격요건 종합 ([자격요건 평가 문서](eligibility.md) 17장) |
|---|---|---|---|---|---|
| 1 | 팔레트, AI 에이전트 서비스 기획자 | 서비스기획 2, 공통 2 (데이터 분석·개선, 협업) | 서비스기획 (2/2) | **일치** | 필수 요건 미충족 (서비스 기획 경력 0.5년 < 3년) |
| 2 | 피피에스, AI 에이전트 개발자 | 개발 5, 공통 1 (API 명세) | 개발 (5/5) | **불일치** | 필수 요건 미충족 |
| 3 | 이씨이십일알앤씨, AI 에이전트 기획 | 서비스기획 4, 공통 1 (실무팀·AX팀 조율) | 서비스기획 (4/4) | **일치** | 조건부 적합 |
| 4 | 씨케이파트너스, AI 에이전트 개발자 | 개발 2 | 개발 (2/2) | **불일치** | 조건부 적합 |

- 6건 모두 직무명과 핵심 직무군이 같아 경고 코드가 없다.
- 4번과 5번은 정보 부족 기준(2개)에 걸리지 않는다. 기준을 3개로 올리면 둘 다 검토 필요가 된다.
- 3번의 "결과 검증"(구현 결과 확인 후 설계에 재반영)은 서비스기획으로 라벨링했다. 공통으로 보면 3/3이 되지만 판정은 같다.
- 1번의 "데이터 분석 & 개선"은 지표 정의·A/B 테스트가 서비스기획과 데이터분석 정의에 모두 걸려 `공통`이다 (3-2 공통 기준 1). 하위 업무 중 직무군 후보는 "피드백 분석 후 흐름 개선" 하나뿐이라 5-2의 과반 규칙으로도 `공통`이다 (2026-10-27 확인, 기대값 유지).

### 7-2. 이름은 다르지만 같은 직무 → 일치

| | 1번 팔레트 | 3번 이씨이십일알앤씨 |
|---|---|---|
| 직무명 | AI 에이전트 **프로덕트 서비스 기획자** | AI 에이전트 **기획** |
| 핵심 업무 | 워크플로우·예외 처리 정의, AI 응답 화면 표시 방식 기획, 개발팀에 연동 요건 전달 | 입력→결과 순서 구상, 화면 구성안 작성, 화면 동작·예외 처리를 개발 요건 문서로 정리 |
| 결과물 | 기획 문서, 화면·인터랙션 정의, 개발 요건 | 화면 구성안, 개발 요건 문서 |

둘 다 "사용자가 쓰는 화면과 흐름을 설계해서 개발자에게 넘기는 일"이다. → 1차(직무군) **서비스기획**으로 일치. 범위 차이는 적합성 평가에서 설명한다.

### 7-3. 이름은 비슷하지만 다른 직무 → 불일치

| | 1번 팔레트 | 6번 이롬넷 |
|---|---|---|
| 직무명 | 서비스 **기획**자 | 경영**기획** 담당자 |
| 핵심 업무 | 서비스 기능·화면 설계 | 연간·중장기 경영 계획, 전사 KPI 수립, 이사회·주주총회 운영 |
| 결과물 | 기획 문서, 화면 정의 | 경영계획서, KPI 보고서, 이사회 자료 |

둘 다 "기획"이고 사람인 대분류도 같은 **기획·전략**이지만 결과물이 다르다. → **불일치**. 직무명이나 대분류만 보면 걸러지지 않는 대표 사례다.

### 7-4. 같은 키워드, 다른 직무

1, 2, 4, 5번 공고에 모두 "에이전트"가 들어 있다.

| 공고 | 결과물 | 직무군 |
|---|---|---|
| 1번 | 기획 문서, 화면 정의 | 서비스기획 |
| 2번, 4번 | 코드, RAG 파이프라인, 테스트 코드 | 개발 |
| 5번 | 원단 판매 실적, 신규 거래처 | 영업 (여기서 "에이전트"는 AI가 아니라 수입 원단 대리점이라는 뜻) |

키워드만으로는 직무를 정할 수 없다. 키워드 매칭만 하면 5번이 AI 직무로 분류될 수 있다. 그래서 키워드는 후보 탐색 단서로만 쓴다.

### 7-5. 공통 업무가 겹쳐도 핵심이 다르면 다른 직무

- 2번 **개발자** 공고에도 "프롬프트 설계", "API 명세 문서 작성"이 있다. 기획자도 하는 일이다.
- 6번 **경영기획** 공고에도 "데이터 분석"이 있고, 1번 서비스 기획자 공고에도 "데이터 분석 & 개선"이 있다.

이런 업무는 `공통`으로 라벨링하고 핵심 직무군 계산의 분모에서 뺀다. 남은 항목으로 보면 2번의 중심은 구현, 6번의 중심은 경영 계획이다.

### 7-6. 직무명·대분류와 업무가 다른 경우 (가상 사례)

| 공고 | 업무 판정 | 처리 |
|---|---|---|
| 직무명 "AI 에이전트 개발자", 업무 4개 모두 서비스 기능·예외 흐름 정의 | 서비스기획 4/4 (명확) | **일치** + 경고 `직무명 차이` |
| 직무명 "AI 에이전트 개발자", 업무 5개 중 서비스기획 3, 개발 2 | 서비스기획 3/5 (과반이지만 2/3 미만) | **검토 필요** (`직무명-업무 충돌`), 핵심 직무군 서비스기획 보존 |
| IT개발·데이터 대분류, 업무는 요구사항 정의와 사용자 흐름 설계 | 서비스기획 (명확) | **일치** + 경고 `대분류 차이` |
| 개발자가 요구사항 문서도 작성 | 기획 키워드가 검출되지만 결과물은 코드 | 요구사항 문서 작성은 `공통`, 핵심은 개발 |
