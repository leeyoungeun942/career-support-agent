# 자격요건 평가 정책: 요건 해석과 판정 기준

> 관련 문서: [job-gate.md](job-gate.md) (직무 게이트, 직무군 분류), [fit-evaluation.md](fit-evaluation.md) (적합성 평가), [job-family-definition.md](job-family-definition.md) (직무군 ID)
> 데이터 형식: [data-contract.md](../data-contract.md) 2장 (`JobRequirement`, `eligibility_result.v1`). 형식은 이 문서의 규칙을 따른다.
> 바탕 자료: 사전 작업 폴더의 `03_정책문서_자격요건평가.md`(2026-10-22). 규칙 1~8장을 이 문서 4~11장으로 옮기고, 입력·출력·사유 코드·순위·개인정보는 새로 정했다.

자격요건 평가는 공고의 지원 자격을 **요건 하나씩** 지원자 프로필과 비교한다. **모든 공고가 받는다.** 직무 불일치 공고도 받는다.

```
공고 1건 ──▶ [요건 추출] ──▶ 요건 R1, R2, R3 …
                                 │ 요건마다
                                 ▼
             [요건 판정] ──▶ 충족 확인 / 확인 필요 / 미충족 확인
                                 │ 필수 요건만 모아서
                                 ▼
             [종합 판정] ──▶ 적합 / 조건부 적합 / 필수 요건 미충족
```

## 0. 이 문서가 정하는 것

### 0-1. 직무 게이트와의 관계

| 질문 | 담당 |
|---|---|
| 이 공고는 지원자가 희망하는 직무인가? | 직무 게이트 ([job-gate.md](job-gate.md)) |
| 지원자가 이 공고의 자격요건을 충족하는가? | **자격요건 평가 (이 문서)** |

- 두 평가는 서로의 결과를 바꾸지 않는다. 게이트 결과는 **정렬 그룹**(`ranking_group`)만 정한다 (14장).
- 신입/경력 구분은 5장(경력 요건 해석)에서 다룬다. 공고를 먼저 걸러내는 단계로 쓰지 않는다. 경력이 부족해도 직무가 맞는 공고는 "필수 요건 미충족"으로 보여 주는 편이 사용자에게 더 쓸모 있다.

### 0-2. 이미 정한 규칙 (개선안 2-2절)

아래 규칙은 이 문서에서 다시 정하지 않는다. 바꿀 때는 개선안을 고친다.

- 개별 요건 상태 3종: 충족 확인 / 확인 필요 / 미충족 확인
- 요건 유형 4종: `numeric`, `skill`, `qualitative`, `preference`
- 미충족 확인은 `numeric` 요건의 값 비교로만 내린다. `skill`, `qualitative`는 사용자가 "없음"을 명시한 경우에만 내린다.
- 프로필 필드가 비어 있으면 확인 필요로 둔다.
- 경력 연수에 인턴 기간을 포함한다.
- "N년 내외"는 N−1년 이상, "N~M년"은 N년 이상이면 충족이다.
- 종합 판정: 필수 중 미충족 확인이 1개 이상이면 필수 요건 미충족, 확인 필요가 1개 이상이면 조건부 적합, 모두 충족 확인이면 적합

**이 문서의 해석: "numeric 값 비교로만"의 뜻.** `numeric` 요건이라고 해서 기준에 못 미치면 모두 미충족 확인이 되는 것은 아니다. **코드가 기준과 값을 둘 다 확실히 계산할 수 있을 때만** 미충족 확인을 내린다.

- 경력 "3년 이상"에 지원자 경력 6개월: 기준(36개월)과 값(6개월)이 모두 숫자로 확정된다 → 미충족 확인 (`below_threshold`)
- 전공 "컴퓨터공학"에 지원자 "컴퓨터과학": 두 이름이 같은 전공으로 인정되는지 코드가 확정할 수 없다 → 확인 필요 (`scope_unclear`, 7장)

규칙을 바꾼 것이 아니라 규칙이 적용되는 범위를 좁혀 읽은 것이다. 개선안 문구에 이 해석을 넣는 일은 작업 현황에 적는다.

### 0-3. 판단 원칙

> **애매하면 미충족 확인이 아니라 확인 필요로 둔다.**

지원할 수 있는 공고를 "미충족"으로 잘못 내리는 것(거짓 미충족)이 더 큰 손해다. 직무 게이트의 "확신이 없으면 제외하지 않는다"와 같은 원칙이다.

### 0-4. 규칙의 상태

4~12장의 규칙은 문서 작성자와 AI 에이전트가 정한 **초기 규칙**이다. 장마다 검토한 선택지와 채택한 안을 함께 적는다. 검증용 공고를 추가로 판정해 보면서 조정한다.

## 1. 입력과 출력

### 1-1. 입력

| 입력 | 출처 | 쓰는 곳 |
|---|---|---|
| 공고의 요건 목록 `JobRequirement` | 요건 추출 (13장 1단계) | 모든 판정 |
| 요건 추출 상태 `extraction_status`, `extraction_issues[]` | 요건 추출 (13장 1단계) | "필수 요건 없음"의 안전장치 (1-4) |
| 지원자 프로필 | 사용자 입력 | 1-2 표 |
| `job_id`, `ranking_group` | 직무 게이트 결과 ([data-contract.md](../data-contract.md) 1장) | 결과 연결, 14장 정렬. 결과에는 `gate_ranking_group`으로 복사한다 |
| `as_of_month` (`"YYYY-MM"`) | pipeline. 평소에는 오늘이 속한 달 | 11장 기간 계산 |

- **모든 공고를 평가한다.** 게이트 결과는 판정을 바꾸지 않는다. 게이트에서 받는 것은 `job_id`와 `ranking_group`뿐이다.
- 판정 코드는 게이트의 `core_family`를 읽지 않는다. 경력이 어느 직무군이어야 하는지는 요건의 `career_family`가 정한다 (4장). 단, 요건 추출 단계는 "관련 경력"의 `career_family`를 채울 때 `core_family`를 쓴다 (4-1).
- 코드는 오늘 날짜를 직접 읽지 않는다. `as_of_month`를 입력으로 받는다. 그래서 테스트는 고정값을 쓰고, 저장된 결과는 몇 월 기준인지 알 수 있다.

### 1-2. 프로필에서 읽는 칸

경험 칸의 뼈대는 `docs/youngeun/`의 입력 형식 자료(`experiences[]`)를 따랐다. 자격요건 판정에 필요한데 그 자료에 없는 칸은 보충했다. 정식 Profile 계약은 프로필 분석 이슈에서 정한다. 아래 표는 자격요건이 **읽는** 칸이다.

| 칸 | 입력 / 계산 | 쓰는 판정 규칙 |
|---|---|---|
| `education[]`: `degree`, `majors[]`(주전공·복수전공·부전공), `status`, `graduation_month` | 사용자 입력 | 학력 순서(6장), 전공(7장), 졸업 예정(6장) |
| `education[].raw` (선택) | 사용자 입력 | 프로필 원문 한 줄. 예: "OO대학교 영어영문학과 졸업 (2026.02)". 코드가 낸 학력·전공 판정의 **근거 인용**에만 쓴다. 없으면 근거를 비워 둔다 (13장) |
| `experiences[].id` | 코드 부여 | 근거의 `experience_id` |
| `experiences[].title` | 사용자 입력 | 근거 표시. 코드가 낸 경력 판정의 **근거 인용**으로 쓴다 (13장) |
| `experiences[].type`: `intern` / `full_time` / `contract` / `project` / `activity` | 사용자 입력 | 경력 합산 대상 판단 (4장) |
| `experiences[].category` (`JF_*`) | 사용자 입력 또는 분류 | 관련 경력 인정 (4장) |
| `experiences[].period`: `start`, `end` (`"YYYY-MM"`, 진행 중이면 `end=null`) | 사용자 입력 | 경력 기간 (11장) |
| `experiences[].duration_months` | **코드 계산** | 경력 기간 (11장) |
| `experiences[].role`, `actions[]`, `result` | 사용자 입력 | skill·qualitative 근거의 **원문 인용 출처** |
| `experiences[].tools[]` | 사용자 입력 | skill 근거 |
| `skills[]` | 사용자 입력 | 경험에 묶이지 않은 스킬 근거 |
| `skills_denied[]` | 사용자 입력 | "없음" 응답 → `user_denied` (3장). 칸이 비어 있으면 "모름"이다 |
| `certificates[]`, `other_qualifications[]` | 사용자 입력 | 자격증·면허, 그 밖의 요건 (8장) |

- **`Experience.category`에는 직무군 ID(`JF_*`)를 쓴다.** `JF_`로 시작하지 않는 값은 프로필 입력 오류로 거부한다(직무군 데이터가 잘못된 것을 "경력 부족"(`not_met`)으로 바꾸지 않는다). 모르면 `null`이다. 직무 게이트와 자격요건 평가가 같은 직무군 분류표를 공유한다 ([job-family-definition.md](job-family-definition.md)).
- 입력 안내 문구: "모르면 억지로 채우지 말고 비워 두거나 '확인 필요'로 입력하세요." 0-3 원칙과 같다.
- 쓰지 않는 칸: `context`, `problem_or_goal`, `team`, `metrics`, `learning`, `evidence_links`는 적합성 평가와 자기소개서 쪽 몫이다.

### 1-3. 출력

공고 1건마다 `eligibility_result.v1` 1개를 만든다. 요건별 결과(`status`, 사유, 근거)와 계산값(`verdict`, 결정적 요건, 확인 필요 개수, `summary`)이 들어 있다. 칸과 관계 검사는 [data-contract.md](../data-contract.md) 2장에서 정한다.

### 1-4. 요건 추출 상태: "필수 요건 없음"을 믿을 수 있는가

요건 목록이 비어 있을 때 두 경우를 구분해야 한다. 공고가 정말 "학력무관·경력무관"이라 필수 요건이 없는 경우와, 요건 추출이 실패해서 요건을 못 뽑은 경우다. 둘 다 요건이 0개로 보이지만, 뒤의 경우를 적합으로 내리면 거짓 적합이 된다.

그래서 요건 추출 단계는 요건 목록과 함께 **추출 상태**를 낸다. 지원자 정보가 아니라 공고 분석이 끝났는지를 나타내는 값이다.

| `extraction_status` | 뜻 |
|---|---|---|
| `complete` | 공고 원문을 끝까지 읽었고, 자격요건 칸(또는 "이런 분을 찾아요"처럼 그에 준하는 칸)에서 요건을 모두 뽑았다. 칸에 "무관"만 있어 요건이 0개여도 `complete`다 |
| `incomplete` | 아래 `extraction_issues` 중 하나라도 있다 |

| `extraction_issues` | 조건 | 사용자에게 보여 줄 문구 예 |
|---|---|---|
| `text_unreadable` | 공고 원문이 잘렸거나 이미지라 읽지 못했다. 자격요건 칸이 있었는지도 알 수 없다 | "공고 원문을 다 읽지 못했습니다" |
| `extraction_failed` | 요건 추출 LLM 호출이나 결과 해석이 실패했다 | "자격요건을 분석하지 못했습니다" |
| `no_requirement_section` | 원문은 읽었는데 자격요건 칸과 그에 준하는 칸이 없다 |
| `partial_extraction` | 자격요건 칸은 읽었지만 요건 일부를 뽑지 못했거나, 조건부 문장처럼 해석하지 못한 문장이 있다 | "일부 자격요건을 분석하지 못했습니다. 원문을 확인해 주세요" |
| `required_preferred_ambiguous` | 필수와 우대를 구분할 수 없다 (칸 이름이 없거나 섞여 있다) | "필수와 우대 구분이 불명확합니다. 원문을 확인해 주세요" | "공고에 자격요건이 적혀 있지 않습니다. 원문을 확인해 주세요" |

- **상태는 문제 목록에서 계산한다.** 요건 추출(LLM)과 코드는 `extraction_issues`만 적는다. 코드는 LLM이 적지 않은 문제도 직접 확인해 추가한다. 문제가 하나도 없으면 `complete`, 하나라도 있으면 `incomplete`다. 상태를 따로 입력받지 않으므로 "`complete`인데 문제가 있음" 같은 모순이 생기지 않는다.
- **`incomplete`이어도 평가를 멈추지 않는다.** 결과는 정상적으로 만들고 정렬·적합성 평가도 그대로 진행한다. 사용자에게는 결과 옆에 안내 문구(위 표)만 보여 준다. 사용자가 답하기를 기다리지 않는다.
- **`incomplete`이면 `eligible`을 내지 않는다.** 원래 `eligible`이었을 결과는 `conditional`이 된다. 이미 확인된 미충족은 추출이 불완전해도 사실이므로 `not_eligible`은 그대로 둔다 (13장 종합 판정).
- 공고별 경우 정리:

| 공고 | 요건 | 추출 상태 | 종합 |
|---|---|---|---|
| "학력무관, 경력무관"만 있음 | 만들지 않음 (5장, 6장) | `complete` | 다른 필수 요건이 없으면 `eligible` |
| 자격요건 칸은 없고 우대사항만 있음 | 우대 요건만 있음 | `incomplete` (`no_requirement_section`) | `conditional` |
| 공고 일부를 읽지 못함 | 읽은 부분만 | `incomplete` (`text_unreadable`) | `eligible` 금지 |
| 추출 실패 | 없음 | `incomplete` (`extraction_failed`) | `conditional` |

## 2. 정의와 코드

판정 값은 영어 코드로 저장하고 화면에는 한글을 보여 준다. 대응은 `core/schemas.py`의 `DISPLAY_LABELS` 한 곳에서만 관리한다.

| 칸 | 코드 | 화면 문구 |
|---|---|---|
| 요건 상태 `status` | `met` / `needs_check` / `not_met` | 충족 확인 / 확인 필요 / 미충족 확인 |
| 종합 판정 `verdict` | `eligible` / `conditional` / `not_eligible` | 적합 / 조건부 적합 / 필수 요건 미충족 |
| 요건 유형 `type` | `numeric` / `skill` / `qualitative` / `preference` | 값 비교 / 기술·자격 / 정성 / 태도·성향 |
| 요건 칸 `level` | `required` / `preferred` | 필수 / 우대 |
| 값 비교 종류 `numeric_kind` | `career_years` / `education` / `major` | 경력 연수 / 학력 / 전공 |
| 결합 방식 `combine` | `all` / `any_of` | 모두 / 하나 이상 |
| 요건 출처 `origin` | `original` / `split` | 공고 그대로 / 사람이 나눔 |
| 판정 주체 | `rule` / `ai` / `user` | 규칙 / AI / 사용자 |
| 요건 추출 상태 `extraction_status` | `complete` / `incomplete` | 추출 완료 / 추출 불완전 |
| 추출 문제 `extraction_issues` (필수 요건이 없다고 확정할 수 없게 만드는 문제만 적는다) | `text_unreadable` / `extraction_failed` / `no_requirement_section` / `partial_extraction` / `required_preferred_ambiguous` | 원문 읽기 실패 / 추출 실패 / 자격요건 칸 없음 / 요건 일부만 추출됨 / 필수·우대 구분 불명확 |

- **`any_of` 요건은 항목별 결과(`item_results`)를 남긴다.** 항목마다 요건 하나처럼 `status`, 사유, 근거를 매긴다. `any_of`는 `skill`·`qualitative` 요건에만 쓴다. 값 비교(`numeric`) 항목을 섞는 사례는 아직 없다("신입 / 경력 N년 이상"은 5-1에서 `any_of` 없이 처리한다). 요건 전체의 상태는 코드가 항목 결과에서 계산한다: 하나라도 `met`이면 `met`, 전부 `not_met`이면 `not_met`, 그 밖에는 `needs_check`.
  - 합친 상태만 남기면 어느 항목이 충족됐는지 보여 줄 수 없고, 사용자가 한 항목에 답했을 때 다시 계산할 수 없고, `not_met`의 원인(`below_threshold`인지 `user_denied`인지)을 잃는다. 그래서 항목별 결과를 결과에 그대로 저장한다.
  - 합친 요건의 사유 코드는 항목 사유에서 코드가 고른다. 고르는 규칙은 data-contract 2장에서 정한다.
- **진행 중인 경험**이나 **상한**처럼 형식에 칸이 필요한 규칙은 해당 장에서 정한 뒤 data-contract 2장에 반영한다.

### `preferred`와 `preference` 구분

이름이 비슷하지만 다른 칸의 값이다.

| 칸 | 값 | 뜻 | 판정에 쓰는가 |
|---|---|---|---|
| `level` | `required` / `preferred` | 공고의 **어느 칸**에 있었나 (자격요건 / 우대사항) | `required`만 `verdict`에 쓴다. `preferred`는 적합성 점수에 쓴다 |
| `type` | `preference` | 요건의 **성격**이 태도·성향 문장이다 (예: "모르는 것을 추측으로 메우지 않고 확인하는 분") | `level`과 상관없이 판정과 점수에서 **모두** 뺀다. 결과에는 남긴다 |

- `type=preference`인 요건은 `status`를 매기지 않는다 (`status=null`).
- `preference`라는 코드 이름은 개선안 2-2절에서 정한 것이라 이번에는 바꾸지 않는다. 혼동이 계속되면 개선안에서 `attitude`로 바꾸는 안을 검토한다 (작업 현황).

## 3. 판정 사유 코드

`needs_check`와 `not_met`에는 사유 코드가 반드시 있다. **사유가 곧 사용자에게 할 질문이 된다.**

### 3-1. 확인 필요 (`needs_check`)

| 사유 코드 | 화면 문구 | 조건 | 사용자에게 묻는 예 |
|---|---|---|---|
| `no_profile_info` | 프로필에 정보 없음 | 요건과 관련된 칸이 비어 있다 | "FastAPI를 써 본 적이 있나요?" |
| `level_unclear` | 수준 확인 불가 | 경험은 있으나 "능숙", "자유자재로" 같은 수준을 판단할 수 없다 | "Excel을 어느 정도 다루나요?" |
| `scope_unclear` | 범위·종류 불명 | 근거가 요건의 일부만 덮거나 종류가 달라 같은 것인지 알 수 없다 | "만든 서비스를 실제로 출시했나요?" |
| `no_threshold` | 기준 없음 | 공고가 값 기준을 적지 않았다 (예: "경력, 연차 무관") | "이 경력에 인턴이 포함되나요?" (공고에 문의) |
| `graduation_pending` | 졸업 예정 | 졸업 예정 학력까지 넣어야 충족하는데 공고에 "졸업 예정자 가능"이 없다 | "지원 가능 여부를 공고에서 확인했나요?" |
| `category_unclear` | 경험 직무군 불명 | 연수에 넣을 경험의 직무군을 몰라 관련 경력 연수를 확정할 수 없다 | "이 경험은 어떤 직무 경험인가요?" |

**사유를 고르는 순서.** 겹쳐 보일 때는 위에서부터 처음 맞는 것을 고른다.

| 순서 | 질문 | 사유 | 예 |
|---|---|---|---|
| 1 | 공고에 비교할 기준 자체가 없는가? | `no_threshold` | "경력 (연차 무관)" |
| 2 | 프로필에 이 요건과 관련된 정보가 아예 없는가? | `no_profile_info` | 전공 칸이 비어 있음, Python 경험이 어디에도 없음 |
| 3 | 정보는 있으나 요건과 같은 것인지 판단할 수 없는가? | `scope_unclear` | 전공 "컴퓨터과학" vs 공고 "컴퓨터공학", 프롬프트 작성 보조 vs "LLM API 호출" |
| 4 | 같은 것은 맞지만 요구하는 수준에 이르는지 판단할 수 없는가? | `level_unclear` | Excel 사용 경험 vs "Excel 능숙" |

`graduation_pending`과 `category_unclear`는 각각 6장과 4장의 계산에서만 생긴다.

**코드가 정하는 질문 문구.** 코드(`core/rules.py`)가 `needs_check`를 낼 때 `question_for_user`에 넣는 문장이다. `{ }`는 값으로 채운다.

| 사유 | 만들어지는 곳 | 질문 문구 |
|---|---|---|
| `no_threshold` | 5장 "연차 무관" | 이 공고는 경력 기준을 적지 않았습니다. 인턴 경력이 포함되는지 공고에 확인해 보세요 |
| `no_profile_info` | 6장 학력 칸이 빔 | 학력 정보를 입력해 주세요 |
| `no_profile_info` | 7장 전공 칸이 빔 | 전공을 입력해 주세요 |
| `no_profile_info` | 4장 경험 목록이 빔 | 인턴·정규직·계약직 경험이 있으면 입력해 주세요 |
| `graduation_pending` | 6장 | 이 공고는 졸업 예정자 지원 가능 여부를 적지 않았습니다. 지원할 수 있는지 공고를 확인해 보세요 |
| `category_unclear` | 4장 2단계 | ‘{경험 제목}’ 경험은 어떤 직무 경험인가요? (직무군을 모르는 경험이 여럿이면 ‘A’, ‘B’ 경험은 …) |
| `scope_unclear` | 7장 전공명이 다름 | 이 공고는 {전공명 목록} 전공을 요구합니다. {지원자 전공} 전공으로 지원할 수 있는지 공고를 확인해 보세요 |
| `scope_unclear` | 4-1 인접 직무 경험 | 이 공고의 "관련 경력"에 ‘{경험 제목}’ 경험이 포함되는지 공고를 확인해 보세요 (인접 직무 경험이 여럿이면 ‘A’, ‘B’ 경험이) |

### 3-2. 미충족 확인 (`not_met`)

| 사유 코드 | 화면 문구 | 허용 조건 |
|---|---|---|
| `below_threshold` | 기준 미달 | `numeric` 요건이고 `status_decided_by=rule`일 때만 |
| `user_denied` | 사용자가 없다고 답함 | `skill`, `qualitative` 요건이고 `status_decided_by=user`일 때만. `skill`, `qualitative`가 `not_met`이 되는 유일한 길 |

- 사용자가 확인 필요 항목에 답하면 `status_decided_by=user`로 바뀐다. "있다"는 `met`, "없다"는 `not_met` + `user_denied`다.
- `met`에는 사유 코드가 없다.

## 4. 관련 경력 인정 기준

**문제:** 1번 공고는 "**서비스 기획** 경력 3년 이상"을 요구한다. 지원자의 인턴 6개월을 이 경력으로 셀 수 있는지 정해야 한다.

| 선택지 | 내용 | 1번 공고 결과 |
|---|---|---|
| A. 모든 경력 합산 | 직무와 상관없이 인턴·경력 기간을 모두 더한다 | 0.5년 < 3년 → 미충족 확인 |
| **B. 요건에 직무가 적혀 있으면 그 직무군만 합산 (채택)** | "서비스 기획 경력"이면 서비스기획 직무군 경험만 더한다. 직무가 적혀 있지 않으면("경력 3년 이상") A처럼 모두 더한다 | 0.5년 < 3년 → 미충족 확인 |
| C. B + 인접 직무군 포함 | 인접 쌍([job-gate.md](job-gate.md) 4장) 경험도 더한다 | 0.5년 < 3년 → 미충족 확인 |

- **채택: B.** 공고가 직무를 적은 데는 이유가 있다. A로 하면 영업 3년 경력자도 "서비스 기획 경력 3년"을 충족하게 된다.
- **요건의 직무군은 `career_family`(`JF_*` 또는 `null`)로 적는다.** `null`이면 모든 인턴·경력을 합산한다.
- **`career_family`를 어떻게 정했는지는 `career_family_basis`로 적는다:** `stated`(공고가 직무명을 적음, 예: "서비스 기획 경력") / `related`("관련 경력"에서 공고 직무로 해석함, 4-1).
- **경험의 직무군은 `Experience.category`(`JF_*`)다.**
- 연수에 넣는 경험은 `type`이 `intern`, `full_time`, `contract`인 것만이다. `project`, `activity`는 연수에 넣지 않는다. 대신 업무 연결 근거로 쓴다.
- 기간이 겹치는 경험은 겹친 달을 한 번만 센다 (11장).
- **직무군을 모르는 경험 (0-3 적용):** `career_family`가 있는 요건은 아래 순서로 판정한다.

| 단계 | 합산 대상 | 결과 |
|---|---|---|
| 1 | 직무군이 같은 경험만 | 기준 이상이면 `met` |
| 2 | 1 + 직무군을 모르는 경험(`category=null`) | 기준 이상이면 `needs_check`(`category_unclear`) |
| 3 | 2 + 인접 직무군 경험. **`career_family_basis=related`일 때만** (4-1) | 기준 이상이면 `needs_check`(`scope_unclear`) |
| 4 | 3으로도 기준 미만 | `not_met`(`below_threshold`) |

- 1~3단계의 합산에는 **11장 기간 계산을 그대로 적용한다.** 시작 월·끝 월을 포함하고, `min(end, as_of_month)`에서 자르고, 경험끼리 겹친 달은 한 번만 센다. 각 단계는 앞 단계 경험에 새 경험을 더한 달의 **합집합**으로 센다. 그래서 같은 달에 직무군이 같은 인턴과 모르는 인턴을 동시에 했어도 한 달로 센다.
- 직무군을 모르는 경험이 판정 결과를 바꿀 수 있을 때만(2단계) `category_unclear`가 된다. 그 경험이 없어도 결과가 같으면 사유로 쓰지 않는다.
- **`category=null`의 원인은 구분하지 않는다.** 실제로 직무군을 알 수 없음, 아직 분류하지 않음, 입력 누락, 여러 직무가 섞임은 모두 `category=null`이고 사유는 `category_unclear` 하나다. 원인이 달라도 판정과 해결 방법이 같기 때문이다. 사용자에게 "이 경험은 어떤 직무 경험인가요?"라고 물어 하나를 고르게 한다. 여러 직무가 섞였으면 비중이 가장 큰 직무를 고르게 안내한다.
- `career_family=null`(직무 무관 경력 요건)이면 직무군과 상관없이 1단계에서 모든 인턴·경력을 합산하므로 `category_unclear`가 생기지 않는다.

### 4-1. "관련 경력"

공고가 직무명 없이 "관련 경력 2년 이상", "유관 경력", "해당 직무 경력"이라고 쓴 경우다.

| 선택지 | 내용 | 영업 2년 경력자 → 서비스기획 공고 "관련 경력 2년" |
|---|---|---|
| A. 직무 표기 없음으로 보고 모두 합산 | `career_family=null` | `met` (거짓 적합) |
| **B. 공고의 직무군으로 해석 (채택)** | `career_family`에 공고의 직무군을 넣는다 | 서비스기획 경력 0개월 → `not_met` |
| C. 무엇이 관련인지 사용자에게 물음 | 항상 `needs_check`(`scope_unclear`) | `needs_check` |

- **채택: B.** 채용에서 "관련 경력"은 대개 그 공고의 직무 경력이다. 4장에서 B안을 고른 이유("영업 3년 경력자가 서비스 기획 경력 3년을 충족하면 안 된다")와 같다.
- 요건 추출 단계가 `career_family`에 게이트의 `core_family`를 넣고, `career_family_basis=related`, `interpretation_note`에 "관련 경력 → 서비스기획으로 해석"처럼 적는다.
- **인접 직무 보완 (0-3 적용):** 무엇이 "관련"인지는 회사가 정하므로, 인접 직무 경험까지 관련으로 볼 여지가 있다. 그래서 `related`일 때만 4장 3단계에서 인접 직무군([job-gate.md](job-gate.md) 4-2의 인접 쌍) 경험까지 더해 본다. 그것으로 기준을 넘으면 `not_met` 대신 `needs_check`(`scope_unclear`)다. 공고가 직무명을 적은 `stated`에는 인접 직무를 더하지 않는다 (4장 C안을 채택하지 않음).
- `core_family`가 없으면(게이트 `out_of_scope`, 또는 `review_needed`인데 추정 직무군이 없음) `career_family`를 정할 수 없다. 이때는 값 비교를 하지 않고 `needs_check`(`scope_unclear`)로 둔다.
- **"동종 업계 경력", "같은 업종 경력"은 다르다.** 업계는 직무가 아니라 회사가 속한 산업이고, 프로필에 산업 칸이 없다. 그래서 직무군으로 바꾸지 않고 `needs_check`(`scope_unclear`)로 둔다.
- 직무 전환자가 공고 직무에 맞는 경험을 얼마나 가졌는지는 적합성 평가 몫이다. 자격요건은 지원할 수 있는지만 본다.

샘플 프로필의 인턴(OO솔루션즈 B2B AI 사업부 기획팀)은 업무가 서비스 기획 보조, QA, 와이어프레임 작성이다. 그래서 `category=JF_SERVICE_PLANNING`, 6개월로 본다.

### 4-2. 코드 구현 규칙

`core/rules.py`가 4장과 4-1장을 구현할 때 쓰는 세부 규칙이다.

- **인접 직무군 쌍 (4-1 3단계).** 쌍의 원본은 [job-gate.md](job-gate.md) 4-2 표이고 **`사용` 상태인 쌍만** 쓴다. 쌍은 순서가 없다(서비스기획↔프로젝트관리는 프로젝트관리↔서비스기획과 같다). 코드는 쌍을 **인자로 받는다**. 기본값은 지금 표의 `사용` 쌍 3개(`JF_SERVICE_PLANNING`↔`JF_PROJECT_MGMT`, `JF_SERVICE_PLANNING`↔`JF_UIUX_DESIGN`, `JF_DEV`↔`JF_QA`)이고, 기본값이 표와 같은지 테스트가 문서를 읽어 대조한다. 게이트 설정값이 이식되면 그 값을 넘긴다.
- **프로필이 비어 있을 때 (0-3).** 경험 목록(`experiences`)이 비어 있고 `min_value`가 0보다 크면 `needs_check`(`no_profile_info`)다. 경험은 있는데 연수에 넣는 유형(`intern`, `full_time`, `contract`)이 하나도 없으면 연수 0개월로 보고 기준 미달이면 `not_met`(`below_threshold`)이다. `min_value`가 0이면 어느 쪽이든 `met`이다.
- **`compared` 표기.** 개월로 적고 기준에만 연을 덧붙인다(11장). `met`이면 `"합계 개월 ≥ 기준 개월"`, `not_met`이면 `"합계 개월 < 기준 개월(N년)"`이다. 합계는 **1단계(같은 직무군) 개월 수**다. `needs_check`(`category_unclear`, `scope_unclear`)도 같은 형식으로 1단계 개월을 적는다(예: `"6개월 < 36개월(3년)"`). 판단이 갈리는 이유는 `question_for_user`가 설명한다. `career_family=null`이면 연수에 넣는 모든 경험의 합집합이다. 기준의 연이 정수가 아니면 소수로 쓴다(예: 18개월(1.5년)).
- **근거 인용.** 판정에 쓴 경험마다 `{experience_id, quote=title}`을 남긴다. 판정에 쓴 경험이 없으면 근거를 비운다.

## 5. 경력 요건 해석 (신입/경력)

공고의 경력 표현을 `min_value`(최소 연수)로 바꾸는 표다. 이 값은 요건 추출 단계에서 넣는다.

| 공고 표현 | `min_value` | 신입 지원 | 샘플 |
|---|---|---|---|
| 신입 | 0 | 가능 | |
| 경력무관, 경력 무관 (신입 지원 가능) | 0 | 가능 | 5번 |
| 신입 / 경력 ~N년, 신입·경력 | 0 | 가능 | 3번 |
| **신입 / 경력 N년 이상**, 신입 또는 경력 N년 이상 | 0 | 가능 | |
| 경력 N년 이상, 경력 N년 초과 | N | 불가 | 1번 (3) |
| 경력 N년 내외 | N−1 (0보다 작으면 0) | N−1 > 0이면 불가 | 2번 (2) |
| **신입 / 경력 N년 이상 ~ M년 이하** | 0 (상한 M은 `max_value`, 5-3) | 가능 | 3번 첫 줄 (N=1, M=3) |
| 경력 N~M년, 경력 N년 이상 ~ M년 이하 | N (상한 M은 `max_value`) | 불가 | 6번 (1) |
| **경력 (연차 무관)** | 정하지 않음(`null`). **`numeric`(`career_years`)이다** | **확인 필요** (`no_threshold`) | 4번 |

- **4번 "경력 (연차 무관, 실무 프로젝트 경험)":** 경력자를 원하지만 기준 연수가 없다. 인턴 6개월을 "경력"으로 볼지는 공고만으로 알 수 없다. 그래서 값 비교를 하지 않고 확인 필요로 둔다.
- 3번처럼 같은 뜻의 경력 표현이 두 줄로 반복되면 요건 하나로 합친다.
- `min_value`가 0이면 항상 `met`이다.

### 5-1. "신입 / 경력 N년 이상"

이 표현은 **신입이면 경력이 없어도 되고, 경력으로 지원하면 N년 이상**이라는 뜻이다. 신입 지원 경로가 열려 있으므로 `min_value=0`으로 본다. "경력 N년 미만은 지원 불가"로 읽지 않는다.

- 예: "신입 / 1년 경력 이상"에 인턴 6개월 지원자 → `met`. 경력 6개월이 1년에 못 미치는 것은 문제가 되지 않는다. 신입으로 지원하면 되기 때문이다.
- 경력 기준 N년은 `interpretation_note`에 남긴다 (예: "경력 지원 시 1년 이상"). 적합성 평가와 화면에서 참고한다.
- **신입 여부는 판정하지 않는다.** 지원자가 신입으로 지원할 수 있는지는 회사가 정하는 것이고 공고만으로 알 수 없다. 짧은 정규직 경력이 있는 사람도 신입으로 지원하는 경우가 흔하다. 그래서 이 문서는 "신입 해당 여부"를 묻는 칸이나 사유를 두지 않는다.
- "경력 연수에 인턴 기간을 포함한다"(0-2)는 경력 연수를 **계산하는** 규칙이다. 인턴 경험이 있다고 신입이 아니라는 뜻이 아니다.
- 반대로 "경력 1년 이상 (신입 불가)"처럼 신입 경로를 닫은 공고는 일반 "경력 N년 이상"이다.

### 5-2. 경계값

| 경우 | 처리 |
|---|---|
| "N년 이상" | 합계 ≥ N×12개월이면 충족. 기준 월 포함 계산(11장)이라 정확히 N년이면 충족이다 |
| "N년 초과" | "N년 이상"과 같게 본다. 월 단위 계산으로는 "이상"과 "초과"의 차이(1개월 안쪽)를 믿을 만하게 가를 수 없고, 0-3 원칙에 따라 지원자에게 유리하게 읽는다 |
| "N년 내외"에서 N이 1 이하 | `min_value`는 0이다. "1년 내외"는 신입도 충족한다 |
| "N~M년" | N년 이상이면 충족. M은 상한으로 `max_value`에 기록한다 (5-3) |
| 1개월처럼 짧은 경험 | 그대로 센다. 화면에는 개월로 보여 준다 (11장 `compared` 형식) |

### 5-3. 상한 ("~3년 이하", "N~M년"의 M)

**상한은 판정에 쓰지 않는다.** 경력이 상한을 넘어도 미충족으로 보지 않고 `max_value`에 기록하며, 근거에 "상한 초과"만 적는다.

- **이것은 MVP 단순화가 아니라 정책 의도다.** 상한은 지원 자격이라기보다 회사가 기대하는 연차 범위다. 상한을 넘는 지원자도 실제로 지원하고, 상한 초과로 미충족을 내리면 거짓 미충족이 된다 (0-3).
- "신입만 모집"인 공고에 경력자가 지원하는 경우도 같다. 판정하지 않고 근거에만 남긴다.
- 검증용 공고에서 상한을 엄격하게 적용하는 공고가 많이 보이면 다시 검토한다 (작업 현황).

**선택 기능:** `min_value`가 0인 공고만 보여 주는 "신입 지원 가능 공고만 보기" 필터를 둘 수 있다. 사용자가 직접 켜는 필터이고, 평가 결과는 바꾸지 않는다. MVP 포함 여부는 아직 정하지 않았다 (작업 현황).

### 5-4. 코드가 원문 표현으로 바로잡는 경력 기준

경력 기준은 종합 판정을 바로 바꾼다(기준을 잘못 읽으면 거짓 미충족이 난다). 그래서 LLM이 뽑은 `min_value`를 믿기만 하지 않고, 원문의 **정해진 표현**이 보이면 코드가 값을 확인하고 다르면 **고친다.** 고친 사실은 `interpretation_note`에 남기고 추출 기록(18장)에 센다. 요건을 버리지는 않는다.

| 원문에 있는 표현 | 코드가 확정하는 값 |
|---|---|
| "신입"이 있고 "신입 불가"·"신입 제외"는 없음 | `min_value=0`. 상한이 "~M년", "M년 이하", "N년 이상 ~ M년 이하"로 있으면 `max_value=M` |
| "경력 N년 이상 ~ M년 이하", "경력 N~M년" (신입 없음) | `min_value=N`, `max_value=M` |
| "경력 N년 이상", "경력 N년 초과" (신입 없음) | `min_value=N` |
| "경력 N년 내외" | `min_value=max(N−1, 0)` (상한은 건드리지 않음) |
| "경력 무관", "경력무관" (신입 없음) | `min_value=0` |
| "경력"이 있고 "연차 무관" | 유형 `numeric`(`career_years`), `min_value=null` |

- **적용 범위.** `numeric`이면서 `numeric_kind=career_years`로 뽑힌 요건에만 쓴다. 단, "경력 … 연차 무관"은 LLM이 `qualitative`·`skill`로 뽑았어도 `numeric`으로 바로잡는다(`combine=any_of`가 아닐 때). 유형을 잘못 뽑으면 `no_threshold` 확인 필요가 `met`이 될 수 있기 때문이다.
- **애매하면 고치지 않는다.** 위 표현이 하나도 없거나 서로 충돌하는 표현이 함께 있으면 LLM의 값을 그대로 둔다. "관련 경력"의 직무군(`career_family`, `career_family_basis`)은 이 코드가 건드리지 않는다. 직무가 없는 "N~M년"(예: "경영기획 분야 1~2년의 경험")도 "경력"이 없으므로 건드리지 않는다.
- 이 표는 코드(`core/career_normalizer.py`)와 테스트가 같이 가진다. 표현을 늘릴 때는 이 표를 먼저 고친다.

## 6. 학력 비교

학력 순서: **고졸 < 전문학사 < 학사 < 석사 < 박사** (`high_school` < `associate` < `bachelor` < `master` < `doctorate`)

| 공고 표현 | 기준 | 샘플 |
|---|---|---|
| 학력무관 | 요건 없음. **요건으로 만들지 않는다** | 4번 |
| 대학졸업(2,3년) 이상 | 전문학사 이상 | 5번 |
| 대학교졸업(4년) 이상 | 학사 이상 | 3번 |
| 대졸 이상 (연수 표시 없음) | **전문학사 이상**으로 해석하고 `interpretation_note`에 기록 | 1번 |

- "대졸 이상"은 2·3년제를 포함하는지 알 수 없다. 0-3 원칙에 따라 지원자에게 유리한 쪽(전문학사 이상)으로 해석한다.
- `재학`, `중퇴`는 그 학력을 갖지 않은 것으로 보고, **졸업한 학력 중 가장 높은 것**과 비교한다.
- **졸업 예정자:** 졸업한 학력만으로 충족하면 `met`이다. 졸업 예정 학력까지 넣어야 충족하는 경우에는, 공고에 "졸업 예정자 지원 가능"이 있으면(`allows_graduating=true`) `met`, 없으면 `needs_check`(`graduation_pending`)다.
- 졸업한 학력도 졸업 예정 학력도 기준에 못 미치면 `not_met`(`below_threshold`)이다.
- **`education`이 비어 있으면** 학력 요건은 `needs_check`(`no_profile_info`)다. 졸업 학력이 없고 `enrolled`·`dropped`만 있으면 기준 미달이므로 `not_met`이다.
- `compared`는 `"학사 졸업 ≥ 전문학사"`(`met`), `"학사 졸업예정 ≥ 학사"`(졸업 예정으로 충족), `"고졸 < 학사"`(`not_met`)처럼 졸업한 가장 높은 학력으로 적는다. 졸업 예정 학력까지 넣어야 충족하는데 공고에 "졸업 예정자 가능"이 없어 `needs_check`(`graduation_pending`)일 때도 졸업한 가장 높은 학력으로 적는다(예: `"고졸 < 학사"`). 졸업한 학력이 하나도 없으면 `"졸업 학력 없음 < 학사"`로 적는다. 학력 이름은 `고졸`, `전문학사`, `학사`, `석사`, `박사`다.
- **근거.** `met`·`graduation_pending`은 판정에 쓴 학력 항목(졸업 예정으로 충족하거나 확인이 필요한 것은 졸업 예정 항목), `not_met`은 졸업한 가장 높은 학력 항목의 `raw`를 `field="education[i]"`로 인용한다. `raw`가 없거나 졸업한 학력이 없으면 근거를 비운다. 같은 학력이 여럿이면 `education`에서 앞선 항목을 쓴다. 근거는 `education[i]`의 `raw`가 있을 때만 인용한다 (13장).

## 7. 전공

- "전공 무관"은 요건 없음으로 보고 요건으로 만들지 않는다.
- **"관련 전공"은 값 비교가 아니라 판단이 필요하다.** 어떤 전공이 관련 전공인지 공고가 정하지 않았기 때문이다. 공고가 전공명을 적었을 때(예: "컴퓨터공학 전공")만 `numeric`(`major`, `major_names`)으로 비교한다. 전공명이 없으면 `qualitative`로 두고 미충족 확인을 내리지 않는다.
- **이 장의 규칙은 자격요건 칸(`level=required`)의 전공 요건에 쓴다.** 예: "자격요건: 경제학 전공자". 우대사항 칸의 전공(`level=preferred`, 예: "우대: 경제학 전공자")은 종합 판정에 쓰지 않고 적합성 점수에만 쓴다 (2장, 15장).

### 7-1. 전공명 비교

| 경우 | 결과 | 예 (공고 "경제학 전공") |
|---|---|---|
| 프로필에 전공 정보가 없음 | `needs_check`(`no_profile_info`) | 전공 칸이 비어 있음 |
| 정리한 전공명이 `major_names` 중 하나와 같음 | `met` | "경제학과" |
| 복수전공·부전공 중 하나가 같음 | `met` | 주전공 경영학, 복수전공 경제학 |
| 전공명이 다름 (비슷한 이름 포함) | `needs_check`(`scope_unclear`) | "경제통계학", "경영학" |
| 공고가 전공명 없이 "관련 전공"만 적음 | `qualitative`로 두고 `needs_check` 가능 | "관련 전공자" |

- **전공명이 달라도 `not_met`을 내지 않는다.** 두 이름이 같은 전공으로 인정되는지, 회사가 엄격하게 구분하는지 공고만으로 알 수 없다 (0-2 해석, 0-3).
- 프로필의 모든 `education[]` 항목의 전공을 본다. 학력 수준(졸업 여부)은 6장이 따로 판정한다.
- **`compared`.** `met`이면 `"{지원자 전공} = {일치한 공고 전공명}"`(예: `"경제학과 = 경제학 전공"`), `needs_check`(`scope_unclear`)이면 `"{지원자 전공 목록} ≠ {공고 전공명 목록}"`이다. 이름은 입력한 그대로 적고 정리한 이름은 쓰지 않는다. 목록은 `, `로 잇는다.
- **근거.** `met`은 일치한 전공이 있는 `education[i]`, `scope_unclear`는 전공을 적은 모든 `education[i]`의 `raw`를 `field="education[i]"`로 인용한다. `raw`가 없으면 근거를 비운다.
- **전공 칸이 빔.** `education`이 비었거나 모든 항목의 `majors`가 비면 `needs_check`(`no_profile_info`)다.

### 7-2. 코드가 하는 전공명 정리의 범위

코드는 아래만 한다. 그 밖의 유사성·관련성 판단은 코드도 LLM도 자동으로 확정하지 않고 `needs_check`로 둔다.

1. 공백을 지우고, 끝의 "전공"을 뗀 뒤, 끝이 "학과"·"학부"이면 "과"·"부"를 뗀다(학 글자는 남긴다). 예: "경제 학과" → "경제학", "경제학과 전공" → "경제학", "컴퓨터공학부" → "컴퓨터공학". 지원자 전공과 공고 `major_names`에 같은 정리를 한다
2. 정리한 이름을 공고의 `major_names`와 **정확히** 비교한다.
3. 복수전공·부전공 목록에서도 같은 비교를 한다.
4. 정리한 결과가 빈 이름(공백만 있거나 "전공"뿐인 이름)은 전공으로 보지 않는다. 지원자 쪽이면 입력하지 않은 것(`no_profile_info`)으로, 공고 쪽이면 비교 대상에서 뺀다. 공고의 `major_names`가 **모두** 빈 이름이면 비교할 전공명이 없는 것이므로 판정하지 않고 요건 입력 오류로 거부한다(요건 추출이 전공명을 뽑지 못한 경우이며, 추출 단계가 `partial_extraction` 등으로 처리한다).

"컴퓨터과학"과 "컴퓨터공학"이 같은지 같은 판단은 하지 않는다. 사용자에게 "이 공고는 컴퓨터공학 전공을 요구합니다. 컴퓨터과학 전공으로 지원할 수 있는지 공고를 확인해 보세요"처럼 묻는다.

- 샘플 6건에는 필수 전공 요건이 없다. 3번의 전공은 우대사항이다.

## 8. 자격증·면허

**문제:** 5번 공고는 필수에 "2종보통운전면허(오토)"를 적었다. 요건 유형 표에 자격증이 없다.

| 선택지 | 프로필에 없을 때 | 문제점 |
|---|---|---|
| A. `numeric`처럼 처리 | 미충족 확인 | 프로필 입력 때 적지 않았을 뿐일 수 있다. 거짓 미충족이 생긴다 |
| **B. `skill`처럼 처리 (채택)** | 확인 필요. 사용자가 "없음"을 명시하면 미충족 확인 | 없음 |

- **채택: B.** 새 유형을 만들지 않고 `skill` 규칙을 따른다.
- 판정은 `certificates`와 `other_qualifications` 두 목록을 모두 본다. 운전면허를 어느 쪽에 둘지는 판정에 영향이 없다.
- 확인 필요가 된 자격은 화면에서 "운전면허가 있나요?"처럼 사용자에게 바로 묻는다.

## 9. 필수와 우대 구분

**기본 규칙:** 공고의 칸 이름을 따른다. "자격요건" 칸은 `required`, "우대사항" 칸은 `preferred`다.

예외는 두 가지다.

| 경우 | 처리 | 샘플 |
|---|---|---|
| 자격요건 칸에 여러 역량이 나열되고 "모두 필수"라는 말이 없다 | `required` + `combine=any_of` + `interpretation_note` 기록 | 5번 "보유역량: 영어가능자, 해당직무 인턴경력, 운전가능자, 차량소지자 …" |
| 우대사항 칸에 태도·성향 문장이 있다 | `type=preference` (판정·점수 제외) | 2번 "모르는 것을 추측으로 메우지 않고 확인하는 분" |

- 자격요건 칸에 있어도 "커뮤니케이션 능력" 같은 문장은 `qualitative`다 (6번).

## 10. 한 문장에 여러 요건이 섞인 경우

**문제:** 1번 "서비스 기획 경력 3년 이상 (앱/웹 서비스 출시 경험 필수)"에는 연수 요건과 경험 요건이 함께 있다.

- **규칙:** 값으로 비교할 부분과 경험·역량 부분이 한 문장에 있으면 **요건 두 개로 나눈다.**
  - 1-R2: 서비스 기획 경력 3년 이상 (`numeric`, `career_years`, `min_value=3`, `career_family=JF_SERVICE_PLANNING`)
  - 1-R3: 앱/웹 서비스 출시 경험 (`qualitative`)
- 나눈 요건은 `origin=split`으로 표시하고, `text`에 공고 원문을 그대로 둔다.
- 나누지 않으면 출시 경험 부분이 연수 비교에 묻혀 판정 근거에서 사라진다.

## 11. 경력 기간 계산

- 기간은 `period`(`"YYYY-MM"`)로 받고 개월 수 `duration_months`는 **코드가 계산한다.** 입력으로 받지 않는다.
- **시작 월과 끝 월을 모두 센다.** `2025-03 ~ 2025-06`은 4개월이다. 같은 달에 시작하고 끝나면 1개월이다.
- **세는 끝은 `min(end, as_of_month)`다.** 진행 중이라 `end`가 없으면 `as_of_month`까지 센다. 예정 종료 월이 기준 월보다 늦으면 기준 월까지만 센다. 예: 기준 월 `2026-11`, 경험 `2026-09 ~ 2027-02`는 3개월이다.
- 기준 월은 공고 확인일이 아니라 **평가를 실행한 달**이다 (1-1).
- **겹친 기간은 한 번만 센다.** 합산은 달 단위로 합집합을 구한다.
- 연 단위 비교는 **개월로** 한다: `합계 개월 ≥ min_value × 12`. 연으로 바꿔 올리지 않는다. 예: 6개월은 0.5년이고 3년 기준에는 미달이다.
- `compared`는 개월로 적고 기준에만 연을 덧붙인다: `"6개월 < 36개월(3년)"`, `"1개월 < 12개월(1년)"`. 1개월처럼 짧은 경험도 소수 연(0.08년)으로 바꾸지 않는다.
- **휴직:** 휴직 기간은 경력에 넣지 않는다. 휴직이 있으면 경험을 휴직 전과 후 두 개로 나눠 입력하게 안내한다. 코드는 입력된 기간을 그대로 센다.
- **동시에 한 경험:** 같은 달에 두 곳에서 일했어도 그 달은 한 번만 센다 (위 "겹친 기간").
- 오류: `end < start`, `start > as_of_month`.
- 샘플 프로필 인턴은 2025-07 ~ 2025-12로 끝났으므로 기준 월과 상관없이 6개월이다.

## 13. 판정 절차: 코드와 LLM 분담

점수·판정 형식 변환·순위 정렬은 코드가 하고 LLM에 맡기지 않는다 (AGENTS.md).

| 단계 | 담당 | 내용 |
|---|---|---|
| 1. 요건 추출 | LLM (공고 분석) + 코드 확인 | 요건 분리, `level`, `type`, `numeric_kind`, `min_value`, `career_family`, `career_family_basis`, `major_names`. `text`는 공고 원문. LLM은 `extraction_issues` **후보만** 낸다. 코드가 후보를 확인하고 직접 확인한 문제를 더해 `extraction_status`를 계산한다 (1-4, 13-1) |
| 2. numeric 판정 | **코드** | 경력 연수 합산(11장), 학력 순서(6장), 전공명 정리와 정확 비교(7-2). `compared` 문자열 생성(4-2). 전공명의 유사성·관련성은 판단하지 않고 `needs_check`로 둔다. 근거는 계산에 쓴 경험의 `title`, 학력은 `education[].raw`(있을 때만)를 인용한다 |
| 3. skill·qualitative 근거 찾기 | LLM | 프로필 근거 = 경험 id + 프로필 원문 인용. 근거가 불충분하면 `needs_check`. 출력 칸과 실패 처리는 13-1 |
| 4. 상태 검증 | **코드** | LLM이 `not_met`을 내면 코드가 `needs_check`로 되돌린다. `not_met`은 numeric 값 비교와 `user_denied`만 허용한다. 되돌릴 때의 사유는 LLM이 낸 확인 필요 사유가 유효하면 그대로 쓰고, 없으면 `scope_unclear`다. `interpretation_note`에 "AI가 미충족으로 판단해 확인 필요로 조정"을 남긴다. 사용자가 정한 `user_denied`는 되돌리지 않는다. 이 검증은 LLM의 원시 출력에 스키마 검증 **전에** 적용한다 |
| 5. 종합 판정·요약 | **코드** | `any_of` 항목 결과 합치기(2장), `verdict`, 결정적 요건, `needs_check_count`, `summary` |

- **상태 검증의 범위 (4단계).** 4단계는 LLM의 원시 출력(딕셔너리)에만 적용한다. 원시 출력은 AI가 낸 것이므로 안에 적힌 `status_decided_by`를 믿지 않고 모두 `ai`로 덮고(`any_of` 항목 포함, 상태가 `null`인 것은 제외), `not_met`은 예외 없이 `needs_check`로 되돌린다. 코드가 판정한 `numeric`의 `not_met`(`below_threshold`)과 사용자가 정한 `user_denied`는 이 검사를 거치지 않는다. 앞의 것은 코드가 만든 결과 객체이고, 뒤의 것은 사용자 답변을 받은 쪽이 검증된 결과 객체(`status_decided_by=user`)로 만들어 넘긴다. 이 검사를 단독으로 불러도 판정 주체를 믿지 않는다.
  - 되돌린 결과의 `status_decided_by`는 `ai`다. 사유는 LLM이 낸 값이 확인 필요 사유(3-1)이면 그대로, 아니면(`below_threshold`, `user_denied`, 빈 값, 모르는 값) `scope_unclear`다.
  - `any_of` 요건은 항목마다 같은 검사를 한다. 하나라도 되돌리면 요건의 `interpretation_note`에 한 번 남긴다. `interpretation_note`가 이미 있으면 뒤에 ` / `로 이어 쓴다.
  - 입력 딕셔너리를 바꾸지 않고 새 딕셔너리를 돌려준다. 상태가 `null`(`preference`), `met`, `needs_check`인 결과는 상태와 사유를 손대지 않는다(판정 주체만 `ai`로 덮는다).
- **`any_of` 합치기 (5단계).** 결정 항목(data-contract 2-4)의 `status`, `reason_code`, `evidence_checked_by`, `status_decided_by`를 요건 전체 값으로 옮기고, `job_quote`, `profile_evidence`, `compared`, `question_for_user`는 비운다. 항목의 `item_index`가 요건의 `items`와 1:1이 아니거나 `combine`이 `any_of`가 아니면 오류다.
- **결과 조립 (코드).** 코드는 위 1~5단계를 이어서 공고 1건의 결과를 만든다. 입력은 같은 공고의 게이트 결과, 프로필, 요건 목록(1단계 출력), `skill`·`qualitative` 요건의 판정(3단계 출력), `extraction_issues`다.
  - `job_id`와 `gate_ranking_group`은 게이트 결과에서 복사하고, `as_of_month`는 프로필에서 가져온다.
  - 요건 유형마다 판정하는 쪽이 다르다: `numeric`은 코드가 판정한다(2단계). `preference`는 `status=null`로 결과에만 남긴다. `skill`·`qualitative`는 밖에서 받은 판정을 쓴다.
  - 밖에서 받는 판정은 요건마다 하나씩 있어야 한다. **빠진 요건이 있으면 오류**다(확인하지 않은 요건을 조용히 `needs_check`로 채우지 않는다). `numeric`·`preference` 요건이나 없는 요건의 판정을 받으면 오류다.
  - 받은 판정이 LLM의 원시 출력(딕셔너리)이면 4단계(되돌림)를 적용한 뒤 스키마 검증을 하고, `any_of`는 항목을 합친다(5단계). 이미 검증된 결과 객체이면 그대로 쓴다. `requirement_id`가 다르면 오류다.
  - **원시 딕셔너리는 4단계를 거친다.** LLM이 스스로 `user`라고 적어 `not_met`을 살리는 길을 막으려고 판정 주체를 `ai`로 덮는다(위 "상태 검증의 범위"). 사용자가 정한 판정(`user_denied`)은 검증된 결과 객체로 넘긴다.
  - 요건 `id`가 겹치면 오류다(판정이 엉뚱한 요건에 붙는 것을 막는다).
  - 만들기 전에 모든 `profile_evidence`를 프로필 원문과 대조한다(위 "프로필 근거 검증"). 어긋나면 결과를 만들지 않는다.
- **종합 판정 규칙:** `level=required`이고 `type≠preference`인 요건만 본다.
  1. 미충족이 하나라도 있으면 `not_eligible`
  2. 없고 확인 필요가 하나라도 있으면 `conditional`
  3. 없고 `extraction_status=incomplete`이면 `conditional` (1-4)
  4. 그 밖에는 `eligible`. 필수 요건이 0개여도 추출이 `complete`이면 여기에 온다
- **결정적 요건:** `not_eligible`이면 `not_met`인 필수 요건 전부, `conditional`이면 `needs_check`인 필수 요건 전부, `eligible`이면 없음이다. 3번 경우처럼 추출 불완전 때문에 `conditional`이면 결정적 요건은 없고, `summary`가 `extraction_issues`를 보여 준다.
- `summary`는 LLM이 쓰지 않는다. 코드가 판정 값을 템플릿에 넣어 만든다.
- **프로필 근거 검증 (코드).** `profile_evidence`의 `experience_id`가 프로필에 있어야 하고, `quote`가 그 경험의 원문(`title`, `role`, `actions`, `tools`, `result`) 안에 있어야 한다. `field` 근거(`skills`, `certificates`, `education[i]`)도 해당 칸의 원문 안에 있어야 한다. 어기면 오류로 처리하고 결과를 저장하지 않는다. 스키마는 프로필을 모르므로 이 검사는 코드가 한다.
  - **원문을 찾는 방법.** `quote`는 원문 **한 조각 안에** 글자 그대로 들어 있어야 한다. 조각은 `title`, `role`, `result`, `actions`의 항목 하나, `tools`의 항목 하나이고, `field` 근거는 `skills`·`certificates`·`other_qualifications`의 항목 하나, `education[i]`의 `raw`다. 여러 조각을 이어 붙인 글에서는 찾지 않는다. 공백이나 문장부호를 맞춰 주지 않는다. 새로 쓴 문장이 근거로 들어오는 것을 막으려는 규칙이다.
  - **다음은 모두 오류다.** 프로필에 없는 `experience_id`, 위 칸이 아닌 `field`(`skills_denied` 포함), 범위를 벗어난 `education[i]`, `raw`가 없는 `education[i]`, 조각 안에 없는 `quote`.
  - **오류는 모아서 낸다.** 위반을 모두 찾아 한 번에 알린다. 위반마다 요건 id(`any_of`는 항목 번호도)와 근거를 적는다. `any_of` 항목의 근거도 같은 검사를 한다. 검사는 요건의 `profile_evidence`가 비어 있어도 통과한다.
- 근거는 원문 인용으로 남긴다. `job_quote`는 해당 요건 `text` 안에, 프로필 인용은 프로필 원문 안에 있어야 한다.
- 근거를 찾으려고 프로필을 **확인한** 주체(`evidence_checked_by`)와 상태를 정한 주체(`status_decided_by`)는 따로 기록한다. 확인했지만 근거가 없었던 경우(`no_profile_info`)도 확인한 주체를 적는다. 아직 확인하지 않았으면 `null`이다.

**비용 최적화 (후속):** 모든 공고를 평가하되, 1·2·4·5단계는 전부 실행하고 3단계(LLM 근거 찾기)만 필요할 때 실행하는 2단계 구조를 검토한다. 예: `job_mismatch` 그룹은 사용자가 펼칠 때 3단계를 실행한다. 이 계약은 3단계를 생략한 결과도 표현해야 한다: `evidence_checked_by=null`이면 근거가 없고 `status=needs_check`다.

### 13-1. LLM 단계 계약 (1단계 요건 추출, 3단계 근거 찾기)

LLM은 두 곳에서만 쓴다. 두 곳 모두 응답을 **구조화 출력**(정해진 칸의 JSON)으로 받고, 코드가 검증한 뒤에만 쓴다. 판정 규칙(numeric 비교, 점수, 순위)과 `summary`는 프롬프트에 담지 않는다(코드 몫). 모델에 시키지 않는 칸: 요건 `id`(코드가 `R1, R2, …`로 붙인다), `status_decided_by`, `not_met`, `compared`, `extraction_status`.

**호출 단위.** 공고 1건에 요건 추출 1회, 근거 찾기 1회다. 근거 찾기는 `skill`·`qualitative` 요건을 한 번에 묻는다. 요건별 호출은 하지 않는다(무료 한도와 비용). 한 번에 묻는 방식이 인용 정확도를 떨어뜨리는지는 실제 실행 기록(18장)으로 확인한다.

**요건 추출 (1단계)**

| 모델이 내는 칸 | 코드가 확인하는 것 |
|---|---|
| 요건 목록: `level`, `type`, `text`, `combine`, `items`, `numeric_kind`, `min_value`, `max_value`, `career_family`, `career_family_basis`, `min_degree`, `allows_graduating`, `major_names`, `origin`(나눈 요건이면 `split`), `interpretation_note` | `text`는 공고 원문의 일부여야 한다. `items`의 `text`는 요건 `text`의 일부여야 한다. `JobRequirement` 검증(data-contract 2-0)을 통과해야 한다 |
| `extraction_issues` 후보 | 1-4의 허용 값 5종만 받고 나머지는 버린다 |

- 확인에 실패한 요건은 **버리고** `partial_extraction`을 더한다. 일부만 버려도 나머지로 평가를 진행한다(1-4: `incomplete`이어도 멈추지 않는다).
- **경력 기준은 코드가 원문 표현으로 한 번 더 바로잡는다**(5-4). LLM이 `numeric`·`career_years`로 뽑은 요건의 `min_value`·`max_value`가 원문의 정해진 표현과 다르면 코드 값으로 고치고 `interpretation_note`에 남긴다. 이것은 요건을 버리는 것이 아니므로 `partial_extraction`을 붙이지 않는다.
- **버린 이유와 보정은 숫자로 센다**(내용은 기록하지 않는다). 공고마다 뽑은 요건 수, 남긴 수, 버린 수를 이유별로(원문에 없음 / `JobRequirement` 검증 실패), 허용 값 밖의 이슈 후보 수, 코드가 보정한 수를 낸다. 18장의 실행 기록에 들어간다.
- 공고 원문이 비어 있으면 호출하지 않고 `text_unreadable`을 적는다. 호출이나 해석이 통째로 실패하면 요건 없이 `extraction_failed`를 적는다.
- 모델이 `extraction_status`를 보내도 받을 칸이 없어 결과에 영향이 없다. 코드가 최종 `extraction_issues`로 상태를 계산한다.

**근거 찾기 (3단계)**

| 모델이 내는 칸 | 허용 값과 코드 처리 |
|---|---|
| 요건 `id`별 판정 | `status`는 `met` / `needs_check`만 받는다. `not_met`을 내면 4단계가 되돌린다 |
| `reason_code` | `needs_check`이면 3-1의 확인 필요 사유 |
| `profile_evidence` | 경험 `id` 또는 칸 이름 + 프로필 원문 인용. 프로필 근거 검증이 원문과 대조한다 |
| `question_for_user` | `needs_check`일 때의 질문 |
| `any_of` 요건 | 항목(`item_index`)마다 위 칸을 낸다 |

- 모델 출력은 코드가 **원시 딕셔너리**로 `build_result`에 넘기고, 판정 주체는 `ai`로 덮인다(4단계). 모델이 `status_decided_by`에 무엇을 적어도 무시한다.
- **모델이 낸 판정을 코드가 이렇게 다룬다.** `met`에 사유가 있으면 사유를 지운다(`met`은 사유가 없다). **근거 인용이 하나도 없는 `met`은 `needs_check`(`scope_unclear`)로 낮추고** `interpretation_note`에 "근거 인용이 없어 확인 필요로 조정"을 적는다(근거가 불충분하면 `needs_check`, 0-3). `any_of`는 항목마다 같은 처리를 한다. `evidence_checked_by`와 `status_decided_by`는 코드가 `ai`로 적는다.
- **요건과 판정은 1:1이다.** 물은 요건(`skill`·`qualitative`, `level`과 무관)마다 판정이 하나씩 있어야 한다. 빠진 요건, 같은 요건의 판정이 둘, 묻지 않은 요건의 판정, 항목별 결과(`item_results`)가 없는 `any_of` 응답, `any_of`가 아닌데 항목별로 낸 응답, 없는 항목 번호는 모두 단계 실패다. 판정이 스키마 계약을 어기는 조합(예: `needs_check`인데 사유 없음, 근거에 위치가 없음)도 같다.
- **`any_of` 요건에 덧붙은 요건 단위 값은 코드가 버린다 (2026-11-04, 이슈 #7).** `any_of`는 항목별 결과로만 판정하는 것이 계약이다(프롬프트도 요건 단위 `status`·`reason_code`·근거·질문을 비우라고 한다). 모델이 항목별 결과를 제대로 내고 요건 단위 값을 **덧붙이면** 그 값은 쓰지 않고 버린다. 요건 전체의 상태·사유는 5단계가 항목에서 합쳐 정하고(요건 단위 값이 항목과 달라도 항목이 이긴다), 버린 요건 단위 근거 인용은 결과에 들어가지 않으므로 근거 대조의 대상도 아니다. 항목별 결과가 없는 `any_of` 응답은 요건 단위 값이 있든 없든 계속 단계 실패다. 실제 모델(`gemini-3.1-flash-lite`)이 5번 공고의 `any_of` 요건 두 개에서 요건 단위 `status`를 덧붙여 공고 전체가 단계 실패가 된 관찰에서 정했다(18-2). 코드가 항목에서 다시 계산하는 값이라 판정 규칙의 완화가 아니다.
- 근거 찾기가 실패하면(통신, 스키마 위반) 단계 전체가 오류다. 확인하지 못한 요건을 조용히 `needs_check`로 채우지 않는다.

**실패 처리 (공통).** 구조화 출력의 파싱 실패나 스키마 위반은 **다시 묻지 않고** 그 단계 실패로 처리한다(호출 한도 절약). 통신 오류 중 일시적인 것(서버 오류, 네트워크, 분당 제한)만 제한된 횟수로 재시도하고, 일일 한도나 quota 소진은 재시도 없이 멈춘다. 일시적 제한인지 구별할 수 없으면 소진으로 보고 멈춘다. 원시 오류와 모델 출력은 사용자에게 보이지 않는다. 사용자에게는 1-4의 안내 문구만 보인다. 자동으로 다른 모델로 바꿔 다시 부르지 않는다(실패를 숨기고 결과가 모델마다 달라진다).

**모델 지정.** 모델은 환경변수로 **정확한 모델 ID**를 지정한다. `latest`·preview 별칭, 폐지됐거나 폐지 예정인 모델은 쓰지 않는다. 쓴 모델 ID와 확인일은 18장에 기록한다.

## 14. 순위와 표시

- **정렬 순서:** `ranking_group` → `verdict` → 적합성 점수다. 뒤 기준은 앞 기준을 넘지 못한다. 점수가 자격요건 결과를 덮어쓰지 않는다.
  - `ranking_group`: `primary` → `job_mismatch` → `out_of_scope` (맨 아래)
  - `verdict`: `eligible` → `conditional` → `not_eligible`
  - **점수의 범위와 의미는 적합성 평가 정책(fit-evaluation.md)에서 정한다.** 범위(0~100 여부), 정수·실수, 음수 허용, 점수 없음의 의미(아직 계산하지 않음과 계산에 실패함의 구분)가 그 대상이다. 이 코드는 유한한 숫자만 받고 범위를 제한하지 않는다.
  - **적합성 점수가 없으면** (적합성 평가가 아직 없거나 계산하지 않은 공고) 같은 `ranking_group`·`verdict` 안에서 점수가 있는 공고가 먼저 오고, 점수가 없는 공고끼리는 입력 순서를 유지한다. 점수가 같을 때도 입력 순서를 유지한다(안정 정렬). 점수는 높은 쪽이 먼저다.
  - **코드의 입력.** 자격요건 결과 목록, 같은 공고들의 게이트 결과 목록, 점수(`job_id` → 점수, 선택)를 받는다. 점수는 판정 칸이 아니라 정렬에만 쓰는 값이다. 코드는 점수를 계산하지 않는다.
  - **정렬하기 전에 게이트와 맞춰 본다 (data-contract 2-2).** 모든 결과에 같은 `job_id`의 게이트 결과가 있어야 하고, 결과의 `gate_ranking_group`이 게이트 결과의 `ranking_group`과 같아야 한다. 어긋나면 정렬하지 않고 오류를 낸다. 오류에는 `job_id`와 두 값을 적는다.
  - **다음도 오류다.** 같은 `job_id`가 결과나 게이트 결과에 둘 이상 있을 때, 점수의 `job_id`가 결과에 없을 때, 점수가 숫자가 아니거나 유한하지 않을 때(`NaN`, 무한대).
  - 게이트 결과가 있는데 자격요건 결과가 없는 공고는 오류가 아니다. 정렬 대상에서 빠진다.
  - **정렬에서 빠진 공고도 화면과 실행 결과에 남긴다.** 평가를 시도했으나 실패한 공고(`failed`)와 시작하지 못한 공고(`not_run`)는 순위 아래에 "평가하지 못한 공고"로 이유(범주 이름)와 함께 보인다. 공고를 조용히 지우지 않는다 (data-contract 3장).
  - **점수가 없을 때의 동점은 입력 순서를 유지한다. 다른 tie-breaker(`job_id` 순서 등)를 임의로 더하지 않는다.** 그래서 같은 `ranking_group`·`verdict` 안의 순서는 입력 순서에 따라 달라지는 것이 정상이다. 순서를 완전히 결정적으로 만들려면 이 장에 세 번째 기준을 먼저 추가해야 한다.
  - **점수가 없으면 화면과 결과에 점수 칸을 두지 않는다.** 0이나 빈 값을 채워 계산한 것처럼 보이게 하지 않는다.
- `not_eligible` 공고도 **지우지 않는다.** 결정적 요건과 함께 보여 준다. 예: "서비스 기획 경력 6개월 < 36개월(3년)".
- **`job_mismatch`, `out_of_scope` 그룹의 판정은 "참고용 평가"로 표시한다.** 지원 추천이 아니다. 문구 예: "직무가 달라 참고용으로만 평가했습니다". 이 표시는 `reference_only=true`인 공고에 항상 붙는다.
- `primary` 그룹이어도 `display_flag`("직무 범위 차이", "직무 확인 필요")는 게이트 쪽에서 정한 표시 그대로 보여 준다.
- 예: 샘플 3번(`primary`, 조건부 적합)이 1번(`primary`, 필수 요건 미충족)보다 위에 오고, 불일치 4건은 둘 다 아래 그룹에 모인다. 불일치 그룹에서 100점인 공고도 `primary`의 미충족 공고 아래에 놓인다.

## 15. 적합성 평가와의 연결

이 문서는 인터페이스만 정한다. 점수 산식은 [fit-evaluation.md](fit-evaluation.md)에서 정한다.

| fit이 읽는 칸 | 용도 |
|---|---|
| `verdict` | 정렬 기준 (14장). 점수가 바꾸지 않는다 |
| 요건별 `status` | 충족·확인 필요 요건 반영 |
| `needs_check_count` | 불확실성 표시 |
| `level=preferred`인 요건의 결과 | 우대 항목 점수 |

- `type=preference` 요건은 점수에서도 뺀다 (2장).
- 자격요건 `verdict`가 `not_eligible`이어도 fit은 점수를 계산할 수 있다. 순위에서만 `verdict`가 먼저다.

## 16. 개인정보와 저장 범위

- 프로필 원문 인용(`profile_evidence.quote`)은 개인정보다. **실행 결과에만 두고 저장소에 커밋하지 않는다.**
- 실행 결과 저장 위치는 `data/results/`이고 `.gitignore`에 넣는다. 프로필 파일(`data/profiles/`)도 커밋하지 않는다.
- 테스트 fixture는 **가상 프로필(김하늘)만** 쓴다. fixture 머리에 `"_comment": "가상 프로필. 실제 지원자 정보 금지"`를 적는다.
- 외부 LLM으로 프로필을 보낼 때는 [프로젝트 안내](../project-guide.md) 3-2의 "별도 승인" 규칙을 따른다.
- **무료 티어 입력의 데이터 사용.** 무료 티어로 보낸 입력은 공급자가 제품 개선에 쓰고 사람이 읽을 수 있다(2026-11-04 가격 페이지와 약관 확인, 유료는 쓰지 않는다고 표시). 그래서 아래를 지킨다.
  - **보내는 프로필 입력:** 이름·연락처·주소·링크를 빼고 경험(제목·역할·활동·도구·결과), 스킬, 자격증, 학력 원문만 보낸다.
  - **외부로 보내는 데이터는 가상 프로필과 샘플 공고뿐이다.** 외부 클라이언트로 근거 찾기를 부르려면 호출하는 쪽이 허용을 명시해야 하고, 기본은 거부다.
  - **실제 지원자 프로필은 팀의 별도 승인 뒤에도 명시적인 실행 플래그가 있을 때만** 보낸다. 이 정책 버전에서는 실제 프로필 경로를 구현하지 않는다.
  - **프로필이 든 요청·결과는 기본으로 디스크에 남기지 않는다.** 근거 찾기 캐시는 기본이 메모리이고, 가상 프로필 개발용 실행에서 명시했을 때만 `data/results/`에 저장한다. 공고 원문만 든 요건 추출 결과는 디스크 캐시를 쓸 수 있다.
  - **사용량 기록**(`data/results/`)에는 호출 수·토큰·캐시 적중·모델 ID만 남기고 프롬프트와 응답 내용은 쓰지 않는다.
- **pipeline 실행 결과의 프로필 인용 (이슈 #7).** 위의 "프로필이 든 요청·결과는 기본으로 디스크에 남기지 않는다"는 **LLM 요청·응답 캐시**에 대한 규칙이다. pipeline 실행 결과(`pipeline_run.v1`, data-contract 3장)는 사용자가 실행해서 얻는 산출물이지만 프로필이 들어 있으므로 같은 방향으로 닫아 둔다.
  - **기본은 인용을 저장하지 않는다.** 요건 상태·사유·`compared`·`job_quote`만 저장하고 `profile_evidence_included=false`로 표시한다.
  - 인용을 저장하려면 `--save-profile-evidence`를 명시해야 하고, **가상 프로필일 때만** 쓴다. LLM 캐시의 `--cache-profile`과는 별개다.
  - 인용을 뺀 결과 파일도 개인정보로 취급한다(모델이 쓴 `interpretation_note`, `question_for_user`에 프로필 내용이 섞일 수 있다). 어느 경우도 커밋하지 않는다.
  - **선택한 공고를 다음 Agent에 넘기는 파일(`selected_job.v1`)** 은 인용이 있어야 쓸모가 있으므로 `--select`와 `--save-profile-evidence`를 함께 줄 때만 인용을 담는다. 이 파일을 외부 LLM으로 보내는 일은 이 장의 같은 제한을 받는다: 가상 프로필만, 실제 프로필은 팀의 별도 승인과 명시적 실행 플래그 없이는 금지. 받는 쪽이 전달받을 때 다시 확인한다. 자동 삭제는 없고 필요 없어지면 손으로 지운다.
  - **자소서·포트폴리오 초안 (이슈 #14).** 초안 입력(`WriterInput`, 사실에 붙은 경험 내용 `evidence_detail` 포함)은 프로필 내용이 들어 있어 저장하지 않는다. 초안 파일은 가상 프로필이고 `--save-draft`를 줄 때만 `data/results/drafts/`에 쓰며 커밋하지 않는다. 외부 LLM에는 가상 프로필과 샘플 공고만 보낸다. 자세한 규칙은 `application-writing.md` 5장이다.
  - **API 키**는 `.env`에만 두고 코드·로그·예외 메시지·캐시·사용량 기록·이슈·PR에 쓰지 않는다. 결제 계정은 연결하지 않는다.

## 18. 검증 계획

- **샘플 6건 회귀 테스트:** 17장의 요건별 상태로 결과를 만들어 종합 판정이 요약표와 같은지 확인한다 (`tests/test_schemas_eligibility.py`). fixture의 요건별 상태가 17장 표와 같은지도 테스트가 이 문서의 표를 직접 읽어 대조한다. 이 테스트는 종합 판정 계산만 확인하고, 요건별 상태를 만드는 코드는 후속 이슈(`core/rules.py`)에서 검증한다.
- **겹친 경력 합산 테스트 (`core/rules.py` 구현 때 필수):** 경험 A `2025-03 ~ 2025-06`과 경험 B `2025-05 ~ 2025-08`의 합계는 6개월이다(단순 합산은 8개월). 직무군이 같은 경험과 모르는 경험의 합집합(4장), 기준 월에서 자르기(11장)도 함께 확인한다. 합집합 계산은 `core/rules.py` 몫이라 스키마 테스트에는 없다.
- **원티드 60건 자격요건 정답:** 후속. 직무 게이트 정답과 따로 기록한다 ([job-gate.md](job-gate.md) 6-2).
- **검증용 공고에 `eligible`이 나오는 사례를 넣는다.**
- **LLM 단계 실행 기록 (13-1).** 기본 실행은 mock(정답 fixture)이고 네트워크를 쓰지 않는다. 실제 모델 실행은 사용자가 직접, 가상 프로필과 샘플 공고로만 하고, 실행 전에 무료 티어 데이터 사용 조건(16장)을 안내한다. 실행 때마다 아래를 **숫자로만** 기록한다. 공고 원문·프로필 내용·모델 출력 원문은 적지 않는다.
  - 실행일, 모델 ID, 모델 상태 확인일(폐지·preview 여부), 그 시점 AI Studio의 RPM·TPM·RPD 화면 값. 한도 숫자는 문서에 고정하지 않고 실행 때마다 적는다.
  - 호출 수, 입력·출력 토큰, 캐시 적중, 한도 대비 사용량, 결제 없음
  - 요건 수·유형이 17장과 일치하는 공고 수, 요건별 상태·사유 일치 수, 근거 인용 검증 통과 수, 스키마 위반 횟수
  - 모델을 비교했으면 같은 항목을 모델별로 나란히 적는다. 실패와 차이는 원인만 적는다.
- **실행 도구.** `python -m tools.eval_eligibility`가 mock으로 샘플 6건을 돌려 요건별 상태·사유를 17장과 비교한다. 실제 모델 실행은 `--ai --accept-free-tier-terms`로만 하고(동의 플래그 없이는 아무것도 보내지 않는다), 시작 전에 설정·공고 원문 파일·하루 호출 예산(공고 6 + 근거 6 = 12회)을 점검한다. 화면에는 공고 id·요건 id·판정·사유 코드·숫자만 출력하고, 요건 text(fixture의 요약문 포함)·공고 원문·프로필 인용·모델 출력과 오류 내용은 출력하지도 저장하지도 않는다(`-v`에서도 같다). 실패 이유는 정해진 범주 이름으로만 낸다. 모델 비교 실행은 `--fresh-cache`로 앞 실행의 공고 추출 캐시를 쓰지 않는다.
- **정답과 비교하는 방법.** 정답(fixture)의 필수 요건과 모델이 뽑은 필수 요건을 **짝짓는 것이 먼저**다. 순서가 바뀌거나 합쳐져도 엉뚱한 요건끼리 비교하지 않도록, 정답 요건의 요약문과 뽑은 요건의 `text`가 겹치는 정도(공백·문장부호를 뺀 두 글자 조각의 겹침)로 한 쌍씩 맞춘다. 짝이 없는 요건은 `정답에만 있음`, `뽑은 것에만 있음`으로 따로 센다. 짝지은 요건은 필드별로(유형, `numeric_kind`, `min_value`·`max_value`·`career_family`, `min_degree`) 맞는지 보고, 상태·사유도 짝지은 요건끼리만 비교한다. 위치 순서로 비교한 값은 **보조 지표**로만 함께 적는다.
- **모델을 비교하는 조건.** 비교하는 실행은 같은 프롬프트 버전, 같은 입력, 같은 응답 스키마, 같은 생성 설정으로 하고, 캐시를 쓰지 않은(모델마다 새로 시작한) 실행끼리만 비교한다. 생성 설정은 캐시 키와 사용량 기록에 남긴다. 공식 문서가 일부 모델에서 `temperature`·`top_p`·`top_k`를 무시한다고 적고 있어 이 값으로 재현성을 만들지 않는다(기본값을 쓴다). 대신 같은 모델을 **여러 번** 돌려 모델 차이와 실행마다의 변동을 구분하고, 실행마다 따로 적는다(합산하지 않는다). 사용량 기록은 실행 ID별로 센다.
- **pipeline 실행 기록 (이슈 #7).** `python -m tools.run_demo`는 김하늘(가상)과 샘플 6건으로 게이트 → 자격요건 → 정렬을 한 번에 돌리고 `data/results/pipeline/<run_id>.json`에 저장한다(data-contract 3장). 기본은 mock이다. `--ai --accept-free-tier-terms`는 **자격요건 단계만** 실제 모델로 바꾸고 게이트의 AI 자리는 mock으로 둔다(게이트 AI는 이슈 #12). 실행 때마다 아래를 숫자와 상태 이름으로만 기록한다: `run_id`, 모델 ID, 프롬프트 버전, 생성 설정, 캐시 모드와 적중, 입력·출력 토큰, `completed`·`failed`·`not_run` 수, 순위, 종합 판정과 결정적 요건의 기대 일치 수. mock 실행과 AI 실행은 별도 `run_id`로 남기고, 모델을 비교할 때는 위 "모델을 비교하는 조건"(같은 입력, 새 캐시, 같은 생성 설정)을 지킨 실행끼리만 나란히 둔다.
- **pipeline 통합 테스트의 보고.** 항상 도는 *게이트 주입* 테스트(`test_pipeline_with_injected_gate`)와 로컬 입력 파일이 있을 때만 도는 *실제 샘플 입력* 테스트(`test_pipeline_with_real_sample_input`)를 따로 보고하고, 건너뛴 사유를 남긴다. 둘 다 통과하기 전에는 "전체 통합 테스트 통과"라고 쓰지 않는다. 입력 순서를 바꾼 테스트는 전체 순서가 아니라 순서 속성(그룹·판정의 부분 순서, 동점 쌍의 입력 순서 유지)만 확인한다.
- **이 검증의 한계.** mock은 정답을 그대로 돌려주므로 파이프라인 연결과 코드 검증만 보장하고 LLM 품질은 보장하지 않는다. 샘플 6건에 맞춰 프롬프트를 다듬는 것은 시연 범위의 한계이고, 일반 공고에서의 정확도는 별도로 점검한다.

### 18-2. pipeline 실행 기록 (2026-11-04, 이슈 #7)

`python -m tools.run_demo --ai --accept-free-tier-terms --fresh-cache`로 가상 프로필(김하늘)과 샘플 6건을 게이트 → 자격요건 → 정렬까지 돌렸다. **게이트는 규칙 + mock AI 자리**(정답 항목 라벨)이고 **자격요건 단계만 실제 모델**이다. 공고 원문·프로필 내용·모델 출력은 적지 않는다. 비교 방법은 18-1과 같다(정답 필수 요건과 텍스트 겹침으로 짝지은 뒤 짝지은 요건만 비교).

**조건.** 모델 `gemini-3.1-flash-lite`(모델 상태·폐지 일정은 18-1 확인과 같다), 요건 추출 프롬프트 version 2, 근거 찾기 프롬프트 version 1, 생성 설정 `a3ea338a`, 캐시는 실행마다 새로 시작(`cache_mode=fresh`), AI Studio 한도 RPM 15 / TPM 250K / RPD 500(사용자 확인, 18-1과 같음), 결제 계정 미연결(사용자 확인). 두 실행 사이에 **코드가 한 가지 바뀌었다**(아래 5번 실패 원인과 13-1). 그래서 두 열은 "같은 조건의 반복"이 아니라 **수정 전과 수정 후**다.

**실행 A에서 5번이 실패한 구체적 원인.** 서버 오류가 아니다(5번의 두 호출 모두 성공했고 토큰이 기록됐다). 모델이 `any_of` 요건(R3 기술 6개 항목, R5 정성 2개 항목)을 **항목별 결과(`item_results`)와 함께 요건 단위 `status`까지 채워서** 답했고, 당시 코드는 `any_of` 요건에 요건 단위 `status`가 있으면 계약 위반으로 단계 실패를 냈다(프롬프트는 요건 단위 값을 비우라고 한다). 판정 누락·중복·묻지 않은 요건은 없었고 요건 id는 묻은 4개와 같았다. 진단으로 5번의 근거 찾기만 두 번 더 불렀고(요건 추출은 캐시) 두 번 모두 같은 종류로 재현됐다(걸린 요건이 R5, R3로 달랐다). **조치(13-1, 이슈 #7):** 항목별 결과가 있으면 덧붙은 요건 단위 값은 코드가 버리고 항목에서 합친다. 항목별 결과가 없으면 계속 단계 실패다. 실행 B는 이 수정 뒤의 첫 실행이고 5번을 포함해 6건이 모두 완료됐다. 진단 호출 2회를 합친 이날 `gemini-3.1-flash-lite` 호출은 28회(한도의 5.6%)다.

**읽는 법과 관찰.**

- **완료 조건(3번 1순위, 1번 2순위, 불일치는 참고용으로 아래)은 실제 모델에서도 충족됐다.** 종합 판정과 결정적 요건은 실행 B에서 6건 모두 정답과 같고 mock과 같은 순위가 나왔다. 단 게이트는 mock이라 이 결과는 "게이트 정답이 주어졌을 때 자격요건 단계가 맞는가"를 본 것이다.
- **한 공고의 실패가 전체를 막지 않았다.** 실행 A에서 5번만 `failed(stage_failed)`로 남고 나머지 5건이 정렬됐다. 화면과 결과 파일에 5번이 "평가하지 못한 공고"로 남았다 (정책 14장, data-contract 3장).
- **실행 A와 B의 숫자 차이를 모델이나 수정의 효과로 읽지 않는다.** 코드 수정은 5번의 완료 여부에만 영향을 준다. 나머지 차이(2번의 요건 수: A는 1개로 `incomplete`, B는 `complete`, 사유 일치 6/11과 14/18 등)는 모델의 실행 간 변동이다(18-1의 관찰과 같다: 같은 모델도 실행마다 다르다). 한 번씩의 실행이라 변동의 크기는 잴 수 없다.
- **한계.** 샘플 6건, 실행마다 한 번, 게이트 mock. 프롬프트는 이번에 고치지 않았다. 일반 공고에서의 정확도와 실제 게이트 AI는 각각 이슈 #8과 #12에서 본다.
