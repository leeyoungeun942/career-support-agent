# 발표용 통합 실행 정책: 모델 역할(JUDGE / WRITER), 한 명령 시연, 공고 선택

> 이슈 #24, #28. 코드: `tools/run_presentation.py`. 결과 형식과 단계별 규칙은 이 문서가 정하고, 각 단계의 판정 규칙은 [직무 게이트](job-gate.md), [자격요건 평가](eligibility.md), [자기소개서·포트폴리오 초안](application-writing.md) 문서가 정한다. 이 문서는 그 단계들을 **어떤 순서로, 어떤 모델로, 실패하면 어떻게** 잇는지만 정한다.

## 0. 이 문서가 정하는 것

- 모델 역할 두 가지(JUDGE, WRITER)와 작업별 배정, 설정 이름 (1장)
- 발표 시나리오의 입력과 사용자 공고 선택 (2장)
- 실행 순서, 단계 상태, 선행 조건 (3장)
- 실패 처리와 종료 코드 (4장)
- 모델별 호출 예산 (5장)
- 저장, 식별자, 사용량 기록 칸, 개인정보 (6장)
- 실제 AI 실행의 합격선 (7장)
- 화면 요약 (8장)

**이 문서가 정하지 않는 것:** 모델 비교 실험(JUDGE 후보, WRITER 후보 선정, 개발셋 평가). #24가 성공한 뒤의 별도 작업이다. 새 저장 형식(요약 JSON)도 만들지 않는다.

## 1. 모델 역할

| 역할 | 하는 일 | 호출하는 단계(LLM 단계명, `LLMRequest.stage`) |
|---|---|---|
| **JUDGE** (판정 모델) | 직무 게이트, 자격요건 평가. 구조화된 JSON 응답 | `gate_label`, `extract_requirements`, `find_evidence` |
| **WRITER** (생성 모델) | 자기소개서, 포트폴리오. 업무 연결 후보 | `write_cover_letter`, `write_portfolio`, (`--task-links ai`일 때) 연결 후보 단계 |

- **JUDGE는 SMALL이라 부르지 않는다.** 이 저장소에는 "SMALL"이라는 이름이 없다(이슈 본문 일부에 남은 표현은 JUDGE로 읽는다).
- **판정·점수·순위는 모델이 아니라 코드가 한다.** JUDGE는 정해진 라벨, 요건 목록, 근거 후보를 낼 뿐이고 종합 판정, 사유 코드, 순위 그룹, 정렬은 `core/rules.py`와 파이프라인 코드가 정한다 (AGENTS.md). WRITER는 코드가 분류한 `usable_facts`로 문장만 쓰고, 프로필에 없는 사실이나 미충족 요건을 판단하지 않는다 (application-writing.md 1장).
- **게이트와 자격요건은 같은 JUDGE 모델을 쓴다.** 두 단계가 같은 모델의 일일 한도를 나눠 쓰고 시작 전 점검이 그 모델 하나로 합산하기 때문이다 (data-contract 3-1, `run_pipeline`이 다른 모델이면 거부).
- **자동 fallback은 없다.** WRITER 호출이 실패해도 JUDGE 모델로 다시 부르지 않고, 반대도 마찬가지다. 모델을 바꾸는 것은 사람이 설정으로만 한다.

**설정.** 키는 `GEMINI_API_KEY` 하나다.

| 설정 | 뜻 | 비어 있을 때 |
|---|---|---|
| `GEMINI_MODEL_JUDGE` | JUDGE 모델의 정확한 ID | `GEMINI_MODEL` |
| `GEMINI_MODEL_WRITER` | WRITER 모델의 정확한 ID | `GEMINI_MODEL` |
| `GEMINI_RPM_JUDGE`, `GEMINI_RPD_JUDGE` | JUDGE 모델의 분당·일일 한도 | `GEMINI_RPM`, `GEMINI_RPD` |
| `GEMINI_RPM_WRITER`, `GEMINI_RPD_WRITER` | WRITER 모델의 분당·일일 한도 | `GEMINI_RPM`, `GEMINI_RPD` |

- 명령줄은 `--model-judge`, `--model-writer`가 `.env` 값을 덮어쓴다.
- 역할 변수가 없으면 지금까지처럼 `GEMINI_MODEL` 하나로 동작한다. 그때 JUDGE와 WRITER는 **같은 모델**이고 화면에 그렇게 표시한다.
- 정확한 모델 ID만 쓴다(`latest`·preview 별칭, 폐지됐거나 폐지 예정인 모델 금지). 한도는 모델마다 다르므로 실행 때마다 AI Studio의 Rate Limit 화면 값으로 맞춘다 (eligibility.md 18-1).
- **이 문서는 모델을 정하지 않는다.** WRITER 후보 선정은 모델 비교 뒤 사용자가 정한다.

## 2. 발표 시나리오와 공고 선택

| 항목 | 값 |
|---|---|
| 프로필 | 김하늘(가상 프로필) |
| 공고 | 샘플 6건 (`sample-1` ~ `sample-6`) |
| 선택 공고 | **평가와 저장이 끝난 뒤 사용자가 공고 번호(숫자)로 고른다.** 자동 선택은 없다 (결정 D14, 2-1) |
| 생성물 | 자기소개서 + 포트폴리오 |
| 업무 연결 후보 | `--task-links` 기본(자동): 선택이 `sample-3`이면 사람이 확정한 합성 고정본(`fixture`, application-writing.md 결정 D18), 그 외 공고는 `--ai`에서 AI가 만든다(WRITER 1회). `fixture`를 명시하면 후보가 `sample-3`뿐이고, `none`은 연결 후보 없음, `ai`는 `--ai`일 때만 |
| 시나리오 이름 | `--scenario full-ai-demo` (선택지는 이것 하나) |

**자동 대체를 하지 않는다.** 사용자가 입력하지 못했거나(입력 없음, 잘못된 입력 3회) 후보가 없으면 다른 공고로 바꾸지 않고 사유를 보이고 멈춘다. 자동으로 고르면 실행마다 결과가 달라지고 왜 그 공고인지 설명하기 어렵다.

**모든 공고에 자기소개서를 만들지 않는다.** 평가는 6건 모두 하고, 초안은 선택한 1건에만 만든다.

### 2-1. 선택 후보와 입력 규칙

- **후보.** `run_presentation`이 따로 계산한다: `evaluation_status == "completed"`이고 `gate.ranking_group == "primary"`(직무 일치 상위 그룹)인 공고, 최종 순위 순서. 자격요건 미충족은 후보에서 빼지 않고 상태를 표시한 뒤 선택할 수 있다(점수가 자격요건을 덮어쓰지 않는다. `select_job`의 기존 계약과 같다). 직무 불일치(참고용) 공고와 평가를 마치지 못한 공고는 후보가 아니다. 실제 선택 검증과 `SelectedJob` 생성은 기존 `select_job()`이 하며 `core/selection.py`는 바꾸지 않는다.
- **mock.** 초안 문장과 연결 후보 고정본이 `sample-3`에만 있으므로 mock의 후보는 `sample-3`뿐이다. 화면에 제한 이유를 한 줄 보인다. 후보가 `fixture` 명시 때문에 `sample-3`으로 줄어드는 경우도 같다.
- **후보 줄.** `1위 [sample-3] 3번 이씨이십일알앤씨(주) — 조건부 적합`: 순위, 공고 ID, 입력할 번호, 표시명, 자격요건 상태(요약 화면과 같은 함수가 `EligibilityResult`에서 계산). 질문은 `자소서/포트폴리오 초안을 생성할 공고 번호를 입력해주세요.` 다음 줄 `공고 번호만 입력하세요 (예: 3):`다.
- **입력 규칙.** 숫자만 받는다(`3` → 공고의 번호 3 → `sample-3`). `sample-3` 같은 ID 문자열, 빈 입력, 숫자가 아닌 입력, 후보에 없는 숫자는 거부하고 다시 묻는다. **3회 실패하면 종료 코드 4**(사유 코드 `invalid_input`). 번호와 `job_id`의 대응은 공고의 번호(`number`)로 하며 번호가 겹치면 시작하지 않는다.
- **입력 환경별 동작.**

| 조건 | 동작 |
|---|---|
| 대화형(터미널) | 질문 후 입력을 기다린다 |
| 파이프 입력 (`echo 3 \| python -m tools.run_presentation ...`) | 한 줄을 읽어 같은 규칙으로 처리한다 |
| 입력 없음(입력 끝, EOF) | 다시 묻지 않고 종료 코드 4 (`no_input`) |
| 후보 없음 | 질문 없이 `상위 직무 매칭 공고가 없습니다.`를 보이고 종료 코드 4 (`no_candidate`) |

- **기본값은 없다.** Enter(빈 입력)도 잘못된 입력으로 센다. `-q`에서도 후보 목록과 질문은 낸다(선택에 필요하다).
- **다른 공고 선택의 검증 상태.** `sample-3` 외 공고로 연결 후보→`WriterInput`→자소서→포트폴리오→코드 검증까지 실제 AI로 확인하기 전에는 **미검증**이다. 확인한 뒤 10장에 결과를 기록한다. 초안 품질의 합격선은 7장을 따른다.
- 공고 ID는 화면과 결과에 그대로 남는다. 새 저장 형식은 만들지 않는다.

## 3. 실행 순서와 단계 상태

| 번호 | 단계 | 하는 일 | 모델 |
|---|---|---|---|
| 1 | `scenario` | 시나리오 고정, `demo_run_id` 생성, 입력 파일 대응 확인 | - |
| 2 | `budget` | 모델별 호출 예산 점검 (5장). 모자라면 **첫 호출 전에** 종료 | - |
| 3 | `pipeline` | 게이트 → 자격요건 → 코드 판정·순위 (`run_pipeline`) | JUDGE |
| 4 | `persistence` | `PipelineRun` 저장(프로필 인용 제외)과 재로딩 검증 | - |
| 5 | `selection` | 후보 목록을 보이고(2-1) 사용자가 고른 공고를 메모리 원본에서 선택 | - |
| 6 | `writer_input` | `WriterInput` 생성 (코드가 사실 분류) | - |
| 7 | `cover_letter` | 자기소개서 | WRITER |
| 8 | `portfolio` | 포트폴리오 | WRITER |

단계 상태는 `completed` / `failed` / `not_run`이다 ([데이터 계약](../data-contract.md) 3-3과 같은 말).

**선행 조건.**

- **`persistence`가 `completed`(저장 성공 + 재로딩 검증 성공)여야 `selection` 이후로 간다.** 발표 결과의 근거 기록이 없는 채로 초안을 만들지 않는다. 실패하면 `selection` 이후 단계는 `not_run`이고 Writer를 한 번도 부르지 않는다.
- `selection`이 `completed`(사용자가 후보에서 고른 공고를 `select_job`이 받아들임)여야 `writer_input`으로 간다. `writer_input`이 `completed`여야 두 Writer 단계를 시작한다.
- **`cover_letter`와 `portfolio`는 서로 독립이다.** 하나가 실패해도 다른 하나는 시작하고, 실패한 쪽의 결과를 성공한 쪽에 섞지 않는다. 포트폴리오 실패가 순위(`pipeline`)나 자기소개서를 지우지 않는다. 예외: 한도 소진은 남은 Writer 단계를 `not_run`으로 둔다.
- `pipeline`에서 어떤 공고가 `failed`여도 후보(2-1)가 있으면 이어 간다. 선택하지 않은 공고의 실패는 선택을 막지 않는다.

### 3-1. 진행 알림 (`run_pipeline`의 `on_progress`)

실행 중 화면에 공고별 진행을 보이기 위해 `run_pipeline`에 선택 인자 `on_progress`를 둔다. 인자가 없으면 동작과 결과(`PipelineRun`)가 지금과 같다.

- **콜백 형태.** `on_progress(stage, done, total, job_id, status)`. `stage`는 `"gate"` 또는 `"eligibility"`, `total`은 입력 공고 전체 수, `done`은 그 단계에서 처리가 끝난 순번(1부터, 입력 순서), `status`는 `completed` / `failed` / `not_run`.
- **파이프라인 구조.** 게이트를 모든 공고에 먼저 돌리고 그다음 자격요건을 모든 공고에 돌린다. 그래서 알림은 단계별이다(공고 한 건이 두 번 알려진다).
- **AI 게이트 실행.** 게이트 알림이 **모든 공고**에 나온다. 입력 오류로 끝난 공고는 `failed`, 한도 소진으로 게이트를 시작하지 못한 공고는 `not_run`이다.
- **주입 게이트 실행**(mock의 fixture 게이트)은 게이트 호출이 없으므로 게이트 알림이 전혀 없다. 주입 게이트와 AI 게이트는 섞을 수 없다.
- **자격요건 단계**는 `completed`·`failed`·`not_run` 모두 알린다. 한도 소진으로 시작하지 못한 공고(게이트 단계에서 이미 소진된 경우 포함)도 `not_run`으로 알린다.
- 알림에는 공고 ID와 상태, 개수만 있다. 원문, 프로필, 모델 출력은 없다. 콜백이 낸 예외는 잡지 않고 그대로 올린다(코드 결함을 숨기지 않는다). 콜백은 결과를 바꾸지 못한다.

## 4. 실패 처리와 종료 코드

| 상황 | 단계 상태 | 종료 코드 |
|---|---|---|
| 모두 완료 | 전부 `completed` | 0 |
| 끝까지 갔지만 실패 단계가 있음: 다른 공고의 `failed`, 한쪽 초안 실패(`DraftError`, `LLMStageError`), **초안 생성은 성공했으나 확인용 md 저장이 실패** | 해당 단계 `failed` 또는 `completed(saved=False)` | 1 |
| 시작하지 않음: 동의 없음, 설정·키 오류, 입력 파일 없음·어긋남, 호출 예산 부족 | 단계 `budget` 등 `failed`, 이후 `not_run`, 호출 0회 | 2 |
| 호출 한도 소진으로 멈춤 (평가가 한도 때문에 멈춰 선택 후보가 없어도 3) | `LLMQuotaExceeded` 단계 `failed`, 남은 단계 `not_run` | 3 |
| 한도와 무관한 시연 중단: 공고 선택 실패(`selection_failed`: 사유 코드 `no_candidate`, `no_input`, `invalid_input`, 또는 선택한 공고를 `select_job`이 거부한 경우의 `gate_failed`, `stage_failed` 등) 또는 저장·재로딩 검증 실패(`persistence_failed`) | 해당 단계 `failed`, 이후 `not_run` | 4 |

- **초안 생성 성공 + md 저장 실패**는 그 초안 단계를 `completed`로 두되 `saved=False`로 표시하고 화면에 "생성 성공, 저장 실패"로 구분한다. 생성한 초안은 메모리(`PresentationResult`)에 남고, 다른 초안과 순위는 영향이 없다.
- **잡지 않는 예외:** `PermissionError`(외부 클라이언트에 허용 없이 프로필을 보냄), `LLMConfigError`(키·설정), `TypeError`·`KeyError` 같은 코드 결함은 단계 실패로 바꾸지 않고 그대로 올린다 (`except Exception` 금지, #7 리뷰에서 확정한 원칙).
- 실패한 섹션이나 단계를 임의의 문장·값으로 채우지 않는다. 원시 오류와 모델 출력은 화면에 보이지 않는다.

## 5. 호출 예산

일일 한도는 **모델마다** 따로다. 시작 전 점검은 **모델 ID별로** 그 모델의 최대 시도 수를 합쳐 각각 오늘 남은 한도(`calls_today(model)` 기준)와 비교하고, 어느 한 모델이라도 모자라면 **아무것도 호출하기 전에** 종료한다(종료 코드 2). 최대 시도 수 = 논리 호출 × (1 + 재시도 상한 3). 재시도와 실패한 시도도 한도를 쓴다.

| 단계 | 논리 호출 | 최대 시도 | 모델 |
|---|---|---|---|
| 직무 게이트 | 최대 21 (샘플 6건, 입력 파일에서 계산, job-gate.md 5-2) | 84 | JUDGE |
| 자격요건 | 12 (공고 6 × 요건 추출 1 + 근거 찾기 1) | 48 | JUDGE |
| 업무 연결 후보 (`--ai`는 **항상 포함**: 어떤 공고가 선택될지 호출 전에 알 수 없다) | 1 | 4 | WRITER |
| 자기소개서 | 1 | 4 | WRITER |
| 포트폴리오 | 1 | 4 | WRITER |

- **같은 모델이면 합쳐서 한 번 점검한다:** 144(= 84 + 48 + 4 + 4 + 4). 선택이 `sample-3`이고 고정본을 쓰면 실제 최대 시도는 140이지만 점검은 144로 한다.
- **다른 모델이면 따로 점검한다:** JUDGE 132, WRITER 12(자소서 4 + 포트폴리오 4 + 연결 후보 4). 고정본만 쓰는 경우의 실제 최대 8은 점검에 쓰지 않는다.
- 정상 실행의 실제 호출은 게이트 21 + 자격요건 12 + 자소서 1 + 포트폴리오 1 = 약 35회다(`sample-3` 외 공고를 고르면 연결 후보 1회가 더 든다). 최대치로 점검하므로 이미 많이 쓴 날은 보수적으로 멈춘다. 캐시가 있어도 점검 값은 줄이지 않는다(캐시 적중은 한도를 쓰지 않지만 실행 전에는 알 수 없다).

### 5-1. 호출 수 세는 법과 공고당 호출 구조

세 가지를 섞지 않는다. **논리 호출**: 서로 다른 (단계, 요청) 개수. **시도**: 캐시 미적중 행 수로, 재시도와 실패한 시도를 포함한다. **캐시 적중**: 캐시가 대신 답한 호출(한도를 쓰지 않는다). 재시도 수 = 시도 − 논리 호출. 사용량 기록의 `cached`, `ok` 칸으로 가른다. 아래 숫자는 공고 원문 없이 개수만 적는다.

**호출이 생기는 구조.**

- **게이트(`gate_label`).** 공고의 업무 항목을 하위 업무로 나누고, 규칙(사전)이 정하지 못한 하위 업무마다 AI를 1회 부른다(요청 ID `sample-N:item:i:subtask:j`). 한 항목의 하위 업무 수가 짝수이고 '공통이 아닌' 하위 업무가 정확히 절반이면 항목 단위 호출이 1회 더 생긴다(`sample-N:item:i`). 그래서 공고마다 호출 수가 다르다.
- **자격요건.** 공고당 요건 추출(`extract_requirements`) 1회, 근거 찾기(`find_evidence`)는 skill·qualitative 요건이 있을 때만 1회다(요건이 모두 경력·자격증처럼 코드가 계산하는 종류이면 0회).

**표 A. 샘플 6건의 게이트 구조** (mock 기준. AI가 실제로 다른 라벨을 고르면 항목 단위 호출이 최대치까지 늘 수 있다)

| 공고 | 항목 | 하위 업무 | 규칙이 확정 | AI를 부르는 하위 업무 (= mock 논리 호출) | 최대 논리 호출 |
|---|---|---|---|---|---|
| sample-1 | 4 | 16 | 7 | 9 | 10 |
| sample-2 | 6 | 6 | 3 | 3 | 3 |
| sample-3 | 5 | 5 | 3 | 2 | 2 |
| sample-4 | 2 | 2 | 1 | 1 | 1 |
| sample-5 | 2 | 2 | 0 | 2 | 2 |
| sample-6 | 6 | 6 | 3 | 3 | 3 |
| 합계 | 25 | 37 | 17 | 20 | 21 |

`sample-1`이 많은 것은 항목 하나에 하위 업무가 4~5개씩 있기 때문이다. 예산의 게이트 논리 호출 21은 이 최대 합계다.

**표 B. 실제 AI 리허설의 호출** (`logical / attempts / cache_hits`, 재시도 = attempts − logical)

| 공고 | 게이트 실행 1 | 게이트 실행 2 | 요건 추출 (두 실행 모두) | 근거 찾기 (두 실행 모두) |
|---|---|---|---|---|
| sample-1 | 10 / 11 / 0 (재시도 1) | 10 / 10 / 0 | 1 / 1 / 0 | 1 / 1 / 0 |
| sample-2 | 3 / 3 / 0 | 3 / 3 / 0 | 1 / 1 / 0 | 0 (skill·qualitative 요건 없음) |
| sample-3 | 2 / 2 / 0 | 2 / 2 / 0 | 1 / 1 / 0 | 1 / 1 / 0 |
| sample-4 | 1 / 1 / 0 | 1 / 1 / 0 | 1 / 1 / 0 | 1 / 1 / 0 |
| sample-5 | 2 / 3 / 0 (재시도 1) | 2 / 2 / 0 | 1 / 1 / 0 | 1 / 1 / 0 |
| sample-6 | 3 / 3 / 0 | 3 / 3 / 0 | 1 / 1 / 0 | 1 / 1 / 0 |
| 합계 | 21 / 23 / 0 | 21 / 21 / 0 | 6 / 6 / 0 | 5 / 5 / 0 |

- `sample-1`의 논리 호출 10은 표 A의 9에 항목 단위 호출 1회를 더한 값이다(AI가 한 항목의 하위 업무를 정확히 절반으로 나눈 경우).
- 실행 1의 재시도 2회는 모두 서버 오류 503(한 번씩 다시 불러 성공)이다. 실행 2는 재시도가 없었다.
- 실행 2에도 캐시 적중이 0인 것은 실행 1이 `--fresh-cache`로 새 캐시 폴더에 썼기 때문이다. 실행 2가 기본 캐시 폴더(`llm_cache/gate`, `llm_cache/extract`)를 처음 채웠다.
- 단계별 소요(각 단계의 첫·마지막 기록 시각): 실행 1 게이트 약 5분 9초(시도당 약 13초), 자격요건 약 3분 31초(시도당 약 19초). 실행 2 게이트 약 3분 50초(시도당 약 11초), 자격요건 약 2분 13초(시도당 약 12초). 분당 한도 15회가 만드는 최소 간격은 4초이므로 시간은 한도 대기보다 모델 응답 시간이 더 크다.

**공고 수에 따른 증가.** 공고 N건이고 공고당 게이트 논리 호출이 평균 g(이 샘플: 3.5, 범위 1~10), 자격요건 호출이 공고당 1~2(평균 1.8)이면, 실제 호출은 약 (g + 1.8) × N + 초안 2~3회다. 시작 전 점검(5장의 최대 시도)은 4 × (게이트 최대 논리 + 2N) + 12 ≈ 22N + 12다. 하루 한도 500에서 새 날에 시작을 허락하는 공고 수는 대략 22건, 실제 소비로는 대략 90건이다(재시도를 뺀 추정). 시간은 시도당 약 11~19초로 공고 1건에 약 1분이 든다.

### 5-2. 시연 절차와 캐시

캐시 규칙은 기존과 같다 (D10, eligibility.md 16장). **공고만 든 요청**(게이트, 요건 추출)은 디스크에 캐시되고(`llm_cache/gate`, `llm_cache/extract`), **프로필이 든 요청**(근거 찾기, 자소서·포트폴리오·연결 후보)은 기본으로 메모리에만 있어 실행마다 다시 부른다. 키는 모델·생성 설정·프롬프트 버전·단계·프롬프트·스키마의 해시이므로 모델이나 프롬프트 버전이 바뀌면 적중하지 않는다. JUDGE 모델의 캐시는 WRITER 모델을 바꿔도 그대로 쓰인다.

| 실행 | 방법 | 예상 호출(시도) | 예상 소요 |
|---|---|---|---|
| ① 리허설 | 기본(`--fresh-cache` 없음)으로 한 번 실행해 캐시를 채운다 | 약 35 (게이트 21 + 요건 추출 6 + 근거 찾기 5 + 초안 2~3) | 약 6~9분 (실측 6.5분, 9.0분) |
| ② 시연 | ①과 같은 모델·프롬프트·입력으로 다시 실행 | 7 (근거 찾기 5 + 초안 2). 게이트 21과 요건 추출 6은 캐시 적중 (실측 7회 일치) | 약 35초 (실측. 10장 실행 A) |
| ③ 재생 | `--cache-profile`로 실행해 프로필 요청까지 저장한 뒤 다시 실행. 가상 프로필일 때만 쓴다. **저장하는 실행이 실패 없이(`완료 6, 실패 0`) 끝났을 때만** 재생한다 | 0 (모두 캐시 적중, 실측 0회) | 1초 안팎 (실측. 10장 실행 C2) |

- **캐시에는 응답이 검증을 통과하기 전에 저장될 수 있다.** 캐시는 응답의 스키마만 확인한 뒤 저장하고, 단계 코드의 의미 검증(예: 요건 누락, `any_of` 요건의 항목별 판정 누락)은 그 뒤에 한다. 그래서 모델이 검증에 실패하는 응답을 한 번 내면 그 응답이 저장되어 **다음 실행에서도 같은 실패가 재생된다**(10장 실행 C1·C2의 `sample-5`). 재생이 실패(`완료 6, 실패 0`이 아님)로 끝나면 해당 캐시 폴더(프로필 요청은 `llm_cache/profile`)를 지우고 다시 실행한다. 이 동작을 고치는 것은 이슈 #28의 범위 밖이다.
- `--fresh-cache`는 처음부터 다시 부르고 싶을 때만 쓴다. 쓰면 ②의 이점이 없다.
- ③은 실제 모델 호출이 아니라 **저장된 응답의 재생**이다. 요약의 캐시 적중 숫자로 정직하게 보이고, 발표에서 그렇게 말해야 한다.
- 선택 질문(2-1)은 ①②③ 모두에서 나온다. 입력은 파이프(`echo 3 | python -m tools.run_presentation ...`)로 줄 수 있다.
- 이슈 #28에서 **하지 않은 것**(호출을 줄이는 코드 변경)과 그 후보는 `docs/youngeun/call-efficiency-report.md`(커밋하지 않는 파일)에 있다.

## 6. 저장, 식별자, 사용량 기록, 개인정보

**저장.**

- **`WriterInput`은 디스크에 저장하지 않는다.** 프로필 내용이 들어 있어 같은 프로세스 안에서만 넘긴다 (application-writing.md 5장).
- **`PipelineRun`은 기존 규칙대로** `data/results/pipeline/<pipeline_run_id>.json`에 프로필 인용을 뺀 채 저장한다 (eligibility.md 16장, data-contract 3-4). 저장 직후 다시 읽어 저장본과 같은지 검증한다.
- **선택과 `WriterInput`은 저장본이 아니라 메모리 원본에서 만든다.** 저장본은 프로필 인용이 없어 `WriterInput`의 사실 분류를 만들 수 없다.
- 초안은 기본으로 저장하지 않는다. 실제 AI 초안은 확인용 md를 항상 쓴다(application-writing.md 결정 D13). json은 쓰지 않는다. 모든 파일은 커밋하지 않는다.
- 이 문서가 새로 정하는 저장 형식은 없다. 단계 요약은 화면과 실행 결과 객체(메모리)에만 있다.

**식별자.**

- **`demo_run_id`**: 한 번의 시연 실행 ID. **사용량 기록(`llm_usage.jsonl`)의 `run_id`로 쓴다.** 그래서 JUDGE·WRITER 호출이 모두 같은 `run_id`로 묶인다.
- **`pipeline_run_id`**: **`save_run`이 돌려준 저장본의 `run_id`**. 같은 이름의 파일이 있으면 `save_run`이 새 `run_id`를 뽑으므로 저장 전 값과 다를 수 있다. 메모리 원본의 `run_id`를 이 값으로 맞춘 뒤 선택해서, 선택 결과, `WriterInput` 메타, 초안 파일명, 화면의 ID가 저장 파일과 같게 한다.
- 둘은 별개의 ID다. 화면에 나란히 보인다.

**사용량 기록 칸** (eligibility.md 16장의 "호출 수·토큰·캐시 적중·모델 ID만" 원칙 유지):

| 칸 | 뜻 |
|---|---|
| `task` | 작업 종류. `gate_label` → `gate`, `extract_requirements`·`find_evidence` → `eligibility`, 초안·연결 후보 단계 → `writer`, 그 밖 → `other` |
| `model` | **요청한 모델 ID** (지금까지와 같은 칸, 이름은 바꾸지 않는다. 일일 한도 계산 `calls_today(model)`의 키) |
| `model_actual` | 응답이 알려 준 실제 모델(SDK의 `model_version`). 모르면 비워 둔다(화면에 "알 수 없음"). 요청과 다르면 화면에 `(불일치)`를 붙여 보이되 자동으로 바꾸지 않는다 |

이전 기록(새 칸이 없는 줄)도 그대로 읽힌다. 프롬프트·응답·`reason`은 기록하지 않는다.

**개인정보.** 외부로 나가는 것은 **공고 정보와 가상 프로필(김하늘)뿐**이다. 무료 티어 입력은 공급자가 제품 개선에 쓰고 사람이 읽을 수 있다 (eligibility.md 16장). 실제 지원자 프로필은 보내지 않고 `--real-profile`은 구현하지 않는다. 입력 파일(`--postings`, `--gate-cases`)은 기본 경로의 샘플 파일을 쓰며, 코드는 샘플 6건의 ID와 직무명이 맞는지만 확인하고 내용이 샘플인지는 검증하지 않는다. 다른 파일을 넘기지 않는 것은 사용자의 책임이다. 화면과 저장 파일에 공고 원문, 게이트 입력, 프로필 인용 원문, 모델 출력, `reason`, 오류 내용이 없다. 키는 `.env`에만 두고 결제 계정은 연결하지 않는다.

## 7. 실제 AI 실행의 합격선

- **합격선:** 사용자가 고른 공고(발표의 기본 흐름은 `sample-3`)가 `completed`이고, 코드가 순위를 만들었고(`PipelineRun`의 `rank` 검증 통과), Writer 단계로 진행했다.
- **전체 순위 `3, 1, 4, 5, 2, 6`은 mock dry-run의 회귀 기준일 뿐이다.** 실제 모델은 실행마다 다르므로(eligibility.md 18-1·18-3) 실제 AI의 순위는 **관찰 결과**로 기록한다. 기대 순위와 다르면 실패가 아니라 차이로 기록하고, 화면에는 "참고: 정책 14장 기대 순위와 같음/다름"만 보인다. 종료 코드에는 영향이 없다.
- 순위가 달라지면 기대표와의 공고별 대조표(eligibility.md 18-3 방식)로 어느 열(게이트, 자격요건, 순위)에서 처음 갈렸는지만 적는다. 정답·정책·프롬프트를 실행 결과에 맞춰 고치지 않는다.
- 초안의 문장 품질은 코드가 판정하지 않는다. 사람이 확인용 md를 읽고 판단하며, 코드 검증이 보장하는 범위와 한계는 application-writing.md 3장을 따른다.

## 8. 화면 요약

**진행 줄.** 실행 중에는 단계가 시작하고 끝날 때마다 한 줄씩 바로 출력한다(`-q`에서는 내지 않는다). 시연에서 호출이 끝날 때까지 빈 화면이 이어지지 않게 하기 위해서다. 진행 줄은 고정 문구, 단계 상태, 개수, 상태 코드만 담고 모델 출력, 공고 원문, 프로필 내용, 오류 내용은 담지 않는다. 한 줄은 `[번호] 단계 이름: 시작` 또는 `[번호] 단계 이름: 완료|실패 (코드)` 꼴이고, 호출이 오래 걸리는 단계(게이트·자격요건, 초안 생성)는 시작 줄에 "수 분 걸릴 수 있음"을 적는다. 진행 줄은 요약의 일부가 아니므로 실행이 끝난 뒤의 요약 내용과 종료 코드는 바뀌지 않는다. 3-1의 공고별 진행 줄은 `[1~3] 게이트 2/6: sample-2 (완료)`, `[1~3] 자격요건 2/6: sample-2 (완료)` 꼴이다. 공고 한 건 안의 호출 진행은 보이지 않는다. 공고 선택의 후보 목록과 질문(2-1)은 순위가 확정된 직후 진행 줄 사이에 나오며 요약의 일부가 아니다.

실행은 아래 순서로 요약한다. 초안 본문은 기본으로 보이지 않고 md 경로만 보인다(`--show-drafts`일 때 본문).

1. 제목: `mock` 또는 `AI`, 프로필, 공고 수, `demo_run_id`, `pipeline_run_id`
2. 직무 게이트 / 자격요건 / 최종 순위 (참고용 평가, 평가하지 못한 공고 포함)
3. 선택 공고 (사용자가 입력한 번호와 공고 ID)
4. `WriterInput` 안전 분류: 사용 가능 사실 / 확인 필요 / 주장 금지의 **개수와 id만** (문장은 보이지 않는다)
5. 자기소개서, 포트폴리오: 상태, 코드 검증 통과 여부 또는 실패 사유 코드, "생성 성공·저장 실패" 구분
6. 실행 요약: 단계별(게이트, 자격요건, 자소서, 포트폴리오) **모델 ID(요청 / 실제)**, 논리 호출·시도·캐시 적중, 토큰, 모델별 오늘 누적/한도, 종료 상태. JUDGE와 WRITER가 같은 모델이면 "같은 모델"이라고 표시한다.

안내 문구: 이 시스템은 모든 공고에 자기소개서를 만들지 않는다. 평가한 공고 중 선택한 1건에만 만든다.
